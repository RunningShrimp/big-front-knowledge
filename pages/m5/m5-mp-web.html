② 深入浅出

一、技术栈差异：你手里的工具被换了

上一页说过，小程序是双线程：逻辑层里没有 window、没有 document， 所以 document.getElementById、window.addEventListener 这些 Web 里的肌肉记忆，在小程序里全部失效。 取而代之的是框架统一封装的组件（view、text、image）与平台 API（如 wx.request 发请求、 wx.setStorageSync 存本地数据）。写法上 WXML/WXSS 换掉了 HTML/CSS 的部分语法，模板指令 wx:if、wx:for 更接近 Vue 的风格。一句话：骨架还是「结构 + 样式 + 逻辑」，但零件几乎全都换成了平台提供的。

二、生命周期对比：页面「活着」的方式不同

Web 页面的生命周期由浏览器事件表达：文档解析完触发 DOMContentLoaded，资源加载完触发 load， 用户切走标签页触发 visibilitychange，关闭前有 beforeunload。 小程序则把「页面的一生」明确拆成了固定钩子：onLoad（页面加载，只来一次，通常在这里拿路由参数）、 onShow（每次进入前台都会触发）、onReady（首次渲染完成，只来一次）、 onHide（切到后台）、onUnload（页面卸载）。 最大的思维转变是：小程序里「切后台再回来」是常态（用户按 Home 键、切到别的小程序）， onShow/onHide 会被反复触发，而 Web 里对应的 visibilitychange 很少被当成主流程来设计。

三、能力边界：不是想发就发、想多大就多大

Web 部署只要把文件放上服务器，用户刷新就是最新版，页面想写多大都行。 小程序则要整包提交、平台审核，通过后才能发布；包体积也有严格上限 （主包长期在几 MB 量级、整包十几 MB 级别，具体以各平台最新规则为准），大资源通常要放网络或分包。 换来的回报是丰富的开放能力：支付、登录、扫码、蓝牙、位置等原生 API 开箱即用， 这些在纯 Web 里要么做不到、要么权限受限。存储、网络请求等基础能力两端都有，但 API 形状与配额规则不同， 迁移时要逐一对表。

四、迁移思路：一份逻辑层代码如何适配两端

业务逻辑（计算、校验、状态管理）本质上是纯 JS，两端通用；真正「不通用」的是平台接触面： 请求、存储、路由、UI 组件。工程上有三条路：一是自建抽象层——把差异封进自己的模块， 业务代码只面向抽象接口；二是运行时判断——在代码里检测当前环境，走不同的分支； 三是跨端框架——用一份类 React/Vue 的代码，由 Taro、uni-app 这类框架在编译或运行时 把它分别翻译成小程序与 H5。三条路的共同内核都是上一页那句话：差异集中在「平台接触面」，把它隔离出去，逻辑就能复用。

生活类比：自驾游 vs 景区观光车

写 H5 像自驾游：车是你的、油随时加、路随便挑，想去哪儿踩油门就走； 但路况全靠自己应对——不同城市限号规则不同（浏览器兼容差异）、爆胎了得自己换（兼容性 bug 自己修）， 出发前也不用向任何人报备（部署零审核）。自由度拉满，操心的事也拉满。

写小程序像坐景区观光车：上车前要过安检（提交审核），行李有重量限制（包体积上限）， 路线固定、不能随意下车改道（只能用平台组件与 API）；但观光车直达景点（原生能力开箱即用）， 司机熟路不怕堵（平台屏蔽了大量兼容问题），同行乘客的体验高度一致（管控带来的一致性）。 选哪样，取决于你要「随处可达的自由」还是「直达景点的省心」——这正是后面选型课要回答的问题。

④ 知识联结

前置依赖：小程序双线程架构 —— 本页几乎所有差异（没有 DOM、生命周期独立、包审核）都是双线程与平台管控这两个决定的直接后果。

向后延伸：理解差异之后，自然衔接两件事：一是「原生壳 + WebView」的另一条混合路线 （Hybrid 开发与 JSBridge），二是把所有方案摆在一起做决策的 （跨端方案选型）。

交叉链接：

  • 前端路由 —— Web 的 History/Hash 路由 vs 小程序框架自带页面栈，两套路由心智。
  • 浏览器存储 —— localStorage 与小程序 Storage 的能力对位与配额差异。
  • Web 安全 —— 没有 DOM 与 eval 环境后，XSS 攻击面如何变化。
  • Hybrid 开发与 JSBridge —— 同样「壳里跑网页」，混合方案如何补齐原生能力。

⑦ 面试视角

问法一：小程序与 H5 开发的核心区别有哪些？
  • 运行环境：双线程，逻辑层无 window/document，不能操作 DOM；H5 拿到完整 DOM/BOM。
  • 技术栈：WXML/WXSS/框架封装组件 + 平台 API；H5 是标准 HTML/CSS/JS + 浏览器能力。
  • 生命周期：onLoad/onShow/onHide/onUnload 显式钩子，切后台回前台是主流程；Web 靠 DOMContentLoaded、visibilitychange 等事件。
  • 发布与体积：整包提交、平台审核、包体积上限；H5 随时部署、秒级生效。
  • 能力面：小程序开放支付、登录、扫码等原生能力；Web 受浏览器权限约束，但部署与链接触达更自由。
问法二：如何让一份业务代码同时跑在小程序与 H5 两端？
  • 先分层：把纯逻辑（计算、校验、状态）与平台接触面（请求、存储、路由、UI）切开，前者天然跨端。
  • 抽象层：为请求/存储/路由等定义统一接口，两端各给一份实现，业务只面向接口。
  • 运行时判断：检测当前环境后走不同分支；适合差异点少、不想引框架的场景。
  • 跨端框架：Taro、uni-app 等用一份类 React/Vue 代码，编译或运行时分别产出小程序与 H5，适合差异点多、长期维护的项目。
  • 加分项：能指出样式单位差异（rpx 与 rem/vw）与组件差异也要纳入抽象层考虑。
