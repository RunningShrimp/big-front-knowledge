② 深入浅出

一、简化版 Promise：三态流转与 then 链

手写 Promise 的骨架是状态机：只有 pending / fulfilled / rejected 三种状态， 且流转单向、单次、不可逆——pending 只能二选一走向 fulfilled 或 rejected，定型后任何 resolve/reject 调用都必须失效。 then 要做两件事：状态还是 pending 时，把回调存进队列等结果；已定型时安排异步执行（规范要求放进微任务， 用 queueMicrotask 模拟即可）；同时返回一个新 Promise，链式调用才成立。

function MyPromise(executor) {
  var self = this;
  self.state = 'pending';    // 三态之一：pending → fulfilled / rejected，不可逆
  self.value = undefined;
  self.callbacks = [];       // pending 期间收拢的 then 回调
  function resolve(v) {
    if (self.state !== 'pending') return;   // 关键防御：只有第一次生效，之后一律忽略
    self.state = 'fulfilled';
    self.value = v;
    self.callbacks.forEach(function (cb) { cb(v); }); // 真实规范：这里应放进微任务队列
  }
  executor(resolve, function (r) { /* reject 同理：状态改 rejected，同样只认第一次 */ });
}

为什么 resolve 里要判状态？因为 executor 里完全可能写出「先 resolve 再 reject」的代码——不设防线，状态会被来回改，号牌就变成了橡皮图章。 为什么 then 要异步执行？若同步调用回调，「先 then 后 resolve」和「先 resolve 后 then」两种时序的行为就会不一致，违背 Promise 的约定。

二、并发控制：limit 个槽位的调度游戏

并发控制（如 limitConcurrency(tasks, limit)）的核心只有两个变量： next 指针（下一个该启动谁）和 running 计数（现在占着几个槽位）。调度规则一句话： 开局把 limit 个槽位填满；每当一个任务完成，立刻从队列补位启动下一个。常见两种写法：

  • 递归 worker 版：雇佣 limit 个「工人」，每个工人循环取任务——有活就干、干完递归取下一个，队列取空即收工。代码短、直觉好。
  • 循环补位版：用 while (running < limit && index < total) 启动，把「补位」写进完成回调。扩展性好——想加取消、重试、优先级，都在这个结构上改。

两个必踩的坑：一，limit 要先和任务数取小、并拦住 0 和负数（Math.max/Math.min 处理），否则可能出现「槽位比任务多没事，槽位为 0 全卡死」； 二，补位逻辑必须写在完成回调里——写在启动循环里，循环一口气跑完就变成了「全部同时启动」，limit 形同虚设。Promise 场景里补位要放 finally，否则一个任务失败就卡死整个队列。

三、手写 Promise.all / race：计数器思维

all 的骨架：结果数组按传入顺序（不是完成顺序）存放——每个任务用自己下标 i 锁定写入位置； 一个计数器统计已落定数量，等于总数才 resolve。任何一个失败立即整体 reject，其余结果不再等待；空数组直接 resolve([])； 非 Promise 值用 Promise.resolve() 包装。race 更简单：所有任务都往同一个 resolve/reject 上「抢跑」，第一个落定的说了算——无论成败。 选型口诀：一损俱损要全量成功用 all；无论成败做盘点用 allSettled；只关心第一响应（超时兜底）用 race。

四、EventEmitter：发布订阅四件套

一个对象存「事件名 → 监听器数组」就够了：on 是往数组 push；off 是 filter 掉指定函数（按引用比对）； emit 是取出数组依次调用，并把第 1 个参数之后的实参透传给监听器；once 最容易翻车——订阅的是一个包装函数， 触发时先把自己从数组里移除，再执行原函数。注意解绑时比对的是包装函数本身：如果错把原函数拿去比对，永远解绑不掉，once 就退化成了 on。

生活类比 · 十一假期的山谷景区：闸机只发 2 张「同时在园证」

十一假期，山谷景区的环山步道很窄，实测同一时间只容得下 2 个旅行团——挤进去第 3 个团，山道就堵死（对应服务器被打满：内存飙升、响应变慢，甚至崩溃）。于是景区定了规矩：入口闸机手上只有 2 张「同时在园证」（这就是 limit）。

早上 8 点，A 团、B 团先后到达，递材料（调用任务）领证入园；C、D、E 团赶到时证都发出去了，只能在门口排队区等（pending 队列）。B 团逛完从出口出来那一刻，闸机员立刻喊：「下一位！」——C 团无缝补位入园，全程园内永远不超过 2 个团，也永远没有团被落下：先来后到，人人有份。

如果景区不做限流，让所有团一拥而入会怎样？山道堵死、导游找不到人、有人被挤下台阶——对应到代码里就是同时发起几千个请求：带宽打满、连接池耗尽、大量超时失败。所以并发控制的本质不是让任务变少，而是给「同时在跑」这件事上锁：完成的走得体面，等待的排得安心，吞吐量反而因为「不拥堵」而更高。下面这个演示，你就是闸机员。

⑦ 面试视角

问法一：手写并发控制有哪些写法？递归版和循环版怎么取舍？
  • 核心不变量先说清：running 计数永远 ≤ limit；任务完成一个就补位一个，队列不丢不重。
  • 递归 worker 版：起 limit 个工人，每个工人「取任务 → 执行 → 完成后递归取下一个」，队列取空即结束。代码短、好讲。
  • 循环补位版：while 填槽 + 完成回调里补位。结构上更好扩展——取消、重试、优先级、进度回调都能平滑加进去。
  • 边界处理：limit 与任务数取小，并拦住 0/负数；Promise 任务用 finally 补位，防止一个失败卡死整条队列。
  • 加分项：提到社区方案 p-limit / asyncPool 的思路，或说明「deep 递归不会栈溢出，因为补位发生在异步完成回调里，不占调用栈深度」。
问法二：手写 Promise.all 要注意什么？和 allSettled 怎么选？
  • 返回一个新 Promise；结果数组按传入顺序写入（每个任务用自己的下标 i 锁位），与完成顺序无关。
  • 计数器统计已落定数量，count === total 时整体 resolve；任何一个 reject 立即整体 reject，不再等其余。
  • 细节：非 Promise 值用 Promise.resolve() 包装；空数组直接 resolve([])；迭代用 for 循环处理数组即可。
  • allSettled：永不 reject，等全部落定后返回 { status, value / reason } 数组，适合批量任务的成败盘点。
  • 加分项：说明 all 的「快速失败」是一把双刃剑——埋点上报这类「个别失败无所谓」的场景选 allSettled，否则一个失败就丢掉全部成功结果。
