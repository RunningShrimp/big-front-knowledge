② 深入浅出

为什么需要自动化测试

项目每天改几十处代码，每改一次就「人肉把所有页面点一遍」，人越多越不现实。自动化测试就是让机器替你点：把「点开购物车应该看到 3 件商品」写成一行代码，以后每次改完代码跑一遍，几秒钟内告诉你哪些原有功能被改坏了。测试本质上是给未来的自己买保险——写的时候花十分钟，之后每次改动都省下一小时的心惊肉跳。测试用例还有个副产品：它是最诚实的文档，读用例就知道这个函数怎么用、边界在哪。

测试金字塔：三道质检工序

  • 单元测试（底层，量最大）：把最小的独立单元（一个函数、一个工具方法）单独拿出来验证。跑得飞快，失败时直接告诉你「哪个函数的哪个分支算错了」，定位最精确。
  • 集成测试（中层）：把几个模块拼起来验证协作，比如「表单组件 + 校验规则 + 提交接口的假实现」能不能配合出正确行为。
  • E2E 测试（顶层，量最小）：驱动真实浏览器，模拟真实用户从打开页面到完成下单的完整链路。最接近真实体验，但最慢、最贵、挂了也最说不清是哪一层的问题。

健康的比例是金字塔形：单元测试铺得最宽，E2E 只挑几条核心链路。越往上，一次测试覆盖的面越广，但每次的花费和定位难度也越高。

单元测试长什么样

Vitest、Jest 这类主流框架都是同一套风格：用 describe/test（或 it）组织用例，用 expect(实际值).toBe(期望值) 这样的断言描述「应该是什么」。断言失败时框架会打印「期望 4，实际 3」以及出错的用例名——这就是「定位到函数与分支」的来源。

mock：把不确定的依赖换成假货

测「发送验证码」的逻辑时，不能每次测试都真发一条短信。做法是把「短信服务」换成 mock（假实现）：假装发出去，并记下「被调用了几次、传了什么参数」。好处有三：快（不发真实网络请求）、稳（不受第三方服务波动影响）、能制造罕见场景——比如让假服务「恰好超时」「恰好返回 500」，专门验证失败分支。定时器也能 mock：把「等 60 秒后再提示」压缩成立即走完。

组件测试与 Testing Library 思想

测 UI 组件时有个重要原则：像用户一样去测。按「按钮上的文字」「输入框的角色」找到元素、模拟点击、断言界面上出现了用户能看到的变化——而不是去断言组件内部的 state 或某个类名。后者一重构测试就全碎，测的不再是「行为」而是「实现细节」。快照测试是补充手段：第一次运行时把渲染结果记录下来，之后每次对比有没有意外变化。

E2E 测试：整车试驾

Playwright、Cypress 这类工具驱动真实浏览器：打开页面、填表单、点登录、断言跳转到了个人中心。它 catches 的正是「零件都合格、组合起来却出错」的问题。但 E2E 也有出名的脆弱性：弹窗、动画时序、测试数据被别人改了，都可能让它误报。所以业内共识是只给核心链路（登录、注册、下单、支付）写少量 E2E，把大量验证交给快得多的单元测试。

覆盖率：有用的指标，危险的目标

覆盖率回答的是「多少比例的代码在测试中被执行过」。注意它只保证「跑到」，不保证「断言对」——一个没有任何断言的测试也能把覆盖率刷上去，一行不写断言的代码被跑过，bug 照样漏网。优先测的顺序：核心业务规则、公共工具函数、曾经出过 bug 的地方；纯函数（同样的输入永远同样的输出）最容易测。100% 覆盖率不值得追求，为凑数字写的测试本身就是负债。

生活类比 · 玩具车工厂的质检流水线

一家玩具车工厂（你的项目）每天出货一千辆小车（每次发版）。厂里有两道质检工序。第一道是零件质检（单元测试）：螺丝、轮子、电机逐颗上检具，几秒钟一颗；哪个不合格当场拦下，标签上写着「3 号电机线圈短路」——缺陷定位精确到零件（测试失败信息直接指到某个函数的某个分支）。检具便宜耐用，一天能测几万颗，所以厂里铺了满满一墙检具（单元测试数量最多）。

第二道是整车试驾（E2E 测试）：随机抽几台整车装上电池，在跑道上学着小顾客的样子跑一圈。它能抓住零件质检抓不到的问题——比如每个零件单看都合格，但遥控器和电机对不上频（模块各自正确、组合起来出错）。但试驾一台要十分钟，还得配专职司机和一条跑道（真实浏览器环境），所以只测「前进、转弯、遥控」这几条核心路线，不可能把每辆车的每种玩法都试一遍。

最糟的经营决策是：砍掉零件质检、全靠整车试驾。一辆车在跑道上抛锚，你只知道「车坏了」，却要拆开整车逐颗零件排查（E2E 失败定位成本高）。这笔账很好算：零件层拦下一个缺陷花 1 块钱，车子出货后召回要花一百块——bug 被发现得越晚，修复成本翻着倍地涨，而测试金字塔就是这道成本算术的答案。

④ 知识联结

前置依赖：无硬性前置，是「性能与质量」模块里可以直接上手的一页；动手前熟悉函数与数组即可（见 JS 类型、作用域与闭包）。

向后延伸：测试拦得住「写错的代码」，拦不住「线上才出现的意外」——接下来学错误处理与容错设计；而重试、降级这类容错逻辑恰恰最值得被测试保护，两页互为补充。

⑥ 巩固复习

一句话讲给外行听：测试就是产品出厂前的质检流水线——单测像逐颗检查螺丝，又快又便宜、坏了当场指出哪颗坏；E2E 像整车试驾，最接近真实但又慢又贵。两层配合，才能让问题在出厂（上线）前被拦住。

建议复习时间：今天睡前复述 1 次，1 天后、3 天后、7 天后各回来重做一遍例题（对应遗忘曲线 1/3/7 天间隔），站点会在地图页标出「该复习了」。

⑦ 面试视角

问法一：单元测试和 E2E 测试各有什么优缺点？项目里怎么搭配？
  • 单元测试：快（毫秒级）、便宜、失败定位精确到函数与分支；缺点是只验证孤立单元，覆盖不到模块组合的问题。
  • E2E 测试：最接近真实用户链路，能发现「零件都对、组合出错」的问题；缺点是慢、环境脆弱易误报、失败时难以定位到具体层。
  • 搭配方式：按测试金字塔分配——单元测试覆盖核心逻辑与工具函数（数量最多），少量集成测试验证模块协作，E2E 只覆盖登录、下单、支付等核心链路。
  • 加分项：能说出「bug 发现越晚修复越贵」，金字塔形状本质是成本算术；以及异步逻辑要靠 mock 定时器 / 假 Promise 才能测得又快又稳。
问法二：测试覆盖率刷到 100%，就代表代码没有 bug 了吗？
  • 覆盖率只统计「代码被执行过」，不统计「断言是否正确、场景是否穷尽」——没有断言的测试同样能刷高覆盖率。
  • 边界与组合没测到照样有 bug：覆盖率高的函数，遇到没覆盖到的输入组合依然会错。
  • 为凑数字写测试是负债：把简单实现「锁死」的测试会阻碍重构，维护成本反而上升。
  • 正确用法：把覆盖率当作发现「完全没被测试触碰的模块」的探照灯，重点补核心业务与高频变更区域的测试，而不是追求全局数字。
