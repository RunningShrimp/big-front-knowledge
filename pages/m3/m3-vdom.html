② 深入浅出

一、先看问题：直接操作 DOM 为什么「贵」

你在页面里写的一行 <li>苹果</li>，在浏览器内部远不止一个标签：它会变成一坨带属性、样式、事件、布局信息的重量级对象。 更麻烦的是，很多 DOM 改动（比如改尺寸、插入节点）会触发重排——浏览器要重新计算一堆元素的位置和大小，再重新画出来。 如果一段代码里连续改 100 处 DOM，浏览器可能就要白白重排很多次。具体重排有多伤性能，可以去看 重排与重绘那一页，这里记住一句话就够：DOM 操作次数越多，页面越卡。

二、虚拟 DOM：用轻量 JS 对象「描述」页面

既然真 DOM 又重又贵，那就先别急着碰它。框架用一个普通 JS 对象来「画图纸」：

{ tag: 'ul', props: { class: 'list' }, children: [
  { tag: 'li', children: ['苹果'] },
  { tag: 'li', children: ['香蕉'] }
] }

这棵「对象树」就是虚拟 DOM。它是纯 JS 数据：创建、复制、修改、比较都飞快，碰不到昂贵的真实 DOM。 页面渲染时，框架把这棵树「翻译」成真实 DOM；数据变化时，先在内存里生成一棵新树，再想办法只更新变化的部分。

三、Diff：新旧两棵树怎么比才快

「找出两棵树的差异」如果全量比较，复杂度是天文数字。所以各家框架都遵守三大启发式策略，把比较降到接近 O(n)：

  • 只做同层比较：旧树第 2 层只和新树第 2 层比，不跨层乱配。一个节点跨层移动，会被当作「旧的删掉、新的新建」处理。
  • 类型不同直接重建：旧的是 <h1>、新的是 <h2>，标签类型都变了，就不再深入比较，整棵子树推倒重建。
  • 列表靠 key 精确配对：同层的一排 <li>，用稳定的 key 当「身份证」对上号——谁该复用、谁该删、谁该增，一目了然。

四、Patch：把差异变成最少的真实 DOM 操作

Diff 的产出不是「重建整棵树」，而是一张补丁清单：替换 1 处、改文本 1 处、删 1 处、插 1 处。 框架把这张清单批量应用到真实 DOM 上，没出现在清单里的节点一概不动。这就是「最小化 DOM 操作」的更新流程： 数据变化 → 生成新虚拟树 → Diff 出补丁 → 批量 Patch 真实 DOM。

生活类比 · 装修的效果图

虚拟 DOM 就像装修前的设计效果图。你想改造房子（更新页面），不会让工人直接进场边拆边试； 而是让设计师在纸面上（内存）把「旧方案」和「新方案」两张效果图逐个房间对比，列出一份改动清单： 客厅的电视墙改个颜色、次卧的旧柜子拆掉、阳台新增一个花架。

工人（真实 DOM 操作）只按清单干活：没出现在清单里的墙一概不碰。房子不用推倒重装，改动却一处不漏。 Diff 就是「逐房间对比出清单」的过程，Patch 就是「按清单施工」的过程。

五、诚实地说：虚拟 DOM 不是「最快」的方案

虚拟 DOM 先生成对象树、再 Diff、再打补丁，相当于多算了一步。如果你能明确知道哪 3 个节点要改， 手写 3 句 dom 操作 肯定比虚拟 DOM 更快。它换来的，是声明式开发下「够用且稳定」的性能：你只管描述「界面应该长什么样」， 框架自动算出最少的更新。这是性能与可维护性之间的折中，面试时能说出这层取舍，比背「虚拟 DOM 快」三个字值钱得多。

④ 知识联结

前置依赖：对象与原型——虚拟 DOM 本质是「对象套对象」的数据结构， 属性访问、引用比较这些基础不牢，Diff 的代码会完全看不懂。

向后延伸：学会虚拟 DOM，就拿到了框架的「渲染底盘」。 React 核心与 Hooks 靠它实现 setState 后的重渲染； Vue 响应式原理则更进一步，先精确知道「谁变了」再走虚拟 DOM，两条路线殊途同归。

交叉链接：

  • 重排与重绘 —— 「直接操作 DOM 为什么贵」的底层答案：改布局引发重排，正是虚拟 DOM 想省掉的开销。
  • 小程序双线程架构 —— 小程序逻辑层碰不到真实 DOM，靠 setData 传「类似虚拟 DOM 的描述」跨线程渲染。

⑥ 巩固复习

一句话讲给外行听：虚拟 DOM 就是先在「草稿纸」上把页面画成一张轻量的数据图， 数据一变就先在草稿纸上对比出「到底哪几处要改」，再拿着清单去动真正的页面——改得少、不出错。

建议复习时间：今天睡前复述 1 次「数据变化 → 新树 → Diff → Patch」流程，1 天后、3 天后、7 天后各回来重做一遍例题（对应遗忘曲线 1/3/7 天间隔），站点会在地图页标出「该复习了」。

⑦ 面试视角

问法一：列表渲染为什么要有稳定的 key？用数组下标当 key 会怎样？
  • key 是同层列表节点的「身份证」，Diff 靠它把旧节点和新节点一一配对，从而正确判断「复用、移动、删除、新增」。
  • 用稳定的业务 id：在中间插入/删除一项时，其他项的 id 不变，框架能精准复用旧节点，只做最小更新。
  • 用数组下标当 key：头部插入一项会让所有项的 key 集体前移，框架误以为「每一项的内容都变了」，触发大面积多余的更新。
  • 更糟的是带内部状态的节点（如输入框）：内容错位复用，会出现「文字串行」的经典 bug。
  • 加分项：用随机数当 key 等于每次渲染都「换身份证」，节点全部重建，比 index 更差。
问法二：虚拟 DOM 一定比直接操作真实 DOM 快吗？它的价值到底是什么？
  • 不一定。虚拟 DOM 要先建对象树、再 Diff、再打补丁，本身有额外计算量；首次渲染甚至比直接 innerHTML 更慢。
  • 在「明确知道改哪」的极端场景下，手写精准 DOM 操作可以更快，但代码难写、难维护、容易漏更新。
  • 虚拟 DOM 的真正价值：让开发者用声明式写法（只描述界面该长什么样），框架用同层 Diff（接近 O(n)）自动算出接近最少的更新——性能「够用」且大规模可维护。
  • 加分项：可对比 Vue 的响应式方案——先精确知道哪个数据变了再小范围更新，是同一种「少碰真实 DOM」思想的不同实现路线。
