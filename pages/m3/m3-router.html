② 深入浅出

一、从「翻页」说起：多页应用 vs 单页应用

早期的网站是多页应用（MPA）：点一个链接，浏览器把整个 URL 发给服务器，服务器现做一张新 HTML 寄回来， 整页白屏重画一遍——就像每翻一页都要重新复印一整本书。而现在的 单页应用（SPA）只从服务器拿一次 HTML 外壳，之后「换页面」这件事全部在浏览器里完成： 地址栏变了、内容变了，但页面从不整体刷新。让「同一个外壳里的视图」随 URL 变化而切换的那套机制，就是前端路由。

二、前端路由要解决的核心问题

一句话：URL 变了，谁来负责换内容？前端路由器干三件事—— ① 监听 URL 变化（事件）→ ② 从 URL 里解析出该显示哪个视图（解析）→ ③ 换上对应的视图（渲染）。 而「URL 怎么变才不会惊动服务器」，衍生出两大流派：hash 模式和 history 模式。

三、hash 模式：借地址栏的「备注栏」记路由

URL 中 # 后面的部分叫「锚点（hash）」。浏览器有个历史遗留的规矩： hash 变化被视为页面内部的跳转，既不刷新页面，也永远不会把 # 后面的内容发给服务器。 于是前端路由器把路由信息全部写在 # 后面（如 index.html#/detail/42）： 改 location.hash 或点锚点链接 → 浏览器触发 hashchange 事件 → 路由器解析 hash、渲染视图。 服务器从头到尾只知道一件事：给我 index.html。

四、history 模式：正经地址 + pushState

hash 模式的地址总带着个 #，不够体面。HTML5 给了 history.pushState： 它可以在不刷新页面、不发送任何请求的前提下，把地址栏改成一个正经路径（如 /detail/42）， 并往浏览器的会话历史里塞一条记录。路由器监听 popstate 事件来响应「用户按了前进/后退」。 注意一个常考细节：pushState / replaceState 自己不会触发 popstate，popstate 只在用户点击前进/后退（或调用 go/back/forward）时触发， 所以路由库要在封装的跳转函数里手动通知视图更新。

五、history 模式的坑：刷新 404 与 Nginx 兜底

hash 模式刷新时，浏览器只请求 index.html（# 后不发出去），永远安全。 history 模式刷新时，地址栏的完整路径会被原样发给服务器——浏览器请求 GET /detail/42， 可服务器上根本没有这个文件，直接 404。解决办法是在服务器做「兜底重写」：所有找不到的路径统统回源到 index.html， 让页面先回来，再由前端路由器接管渲染。Nginx 的经典写法是 try_files $uri $uri/ /index.html;。部署细节可以去看 部署基础：Nginx 与 Docker。

生活类比 · 商场导览屏与只认门牌号的保安

SPA 就像一栋固定的商场：楼还是那栋楼（页面不刷新），大堂里那块导览屏（视图）随时切换内容——你从「餐饮层」看到「电影院」， 不需要拆掉重建商场，屏幕换画面而已。前端路由器就是导览屏的换片程序：看到你输入哪个展厅名，就播哪套画面。

hash 模式像把目的地写在门票背面的备注栏：保安（服务器）检票时只看门票本身（index.html）， 背面写了什么他根本不看、也不管——所以你随手改备注（改 hash）永远不会被保安拦下，也无须重新买票。

history 模式则把目的地直接印在门票正面，体面好看。但一旦你走出商场再回来（刷新页面）， 保安只认正门编号（真实存在的 index.html），看到票面写着「三楼中庭影院」（/detail/42）就懵了： 查无此门，直接把你拦下（404）。解决办法是给保安一本备忘录（Nginx try_files 兜底规则）： 「凡是不认识的门牌，一律先领客人回大堂（回源 index.html），再让导览屏带他去想去的地方。」

⑥ 巩固复习

一句话讲给外行听：前端路由就是让网页「换内容不换页」的换片程序——hash 模式把目的地写在门票背面（# 后），保安看不见所以永远安全； history 模式把目的地印在门票正面（体面），但刷新时保安看不懂就要靠服务器备忘录（try_files 兜底）先把你领回大堂。

⑦ 面试视角

问法一：hash 模式和 history 模式有哪些区别？各自怎么选？
  • 原理：hash 依赖 hashchange 事件，路由写在 # 后、永不上传服务器；history 依赖 pushState/replaceState 改地址 + popstate 响应前进后退。
  • 刷新行为：hash 刷新只请求 index.html，天然无 404；history 刷新会把完整路径发给服务器，必须配 try_files 之类的兜底。
  • 外观与 SEO：history 地址干净无 #；对需要服务端配合 SEO 的站点更友好（hash 路由对爬虫不透明）。
  • 兼容与部署成本：hash 兼容性极好、部署零配置；history 要求服务器支持兜底重写，但现代项目默认都选 history。
  • 加分项：说出「锚点本是浏览器滚动定位机制，hash 路由是借用了这个历史遗留行为」。
问法二：手写一个简易前端路由，你的思路是什么？pushState 为什么不触发 popstate，视图怎么更新？
  • 三件套：监听变化（hashchange / popstate）、解析路径（如把 /user/:id 与当前路径按 / 分段配对，冒号段收进 params）、按匹配结果渲染对应视图。
  • 跳转封装：hash 模式改 location.hash 即可；history 模式封装 navigate()，内部调 pushState 后手动调用渲染函数，再派发一个自定义事件（如 routechange）供外部订阅。
  • 为什么 pushState 不触发 popstate：popstate 的语义是「用户在历史记录间移动」，pushState 只是写入一条新记录，规范如此设计以区分「程序改地址」与「用户后退」。
  • 加分项：提到路由守卫（跳转前拦截）、动态路由匹配、嵌套路由，都是在这三件套上加规则。
