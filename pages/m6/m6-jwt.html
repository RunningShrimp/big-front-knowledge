② 深入浅出

一、Session 的两个烦恼

上一页的「柜子与钥匙」好用，但有两个烦恼：其一，服务端要腾地方存，用户一多，柜子管理本身成了负担；其二，多台机器要共享一本登记簿，必须引入 Redis 这样的集中存储。能不能反过来——服务端什么都不存，把「你是谁」直接写在凭证上交给用户随身带，服务端只验真伪？这就是 JWT（JSON Web Token）的思路。

二、拆开三段式：Header、Payload、Signature

一个 JWT 长这样：三段字符串用两个点号连起来。Header 声明签名算法（如 {"alg":"HS256","typ":"JWT"}）；Payload 放具体信息（{"uid":7,"role":"user","exp":1735689600}，exp 是过期时间戳）；Signature 是前两段的签名。前两段只是做了 base64url 编码——注意，编码不是加密！拿任何工具都能解开看，所以 Payload 里绝不能放密码、身份证号这类敏感明文。真正防止「被改」的是第三段签名。

三、签名：信息可见，但改不动

签名怎么算？服务端持有一把只有自己知道的密钥，用 Header 声明的算法对「Header.Payload + 密钥」做一次不可逆的运算（真实世界是 HMAC-SHA256），得到一串签名附在末尾。验证时服务端用同样的密钥重算一遍，与 token 上带的签名比对：一致，说明前两段一个字都没被动过；不一致，直接拒绝。整个验证过程不需要查任何数据库——这就是「无状态」的含义：数学保证真伪，存储不背锅。攻击者改了 Payload？签名对不上。自己伪造签名？没有密钥算不出来。密钥一旦泄露，所有 token 都能被伪造——所以密钥的保管级别等同最高权限。

四、JWT vs Session：一张对照表

两者没有绝对优劣，只有场景取舍：JWT 的优势是服务端免存储、天然跨服务（任何持有密钥的服务都能验签），分布式扩容不再需要共享登记簿；代价也明确：① token 比一个 SessionID 大得多，每个请求都多背一点流量；② 签发出去就收不回——服务端不存状态，就没法「立即作废」某个 token，注销只能靠黑名单、token 版本号这类「重新引入状态」的手段，或把有效期压短、配合 refresh token 换发；③ Payload 谁都能解码，敏感信息不能放。典型组合拳：access token（短命，十几分钟）+ refresh token（长命，用于换新），把泄露窗口压到最小。

五、OAuth 2.0：不是登录，是「授权」

「用微信登录」背后的协议是 OAuth 2.0，它解决的其实是另一个问题：让第三方在不知道你密码的前提下，拿到有限的授权。最常用的是授权码模式，完整时序五步走：① 你在 A 网站点「用微信登录」，被跳转到微信授权页；② 你确认后，微信回跳 A 网站并附上一个一次性的授权码 code（只经浏览器中转，真正的令牌不在浏览器露面）；③ A 网站后端拿 code + 自己在微信注册时获得的 client_secret，去微信服务器换 access token（密钥只走服务端之间的通道）；④ 用 token 调微信接口拿到你的昵称头像；⑤ A 网站据此建立自己的会话。为什么要 code 中转而不是直接发 token？因为浏览器这一段是「公开信道」，code 又短命又需配密钥才能兑换，把敏感令牌的交换压缩在服务端之间完成，泄露面最小。

生活类比 · 防伪工牌：信息印在卡上，钢印保证改不动

入职那天，HR 给小帅打印了一张工牌：正面印着「小明 · 前端组 · 实习生」——这些信息人人都看得见（Payload 只是编码不是加密，所以工资这类敏感数字千万别印上去）；背面盖上了一枚钢印（Signature）。钢印是用公司的印章模板压出来的，模板锁在 HR 保险柜里（服务端密钥），外人拿不到。

之后每天进大楼，保安不查任何系统，只掏出同款模板对着钢印比一下：对得上就放行——大楼里没有一个「会员登记处」，验真全靠比对（无状态验证）。某天小帅动起了歪脑筋，拿笔把「实习生」改成「总监」：字迹确实改了，但钢印还是旧内容的钢印，保安一比对就穿帮（篡改 Payload 立即验签失败）。他想干脆自己刻个章？没有模板，刻出来的纹路对不上（没有密钥伪造不了签名）。

但这套体系有个软肋：工牌一签发，保安只认钢印不查名单——小帅被开除了，工牌还在有效期，照样能刷卡进楼（JWT 注销难题）。公司的补救办法：把有效期印短一点，每天回 HR 换新牌（access + refresh）；或者前台放一本「作废名单」，验钢印之外再翻一眼（黑名单——代价是又引入了一点状态）。至于 OAuth 2.0，就像酒店入住：你不把身份证押在前台（不交微信密码），前台核实身份后给你一张临时房卡（token），只能开指定楼层（scope 权限范围），退房自动失效——授权完成，密码从未离开你手里。

向后延伸：理解了「用密钥签名验真身」，再去看登录态在微服务间的传递、单点登录（SSO）的设计会顺理成章； token 的存放位置与传输安全是部署层课题，见部署基础：Nginx 与 Docker 里的统一入口与 HTTPS 终结。

交叉链接：

  • HTTPS 与 TLS 握手 —— 数字签名与 CA 证书链的「用密钥证明我是我」，和 JWT 验签是同一套数学思想的不同应用
  • Web 安全：XSS、CSRF 与 CSP —— token 放 localStorage 有 XSS 风险、放 Cookie 有 CSRF 风险，权衡正是安全篇的延续
  • RESTful API 设计 —— 401（未认证：没带或带错凭证）与 403（已认证但无权限）的语义边界，靠鉴权中间件落地

⑦ 面试视角

问法一：JWT 是无状态的，那如何实现「注销」和「续期」？
  • 先点破矛盾：注销的本质是「让已签发、未过期的 token 提前失效」，而 JWT 的卖点恰恰是服务端不存状态——两者天然冲突。
  • 方案一 黑名单：把要作废的 token（或其 jti 唯一号）存入 Redis，验签后再查一眼名单；代价是重新引入了存储与查询。
  • 方案二 版本号：用户表存一个 token_version，签发时写进 Payload，改密码/登出全端时版本号 +1，旧 token 全部失效。
  • 续期组合拳：access token 短命（分钟级）+ refresh token 长命（天级），过期后用 refresh 换新；refresh 服务端可存可撤，作废能力落在这里。
  • 加分项：指出「短有效期本身就是兜底」——窗口压得足够小，泄露危害可控；再按敏感级别决定是否上黑名单。
问法二：认证与授权的区别是什么？OAuth 2.0 授权码模式为什么要有授权码这个中转？
  • 认证（Authentication）回答「你是谁」：验明身份，如账密登录、验 JWT；授权（Authorization）回答「你能干什么」：有没有权限做这件事，如角色、scope。
  • OAuth 2.0 是授权框架而非登录协议：第三方拿到的是「代表你访问某些资源的许可」（scope 限定的 token），不是你的密码。
  • 授权码模式时序：跳转授权页 → 用户确认 → 带 code 回调 → 后端拿 code + client_secret 换 access token → 调接口取资料 → 建立自有会话。
  • code 存在的意义：浏览器这一段是半公开信道，code 短命、一次性、且必须配 client_secret 才能兑换——真正敏感的 token 只在服务端之间交换，泄露面最小。
  • 加分项：能对比隐式模式（token 直接经浏览器，已不推荐）说明授权码模式在安全上的进步。
