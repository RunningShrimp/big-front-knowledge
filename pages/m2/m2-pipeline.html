② 深入浅出

一、从「一串文字」到「满屏像素」

打开网页的瞬间，浏览器拿到的其实只是一串纯文本——HTML 源码；而屏幕上最终显示的是一格一格的像素。从「文本」到「像素」中间有一条固定的加工流水线： 解析 → 合成渲染树 → 布局 → 绘制 → 合成。这条流水线就叫渲染流水线。理解了它，后面所有性能优化的讨论（这一模块后面的重排重绘、性能指标）都有了坐标系：任何一次页面改动，本质上都是问「流水线要从哪一站重新跑」。

二、第一站：解析出两棵树——DOM 与 CSSOM

浏览器读 HTML 是从上到下逐个标签读的：读到 <html> 搭树根，读到 <body> 长枝干，读到段落、图片就长出叶子——最终搭成一棵 DOM 树（文档对象模型），它回答「页面上有什么、什么结构」。 与此同时，遇到 CSS（无论是 <style> 内嵌还是 <link> 外链），浏览器会逐条解析出 CSSOM 树：它回答「每类节点长什么样」。为什么要分成两棵树？因为「结构」与「样式」职责不同：结构基本只在加载时构建一次，而样式可能被脚本随时增删，分开管理才能各自缓存、按需更新。

三、第二站：合成渲染树——只留「画得到」的

两棵树都就位后，浏览器遍历 DOM 中的可见节点，去 CSSOM 里查出它应该有的样式，组装成渲染树（Render Tree）。两个高频细节： <head>、display: none 的节点不在渲染树里（它们根本不会画上屏幕）；而 visibility: hidden 的节点在渲染树里（看不见但占着位置，仍要参与布局）。所以「DOM 里有」和「屏幕上画」不是一回事，渲染树就是二者的分界线。

四、第三站与第四站：布局（Layout）与绘制（Paint）

布局：拿着盒模型（content / padding / border / margin）给每个节点算出它在视口里的确切 x、y 坐标和宽高——相当于施工前「量尺寸、定位置」。 绘制：把每个节点的外观（背景色、边框、文字、阴影）画成一格一格的像素。注意此时还没直接画到屏幕上，而是先画在一层层「草稿纸」（图层）上，为最后的合成做准备。

五、第五站：合成（Composite）——分层拼装亮相

现代浏览器会把页面拆成若干图层（比如做了 transform 动画的元素、Will-change 标记的元素会单独成层），合成线程把这些图层像贴纸一样按正确顺序叠起来，输出最终画面。合成的特别之处：它主要靠 GPU 完成，不必惊动跑 JS 的主线程——这正是下一页「为什么 transform 动画快」的伏笔。

六、脚本与样式的阻塞：普通、defer 与 async

浏览器默认假设 JS 可能会改文档结构（历史遗留的安全假设），所以普通 <script> 下载时会暂停 HTML 解析，执行时同样暂停——脚本越大，白屏越久。两个属性用来化解： defer：下载不阻塞解析，等 HTML 解析完、DOMContentLoaded 事件之前按出现顺序执行——适合依赖完整 DOM、讲究先后顺序的主脚本； async：下载不阻塞解析，下载完立即执行，多个之间顺序不保证——适合互不依赖的独立脚本（如统计埋点）。 CSS 也会阻塞：CSSOM 没建完，渲染树就合成不了，所以 CSS 会阻塞首次渲染；而且 CSS 还会阻塞它后面的普通 JS 执行（脚本可能要读取样式）。这就是「CSS 要放头部尽早加载、非关键 JS 加 defer」的根本原因。

七、首屏关键路径与优化切入点

「首屏关键路径」= 从收到 HTML 到首次画出内容，必须经过的最短资源与工序链。优化思路就三条： ① 关键资源早点开始下：压缩体积、减少请求数、非关键 JS 用 defer/async； ② 关键资源尽量小：精简首屏 CSS、关键样式内联，别让 CSSOM 迟迟建不完； ③ 让流水线少跑回头路：首屏别频繁改动触发重排重绘（下一页细讲）。 面试里「从输入 URL 到页面展示」的完整回答就是两段拼接：网络段（DNS 解析 → TCP 握手 → TLS 握手 → 发请求收响应）＋ 渲染段（解析 HTML/CSS → 渲染树 → 布局 → 绘制 → 合成 → 屏幕亮起）。

生活类比 · 老王家装修流水线

老王家装修新房，开工前有两份材料：设计院的图纸（DOM：客厅连着餐厅、餐厅连着厨房——只管结构关系）和一份风格清单（CSSOM：墙面米白、地面木地板、儿童房浅蓝——只管长什么样）。 工头把两份合成一份施工方案（渲染树）：方案里没有储物间——因为它标了「不装」（display:none，等于不存在）；但主卧暗柜要留位置——标的是「不外露但占地方」（visibility:hidden）。 接着量尺员进场，量出沙发距北墙 2.3 米、餐桌居中（Layout）；油漆工刷墙铺地、把颜色纹理变成实物（Paint）；最后家具进场，窗帘、挂画分层摆好，全屋拍照定格交付（Composite）。 装修中途改主意也有讲究：换一幅挂画，拍张照就完事；可要是砸墙改户型，量尺、刷漆、家具摆位全得重来——这正是下一页「重排与重绘」要讲的故事。

④ 知识联结

前置依赖：CSS 盒模型与 Flex·Grid 布局——布局工位算的就是盒模型的几何；不懂 content/padding/border/margin 四层，就看不懂浏览器在量什么。

向后延伸：流水线跑完不是终点。页面会被 JS 反复改动，每次改动都可能让流水线「部分重跑」——代价多大、怎么省，就是下一页重排、重绘与合成层的主题；再往后，Core Web Vitals 性能指标把「首屏多久亮、交互多久响应」量化成了可考核的数字。

交叉链接：

  • HTML 语义化与页面结构 —— DOM 树长什么样，取决于你写的 HTML 结构是否清晰。
  • CSS 进阶：BFC、层叠上下文与动画 —— 合成站「分层贴纸」怎么叠，层叠上下文说了算；transform 动画为什么快也在这里埋了线索。
  • 虚拟 DOM 与 Diff 算法 —— 框架层减少真实 DOM 操作，本质是少让流水线回头重跑。

⑥ 巩固复习

⑦ 面试视角

问法一：从输入 URL 到页面展示，中间发生了什么？（经典开场题）
  • 网络段：URL 解析 → DNS 把域名换成 IP → TCP 三次握手建连（HTTPS 再加 TLS 握手）→ 发送 HTTP 请求 → 服务器返回 HTML（期间命中缓存则可能免下载）。
  • 渲染段：解析 HTML 构建 DOM（遇到 CSS 并行构建 CSSOM；普通 script 阻塞解析，defer/async 不阻塞）→ 合成渲染树（去掉 head 与 display:none 节点）→ 布局计算几何 → 绘制生成图层像素 → 合成线程把图层叠合输出 → 屏幕亮起。
  • 结构化答法：把回答拆成「网络段 + 渲染段」两大块，再各展开三五个小点，比想到哪说到哪清晰得多。
  • 加分项：提到首屏关键路径与优化（关键 CSS 内联、JS 加 defer、资源压缩）；提到白屏多发生在「CSSOM 未就绪 / 阻塞脚本下载慢」。
问法二：defer 和 async 有什么区别？各自适合什么场景？
  • 共同点：两者下载阶段都不阻塞 HTML 解析。
  • defer：等 HTML 解析完成后、DOMContentLoaded 事件触发前执行；多个 defer 脚本按出现顺序执行——适合依赖完整 DOM、有先后依赖的主逻辑脚本。
  • async：下载完立即执行，执行时会阻塞解析；多个 async 脚本执行顺序不保证（谁先下完谁先跑）——适合互不依赖的独立脚本，如统计埋点、广告。
  • 普通 script（无属性）：下载与执行都阻塞解析——这是浏览器「脚本可能改文档」的默认假设，放 body 底部是历史上绕开阻塞的土办法。
  • 加分项：指出 CSS 也会阻塞首次渲染与后续普通 JS 执行（渲染树依赖 CSSOM，脚本可能读样式）；动态创建的 script 默认行为等同 async。
