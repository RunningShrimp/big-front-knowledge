② 深入浅出

一、从一个痛点说起：接口命名为什么不能随心所欲

很多新手这样设计接口：/getUserList、/deleteUserById、/createOrder——每个接口自带动词，像每道菜都写满做法。 坏处是：对接的人要挨个读文档才知道「谁是谁」，而且同样的动作（查、增、删）每套接口拼法都不同。 REST（Representational State Transfer，表述性状态转移）给出的答案是两条分工：URL 只说「什么东西」（资源，用名词），动作全部交给 HTTP 方法（GET/POST/PUT/DELETE）。于是同一套规矩覆盖所有接口，看 URL 和方法就能猜出大半行为。

二、URL 设计规范：名词复数、层级克制、版本前置

资源用名词复数：/users 是「用户集合」，/users/42 是「集合里的第 42 个」——集合与单个天然由 URL 区分，不用再造 /userList。 需要「用户的订单」时做一级嵌套 /users/42/orders，但嵌套超过两层建议改用查询参数（/orders?userId=42），否则 URL 越拼越长。 接口会有不兼容的改动，所以路径里放版本号 /api/v1/users。过滤、分页、排序都走查询参数，不放路径里。

三、HTTP 方法语义表：动词就这五个，别自创

两个关键词先说清：安全指不改变服务器状态（只读）；幂等指执行一次和执行多次效果相同。 GET 读取，安全且幂等，可被缓存；POST 新建/提交，不幂等（点两次可能建两条）；PUT 全量替换，幂等（替换多少次结果一样）； PATCH 局部更新，通常不幂等；DELETE 删除，幂等（删两次还是那个结果）。 幂等不是学究概念：网络超时后客户端敢不敢自动重试，就看方法是否幂等。

四、状态码语义化：回执要用统一格式

常见误用是「所有响应都返回 200，成功与否再看 body 里的 code 字段」。这会让监控、网关、浏览器缓存全部失明——它们只认状态码。 该用的几枚印章：200 成功；201 新建成功（Created）；204 成功但无返回体（删除常用）； 400 参数错误；401 未认证（没登录 / 凭证失效）；403 已认证但无权限；404 资源不存在；500 服务端出错。 一句话分界：401 是「查无此人（身份）」，403 是「知道你是谁，但你不配」。

五、统一响应结构与分页过滤排序

列表类接口三件套是约定俗成的查询参数：GET /api/v1/users?page=1&size=20&sort=created_at:desc&status=active——分页（page/size）、排序（sort）、过滤（status）。 返回体建议统一外层结构（如 { code, message, data }，列表再带 total 供前端算页码），前端就能用同一套封装处理所有接口。 注意分寸：状态码负责「大类」，body 里的 code/message 负责「业务细节」，两者互补而不是互相取代。

生活类比 · 老钱庄与 RESTful 银行的区别

老式钱庄办事全靠打听：办汇兑去东屋找张掌柜，存银子去西屋找李掌柜，每添一个新业务，客户就得重新认识一位掌柜、学一种单据——这就是「动词满天飞」的接口风格。

RESTful 银行立了三条店规：第一，单据上先写清「哪个账户」（URL 表资源，只写名词，如「储蓄账户 42 号」）； 第二，动作从柜台顶上那块固定牌子里勾选——存、取、查、销户，对应 POST / PUT / GET / DELETE，柜员看见勾选就知道标准流程，连你讲故事的时间都省了； 第三，回执格式全行统一（状态码语义化）：盖「办讫」（200/201）、「金额不足」（400）、「账户不存在」（404）、「权限不够」（403），一眼可辨，稽核部门（监控系统）扫一眼回执就能统计全行业务。 之后银行推出基金、外汇等新业务，不过是多了几种「资源」，三条店规一字不改——这就是 REST「统一接口」的好处。

④ 知识联结

前置依赖：HTTP 服务：Express 与 Koa——REST 是「接口该怎么设计」，框架是「接口该怎么实现」。

向后延伸：规范的接口是系统设计的地基，见前端侧系统设计；资源最终要落库，衔接数据库基础与索引。

交叉链接：

  • HTTP 协议基础 —— 方法与状态码的本体语法都定义在协议层，REST 只是给它们派了用场
  • HTTP 缓存 —— 只有 GET 这类安全幂等的方法才放心缓存，REST 语义直接决定缓存策略
  • Cookie、Session 与鉴权基础 —— 401 与 403 的分界线，正是「未认证」与「未授权」的分界线

⑦ 面试视角

问法一：说说你理解的 REST 设计原则？现场设计一个用户模块的 API。
  • 核心思想：一切皆资源——URL 表资源（名词复数），HTTP 方法表动作，状态码表结果，统一接口降低沟通成本。
  • 示范设计：GET /api/v1/users?page=1&size=20（分页列表）、POST /api/v1/users（新建，回 201）、GET/PUT/PATCH/DELETE /api/v1/users/42（详情/全量更新/局部更新/删除，删除回 204）。
  • 层级克制：用户订单用 /users/42/orders，超过两层改查询参数 /orders?userId=42。
  • 版本化：/api/v1 前缀，不兼容改动升版本而不是原地改语义。
  • 加分项：主动谈幂等性（PUT/DELETE 幂等、POST 不幂等）对超时重试安全性的意义。
问法二：GET 和 POST 有什么区别？为什么不能把所有接口都返回 200 再用 body 里的 code 区分？
  • GET 语义是获取资源：安全、幂等、可被缓存、可收藏为书签，参数按惯例放 URL 查询串。
  • POST 语义是提交处理：不幂等（可能产生新资源或副作用）、一般不被缓存，数据放请求体。
  • 两个常见误区：「GET 比 POST 安全」不成立（URL 反而更易被日志记录，机密靠 HTTPS）；「GET 不能传参」不成立（查询串就是它的传参方式）。
  • 全 200 的坏处：网关、监控、浏览器缓存、重试中间件都只认状态码，全 200 等于把所有语义信息私有化到 body，故障率统计与自动重试全部失灵。
  • 加分项：401（未认证）与 403（未授权）的分界；201 配合 Location 头返回新资源地址。
