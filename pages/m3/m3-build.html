② 深入浅出

一、浏览器只认识它认识的，构建工具补上剩下的

你写的工程代码浏览器往往「一口吞不下去」：几百个模块文件（总不能发几百个请求）、TypeScript/JSX 这类浏览器不认识的语法、 还要兼容旧浏览器（语法降级）、上线前要把体积压到最小（压缩混淆）、把环境变量注入代码。这些脏活累活， 全部交给构建工具（Webpack / Rollup / esbuild / Vite）在代码送进浏览器之前处理。它的四大本职： 模块合并（打包）、语法降级（编译转译）、资源压缩、环境变量注入——记住这个清单，就不会把它神化成「黑魔法」。

二、传统方案 Webpack：先全部打包，再开始服务

Webpack 的开发流程是：npm run dev → 从入口出发递归分析整个依赖图， 把所有模块编译、合并成若干 bundle → 打包完毕，dev server 才开始提供服务。 项目越大，依赖图越大，「启动前的等待」就越长——哪怕你今天只想改首页的一行字， 它也要先把几千个模块全部嚼一遍。冷启动慢是这条路线的天然代价。

三、Vite 的思路：开发时按需编译，利用浏览器原生 ESM

Vite 反着来：开发环境几乎不打包。启动 dev server 时只做一件轻活——用 esbuild 把第三方依赖预构建一下 （把 CJS 依赖转成 ESM、把碎文件合并），源码模块一个都不碰。然后它直接把「未经打包的源码」交给浏览器： 现代浏览器本来就走 <script type="module"> 的原生 ESM 加载，遇到 import 就向 dev server 要那个文件， Vite 收到请求才即时编译该模块并返回。于是启动速度与项目体积几乎无关——因为开工时根本没编译几个文件。 这就是「按需编译」：请求驱动、即点即得。

四、生产环境仍然要正经打包

别把 Vite 的快误解成「不需要打包」。开发环境是「现炒」给一个用户看的；生产环境要把产物发给成千上万个用户， 必须做合并、压缩、加指纹、拆包优化——此时 Vite 换用 Rollup 做全量打包（依赖预构建用的则是 esbuild）。 所以准确的总结是：Vite 的快是「开发期」的快，来自按需编译 + esbuild 预构建；生产构建它依然走成熟的打包路线。

生活类比 · 自助餐厅与现点现炒的小馆子

Webpack 像自助餐厅：规矩是「全部菜炒好才开门营业」。每天早晨（冷启动），后厨把菜单上六十几道菜 全部炒完、摆上餐台（全量打包），客人才能进店。开门之后自然爽——客人点什么，端起来就吃（改代码后热更新也快）； 可每天开门前的那一两个小时，大家只能盯着卷帘门干等。店越大（项目越大），备菜越久。

Vite 像现点现炒的小馆子：卷帘门唰地一下就拉开（dev server 秒起），后厨其实还空着。 客人点什么（浏览器 import 哪个模块），师傅才现炒那一道（按需编译），几十秒后热腾腾上桌； 没人点的菜，后厨一整天都不会碰。当然，店里办婚宴（生产环境、服务成千上万客人）时， 现炒就顶不住了——老板会请一支专业宴席班子（Rollup）来做全量备菜，该打包的一样打包。

五、配置与插件生态：一套配置打通开发与生产

Vite 把「开发服务器行为」与「生产构建行为」收进同一份 vite.config，通过插件机制扩展 （如 @vitejs/plugin-react 处理 JSX）。插件在两条流水线上都能挂钩子，所以大多数项目一份配置就能同时管住 dev 与 build——工程化体验统一，也是它流行的重要原因。

向后延伸：构建产物如何送到用户手里，是下一站的功课—— 首屏与资源加载优化 讲构建后的资源怎么拆、怎么按优先级加载； 部署基础：Nginx 与 Docker 讲打包产物如何被静态服务器与容器服务起来。

交叉链接：

  • 浏览器渲染流水线 —— 构建产物（脚本/样式）进入浏览器后如何被解析、哪些会阻塞渲染，决定打包策略怎么定。
  • 首屏与资源加载优化 —— 路由懒加载、代码分割都是「构建工具能力 + 加载策略」的组合拳。
  • 部署基础：Nginx 与 Docker —— dist 目录里的静态产物上线、SPA 路由兜底，都在部署环节收尾。

⑥ 巩固复习

一句话讲给外行听：构建工具是「翻译+打包流水线」，替浏览器看懂你写的现代代码并压缩瘦身； Webpack 像自助餐厅——全部菜炒好才开门（先全量打包再服务），Vite 像现点现炒的小馆子——开发时客人点哪道才炒哪道（按需编译），办宴席（生产上线）时再请专业帮手 Rollup。

建议复习时间：今天睡前复述 1 次「构建四职责：合并/降级/压缩/注入；Vite 开发快 = 原生 ESM 按需编译 + esbuild 预构建；生产构建用 Rollup」，1 天后、3 天后、7 天后各回来重做一遍例题（对应遗忘曲线 1/3/7 天间隔），站点会在地图页标出「该复习了」。

⑦ 面试视角

问法一：Vite 为什么快？它与 Webpack 的本质差异是什么？
  • 启动模型不同：Webpack 先递归打包整个依赖图再提供服务，冷启动耗时随项目体积增长；Vite 先起 dev server，源码模块不做打包。
  • 按需编译：Vite 利用浏览器原生 ESM，浏览器 import 哪个文件，dev server 才即时编译哪个，请求驱动、启动速度与项目大小基本无关。
  • 依赖预构建：首次启动用 esbuild 把第三方依赖转成 ESM 并合并碎文件，esbuild 是 Go 编写的原生工具，比 JS 工具链快一个量级。
  • 本质差异一句话：Webpack 是「bundler 优先」，Vite 是「native ESM + 按需编译优先」，两者不是谁取代谁，而是开发体验与构建策略的不同取舍。
  • 加分项：热更新（HMR）也更精确——模块级失效重编译，而不是整包重新构建。
问法二：「Vite 不需要打包」这个说法对吗？生产环境怎么办？
  • 不对，快只属于开发期。生产环境面向海量用户，必须合并、压缩、语法降级、加内容指纹、按路由拆包——这些只有全量打包能做到。
  • Vite 生产构建底层用 Rollup（依赖预构建用 esbuild）：产物质量、Tree Shaking、代码分割都是打包器的看家本领。
  • 为什么开发能省：开发服务的是你自己一个用户，请求驱动现编译即可；生产面对的是不可控的并发与网络环境，目标完全不同。
  • 加分项：说出「按需编译是加载策略，不是优化信仰」——工具选型要按环境目标拆开讨论，这正是面试官想听的权衡意识。
