② 深入浅出

先分清「首屏」和「白屏」

首屏是用户打开页面后第一眼能看到的区域；白屏是屏幕上什么内容都没有的阶段。白屏的常见流程是：请求 HTML → 下载并解析 CSS/JS → 构建渲染树 → 绘制。中间任何一环被卡住，用户就盯着白屏发呆。优化的总思路：让首屏必需的资源最先到位，让其余资源不挡路。

关键渲染路径：CSS 和 JS 为什么会「堵门」

浏览器渲染前需要 DOM（HTML 解析产物）和 CSSOM（CSS 解析产物）。CSS 默认阻塞渲染——样式没就绪就画页面会出现「裸奔一瞬」，所以关键 CSS 要尽早送达，甚至内联进 HTML。JS 默认既阻塞解析又阻塞执行——遇到普通 script 标签，HTML 解析要停下来等它下载并执行完，因为脚本可能修改 DOM。

defer 与 async 怎么选

  • 普通 script：下载时中断解析，下载完立即执行——适合确实要先执行的小脚本。
  • async：下载不阻塞解析，下载完立刻执行，多个脚本之间执行顺序不保证——适合独立统计、埋点类脚本。
  • defer：下载不阻塞解析，等 HTML 解析完再按文档顺序执行——适合大多数业务脚本，既不堵解析又保住依赖顺序。

代码分割与路由懒加载：别为没去的页面买单

打包工具默认把所有 JS 揉成一个大文件，用户打开首页却要连带下载「个人中心」「设置页」的代码。把包按路由拆开（动态 import / 路由懒加载），访问哪个页面才加载哪个分包，首屏 JS 体积立减。构建工具层面的对比见构建工具思想与 Vite。

preload 与 prefetch：给下载排优先级

preload 告诉浏览器「这个资源当前页马上要用，提前高优先级去拿」，适合关键字体、首屏大图；prefetch 表示「下一页可能要用，空闲时顺手拿」，适合预测性的下一步。注意别滥用：把所有资源都 preload，等于没有优先级，还会挤占带宽。

SSR / SSG：把「组装页面」提前

纯客户端渲染要「先下载 JS → 再执行 → 再长出页面」，白屏自然长。SSR（服务端渲染）在服务器把首屏 HTML 拼好直接送达，用户先看到内容，JS 再「接管」页面；SSG（静态生成）在构建期就把页面生成好，发出去的就是成品 HTML。两者本质相同：把组装工作从用户浏览器挪到服务器或构建期。

白屏排查清单（面试高频）

  • 网络层：请求发出去了吗？接口/静态资源是否 404、超时？
  • 阻塞层：是否有关键 CSS/JS 阻塞？脚本是否该加 defer/async？
  • 报错层：控制台有没有 JS 报错导致渲染中断？
  • 容器层：SPA 的挂载节点是否存在、JS 是否在 DOM 就绪前执行？
生活类比 · 餐厅的上菜策略

你饿着肚子走进餐厅（打开网页）。策略 A 的厨房很「实诚」：坚持把满汉全席二十道菜全部做完、装上同一辆大车一起端上来——你在座位上干等了半个多小时，才见到第一口吃的。这就是「全量打包」：首屏用不到的代码和图片，把真正要紧的东西堵在了路上。

策略 B 是聪明厨房：先上招牌菜和米饭（首屏关键 HTML/CSS/JS），让你一分钟内开吃（LCP 达标）；配菜让后厨慢慢做、做好了再上（非首屏资源懒加载、代码分包）；茶水在你落座前就备好在桌边（preload 提前拿马上要用的资源）。

而你上次来过这件事也有用：家里囤着常用调味料（浏览器强缓存），第二次来连「招牌菜」都不用厨房现做——这正是缓存策略在首屏优化里的价值。

⑦ 面试视角

问法一：线上页面首屏白屏，说说你的排查思路和优化清单。
  • 先定位：抓包看 HTML/关键资源请求是否发出、状态码与耗时；看控制台是否 JS 报错中断渲染。
  • 阻塞项：关键 CSS 是否过大、能否内联首屏样式；非首屏 JS 是否加 defer/async、是否可代码分割。
  • 体积项：路由懒加载拆包、图片压缩与懒加载、大依赖按需引入。
  • 优先级：对马上要用的关键资源 preload；HTML 不缓存、静态资源长缓存加指纹。
  • 架构项：瓶颈在「组装太晚」时考虑 SSR/SSG，把首屏 HTML 提前拼好。
  • 收尾：用性能指标（LCP）量化优化前后，避免「感觉变快了」。
问法二：defer 和 async 有什么区别？业务脚本为什么更常用 defer？
  • 共同点：两者下载阶段都不阻塞 HTML 解析。
  • 执行时机：async 下载完立即执行（顺序不保证）；defer 等 HTML 解析完、触发页面前按文档顺序执行。
  • 选型：业务脚本常依赖 DOM 就绪与脚本间依赖顺序，defer 两条都满足；独立的埋点、广告脚本可用 async。
  • 加分项：提到 ES Module 默认类似 defer 行为；内联 script 加 defer 无效。
