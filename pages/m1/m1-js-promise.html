② 深入浅出

1. 痛点起点：回调地狱

JS 里耗时的事（读文件、发请求）不能卡住线程，于是约定「做完后调用我传给你的函数」——这就是回调。 可一旦 A 做完才能做 B、B 做完才能做 C，代码就会一层套一层，缩进越来越深，错误处理散落各处：

getUser(id, function (user) {
  getOrders(user, function (orders) {
    getDetail(orders[0], function (detail) {
      // 缩进已经三层了，错误处理还没写……
    });
  });
});

这种「横向生长」的嵌套就是回调地狱。Promise 的使命，是把它变成「纵向生长」的链条。

2. Promise：一张「未来才兑现」的凭证，共三种状态

调用返回 Promise 的函数，你拿到的不是结果本身，而是一张凭证。凭证内部维护一个状态：

  • pending（待定）：事情还在办，结果未知；
  • fulfilled（已兑现）：办成了，携带结果值（通过 resolve(value) 进入）；
  • rejected（已拒绝）：办砸了，携带失败原因（通过 reject(reason) 进入）。

关键规则：状态只能从 pending 单向走向 fulfilled 或 rejected，且一旦敲定永远不可逆——之后再调 resolve/reject 都会被忽略。

3. then 链：值穿透与错误冒泡

then(onFulfilled, onRejected) 返回一个新的 Promise，所以能一直 .then 下去。两条核心规则：

  • 值传递：上一个 then 的回调返回什么值，下一个 then 就收到什么值；返回的若又是一个 Promise，链条会等它敲定再继续。
  • 错误冒泡：链条中任何一步被拒绝或抛错，会跳过后面所有成功的回调，直接找到最近的 catch——像异常一路上浮。这也是「在链条末尾统一 catch」能兜住全链错误的原因。

catch(fn) 本质是 then(null, fn)；finally(fn) 无论成败都执行（常用来关 loading），且不改变传递下去的值。

4. 并发四兄弟：all / allSettled / race / any

多个异步任务同时发车（并发）时，四个静态方法各有脾气：

  • Promise.all：全部成功才成功（结果按传入顺序排列）；任何一个失败立即整体失败——适合「缺一不可」的强依赖。
  • Promise.allSettled：等全部敲定，永远成功，返回每项的 { status, value | reason }——适合「有几条算几条」的报表类场景。
  • Promise.race：谁先敲定（无论成败）就用谁的结果——经典用法是给请求包一层超时。
  • Promise.any：取第一个成功的；全失败才拒绝（AggregateError）——适合多源冗余请求。

5. async/await：Promise 的语法糖

async function 的返回值会被自动包成 Promise；await 后面跟一个 Promise 时，函数在这里「暂停」，等它敲定后拿值继续——写起来像同步代码，底层仍是 then 链与微任务。

错误处理上，await 的拒绝等价于在该处抛错，用 try/catch 接住即可；并发场景推荐 await Promise.allSettled(...) 或对 Promise.all(...).catch(...) 整体兜底，避免每个 await 各包一层 try。

生活类比：奶茶店的取餐小票

老周在「茶不语」奶茶店点了一杯杨枝甘露。店员不让他干等在窗口，而是递来一张取餐小票——这就是 Promise 对象，此刻票面状态是「制作中」（pending）。

几分钟后后厨做好了，小票被盖上「已出餐」章（fulfilled），老周凭票取餐；若想追加珍珠，凭同一张票到窗口说一声就行（.then 拿上一步的值继续加工，上一步给了什么，下一步就拿到什么）。要是杨枝甘露卖完了，小票被盖「已退款」章（rejected），老周不用再排队，照票面指引走退款流程即可（.catch）。无论出餐还是退款，离开店时小票都会作废（.finally 总会执行）。

章一旦盖上就擦不掉：已出餐的票绝不可能再变成退款票（状态不可逆）。老周又帮同事点了三杯不同的奶茶，三张小票可以同时制作（并发）；「三杯都好了再一起取」是 Promise.all，「好了几杯取几杯、卖光的单独退款」是 allSettled。而 await，就是拿到小票后坐回座位等叫号——不必趴在窗口反复追问，广播（微任务队列）叫到号，你自然起身往前走。

⑦ 面试视角

问法一：setTimeout(fn, 0) 和 Promise.then(fn) 写在一起，谁先执行？为什么？
  • 先给结论：then 的回调先执行，setTimeout 哪怕延迟 0 也要靠后。
  • 推演框架：同步代码跑完 → 清空整个微任务队列（Promise.then、queueMicrotask、MutationObserver）→ 取一个宏任务（setTimeout、I/O、UI 渲染）→ 再清微任务，如此循环。
  • then 属于微任务，在当前宏任务的「收尾阶段」立即清空；setTimeout 属于宏任务，必须排到下一轮。
  • 加分项：await 表达式之后的代码等价于放进微任务；Node 与浏览器在宏任务阶段划分上有差异（可延伸到 Node 事件循环六大阶段）。
问法二：Promise.all 与 allSettled 怎么选？await 的错误处理有哪些写法？
  • all：一损俱损（快速失败），适合强依赖的组合请求，比如「用户信息 + 权限列表」缺一不可。
  • allSettled：永不拒绝、全量结算，适合看板、聚合报表这类「有几条展示几条」的场景。
  • 补充横向对比：race 取第一个敲定的结果（常用于请求超时兜底）；any 取第一个成功的（多源冗余）。
  • await 错误处理三件套：局部 try/catch、对整个 Promise 表达式 .catch、并发用 allSettled 免 try；另外提醒 async 函数的返回值会被自动包成 Promise。
