② 深入浅出

先分清两种错误：该接住的与该修的

可预期错误：网络会断、接口会超时、用户会输错——这些事情发生是「正常营业的一部分」，代码必须接住它并给用户一条出路。程序缺陷：变量名拼错、边界条件算反——这些不该发生，发现了要修；用 try/catch 把它吞掉装作没看见，只会让 bug 藏得更深、更晚爆炸。一句话原则：可预期错误做容错，程序缺陷做修复并交给监控上报。判断不准时的自问：这个错误下次还会「合情合理地」发生吗？会，就是前者。

同步错误的接法：try/catch 的能力边界

try/catch 只能接住它亲眼看着执行的同步代码。最经典的坑：把 setTimeout 的回调写进 try 块——回调真正执行时，try 块早就跑完了，回调里抛的错它根本接不住，最后飞到全局。事件回调同理。

异步错误的接法：从 .catch 到全局兜底

Promise 时代的错误会沿着链路传递，链尾挂一个 .catch 就能接住前面任何一环的失败；async/await 本质是 Promise 的语法糖，await 一个被拒绝的 Promise 会把拒绝「抛」进当前 async 函数，所以写在 async 函数里的 try/catch 反而能接住异步错误——这是它和普通函数最大的区别之一。最后一道防线是全局钩子（window.onerror 与 unhandledrejection，见监控页），但全局兜底主要用来上报，很难帮某个具体功能恢复，所以别把它当主力。

边界与兜底：让崩溃只砸坏一小块

React 的 ErrorBoundary（错误边界）给了很好的示范：在组件树的关键位置挂上「安全网」，某个子组件崩溃时只有那一块显示兜底 UI，页面其余部分照常工作——而不是一个角落的 bug 让整页白屏。请求层同样有标配三件套：超时控制（不能干等一个永远不回来的响应）；失败重试（但只重试幂等操作——查询重试无害，「下单」「扣款」这种非幂等请求盲目重试可能造成重复提交）；递增间隔（第一次等 1 秒、第二次等 2 秒，避免把刚缓过来的服务又打挂）。

降级与功能开关：坏了也要有「退而求其次」

  • 默认值 / 兜底数据：个性化推荐挂了，就展示写死的运营位——内容差点，位置不能空。
  • 缓存旧数据：新数据拿不到就先给上次的旧数据，并明确标注「更新失败，展示的是 X 日数据」——诚实比假装正常好。
  • 骨架屏：加载慢时先给结构占位，让用户知道「在努力」而不是「死了」。
  • 功能开关（Feature Flag）：给非核心功能装一个远程开关，出问题一键关闭，不必等一个发版周期。前提是设计阶段就想清楚：哪些是核心（用户来的目的），哪些是非核心（锦上添花）。

给任何页面做容错设计，先回答三个问题：这里最可能怎么坏？坏了用户会看到什么？坏的时候核心功能还剩多少？三个答案都有了，容错才算设计过，而不是出事后现补。

生活类比 · 银行停电的那十分钟

你下午去银行办业务（用户使用产品），办到一半市电突然断了（依赖的下游服务挂了）。但你发现大厅并没有陷入黑暗：柜台上方的应急灯亮着（降级：核心功能保住）；柜员不慌不忙翻开纸质登记本继续受理（备用方案：兜底数据 / 降级流程）；叫号机停了，大堂经理改用口头喊号（交互降级，体验打折但业务不断）。你出门时，保安递给你一张卡片：「今日系统检修，部分业务请改日光临」（兜底提示：明确告知好过让用户对着黑屏瞎猜）。

而你以前去过另一家小网点，同样停电，整栋楼瞬间漆黑，所有人被请出门在外干等（没有容错：一个依赖挂掉，整页白屏）。同一场事故，两种结局。更耐人寻味的是成本：那台备用发电机一年也用不上几次，平时纯属「浪费钱」（容错代码平时毫无存在感），但它的价值只在断电那一刻兑现（线上出事时才见效）——而且银行每季度都要演练一次切换（降级逻辑不演练，真出事时它自己可能就是坏的）。

④ 知识联结

前置依赖：前端监控与错误上报——全局兜底钩子抓到的错误要靠监控送出去；「发现」与「接住」是同一套体系的上下游。

向后延伸：容错逻辑（重试、降级、兜底）平时不被触发、最容易被改坏，恰恰最值得用单元测试与 E2E 测试保护——降级预案也要「定期演练」。

⑦ 面试视角

问法一：让你为一个关键页面（比如收银台）设计容错与降级方案，你会怎么做？
  • 依赖分级：先明确核心链路（浏览商品、下单、支付）与非核心（推荐、分享、客服浮窗），容错资源优先保核心。
  • 请求层三件套：超时控制；只对幂等查询自动重试并采用递增间隔，下单类非幂等操作改为明确的「提交状态确认」，防止重复扣款。
  • 降级预案：支付通道异常时切换备用通道或给出明确的稍后再试引导；推荐挂了回退静态运营位；旧数据 + 明确标注好过空白。
  • 功能开关：非核心模块接入 Feature Flag，线上异常可一键关闭，不等发版。
  • 配套监控与演练：所有降级触发都要上报告警（呼应前端监控页），预案要定期演练验证真的可用。
问法二：try/catch 能捕获哪些错误、不能捕获哪些？
  • 能捕获：try 块内同步执行的运行时错误；async 函数内 await 抛出的 Promise 拒绝（因为 await 会把拒绝转成同步样式的抛出）。
  • 不能捕获：setTimeout / 事件回调等异步回调里抛的错——回调执行时 try 块早已结束，错误会飞到全局。
  • 不能捕获：未被 .catch 接住的 Promise 拒绝（除非用 await 等待它）；这类错误归 unhandledrejection 全局钩子管。
  • 不能捕获：语法错误——代码在解析阶段就失败，根本执行不到 try 块，只能在构建期暴露。
  • 加分项：指出「全局钩子主要用来上报，难以恢复具体功能」；以及吞掉程序缺陷式错误（catch 后什么都不做）是反模式。
