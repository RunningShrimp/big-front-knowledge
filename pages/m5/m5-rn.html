② 深入浅出

一、核心思想：JS 管逻辑，原生管渲染

React Native 的分工非常干脆：你照常用 React 写组件，写 <View>、<Text>， 状态变了框架算出新界面描述——这一切发生在 JS 世界里。但真正把这行字、这个按钮画到屏幕上的， 是手机平台的原生控件：<View> 在 iOS 上变成 UIView，在 Android 上变成原生 View。 注意它不是 WebView：没有浏览器，没有 HTML，你得到的是和原生 App 一模一样的控件质感。

二、旧架构 Bridge：异步消息桥

麻烦在于 JS 和原生是两个世界：JS 跑在 JS 引擎线程，原生控件活在另一边的原生线程， 两边不共享内存、类型系统也不同。旧架构的办法是修一座「桥」： 任何跨世界交流，都要把消息序列化成 JSON 文本发过去，对面收到再反序列化、按内容办事。 这座桥还有三个脾气：异步（消息发出后不等待回执）、批量（攒一批一起送）、 单向无类型保障（发错了到对面才炸）。平时代价不明显，但遇到滚动、动画、手势这类 一秒几十次的高频通信，序列化开销加上异步延迟就会堆成瓶颈——列表掉帧、动画卡顿，根源常在这里。

三、新架构 JSI 与 Fabric：把桥换掉

新架构的思路不是把桥修宽，而是拆桥直连。核心是 JSI（JavaScript Interface）： 一层用 C++ 写的轻量接口，让 JS 可以直接持有原生对象的引用并调用它——就像不再是「写信」， 而是「拿到对方的电话直接讲」，同步调用成为可能，JSON 序列化这一步整个消失。 JSI 还与具体 JS 引擎解耦，所以 RN 能换上启动更快、内存更省的 Hermes 引擎。 渲染侧的新架构叫 Fabric：渲染器的核心逻辑下沉到 C++ 层维护一棵界面描述树（Shadow Tree）， 布局计算与协调效率更高，也让「同步测量布局」这类以前做不到的事成为可能。 配套的 TurboModules 让原生模块按需加载，Codegen 自动生成两端的胶水代码。 一句话总结：从「异步文本传话」进化为「直连对象调用」。

四、样式系统：Flexbox 子集，但没有 CSS 级联

RN 没有引入 CSS 引擎，而是自带了一套基于 Flexbox 子集的布局系统， 样式写在 StyleSheet 对象里，最后被翻译成原生控件的布局属性。 两个高频坑必须记住：RN 里 flexDirection 默认是 column（Web 的默认是 row）； flex: 1 在 RN 里是一个权重数字，不是 CSS 里 flex-grow/shrink/basis 的简写。 另外因为没有 CSS 级联，组件的最终样式由样式数组的合并顺序决定——后面的覆盖前面的， 这让样式的计算结果完全确定，也带来一个经典手写题：实现一个样式合并函数。

生活类比：隔着翻译的电话会 vs 随身同传

旧 Bridge 像隔着翻译开跨国电话会。中方（JS 世界）和美方（原生世界）都只说自己的语言， 每句话都要走三步：说给翻译听、翻译组织成另一种语言、对方听懂再执行。 电话还有延迟（异步），翻译习惯攒几句一起翻（批量），而且翻译只传「文字记录」（JSON 序列化）， 你比划的手势、桌上指的实物（内存里的对象引用）统统传不过去。 平常开会还行；一旦会议变成连珠炮式的快速问答（高频动画通信），翻译就成了全场的瓶颈， 大家都在等他，节奏全乱——这就是滚动掉帧的比喻版。

新架构 JSI 像给双方配了随身同传，而且更进一步：同传就坐在你耳边（C++ 直连层）， 你说的下一秒对方就听到（同步直调），不需要整理成文字记录（无序列化开销）。 甚至你可以直接「拨通对方的直线电话」——JS 拿到原生对象的引用直接调用。 沟通成本大降，连珠炮式对话也跟得上，这就是新架构解决旧瓶颈的方式。

④ 知识联结

前置依赖：React 核心机制 —— 组件、状态与「状态变化 → 重新描述界面」这套心智，在 RN 里原样成立，只是渲染目标从 DOM 换成了原生控件。

向后延伸：RN 解决「复用 React 与原生质感」，但它仍映射原生控件；另一个流派干脆自己画， 见 Flutter 自绘引擎；把所有方案放上天平做决策，见 跨端方案选型。

⑦ 面试视角

问法一：RN、小程序、Hybrid 在渲染方式上有什么区别？
  • Hybrid：原生壳里嵌 WebView，页面就是 H5，由浏览器内核渲染，性能受 WebView 上限约束。
  • 小程序：渲染层是 WebView，但组件由框架统一封装，逻辑层独立线程，靠 setData 跨线程通信驱动渲染。
  • RN：JS 写组件、框架算出界面描述后映射为真正的原生控件渲染，没有 WebView，控件质感与原生一致。
  • 共同点：三者都是「JS 管逻辑 + 另一个世界管渲染」，差异在「最终由谁画像素」与「跨世界通信的通道设计」。
  • 加分项：指出 Flutter 是第四条路——既不用 WebView 也不映射原生控件，自绘一切。
问法二：旧 Bridge 的性能瓶颈是什么？新架构 JSI 如何解决？
  • 旧 Bridge 三个特征：异步（无回执）、批量（攒包发送）、JSON 序列化（对象变文本再还原）。
  • 瓶颈场景：滚动、动画、手势等一秒几十次的高频通信，序列化开销叠加异步延迟，导致掉帧。
  • JSI 的解法：C++ 轻量接口层，JS 直接持有原生对象引用并调用，支持同步调用，序列化步骤消失。
  • 附带收益：JSI 与 JS 引擎解耦，使 Hermes 引擎可替换；Fabric 渲染器下沉 C++，配合 TurboModules 按需加载与 Codegen 生成胶水代码。
  • 加分项：能概括为「从异步文本传话到直连对象调用」的架构升级，并联系高频通信场景举例。
