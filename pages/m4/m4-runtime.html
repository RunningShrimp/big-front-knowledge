浏览器主线程只有一条，滚动、输入这类事件每秒能触发几十上百次。防抖、节流、计算缓存是三件最常用的「限流与省力」工具，也是手写题的常客。

② 深入浅出

问题从哪来：主线程只有一条

浏览器用一条主线程跑 JS、排排版、响应点击。scroll、input、mousemove 这类事件触发频率远高于人眼需要的更新频率——滚动一秒能触发上百次回调。如果每次回调都做重活（发请求、算布局），页面就卡。思路于是很朴素：少干、按需干、干过的别重干。

防抖（debounce）：等你彻底停手再执行

防抖的规则：事件停止触发 wait 毫秒后，才执行一次；期间每多触发一次，就重新计时。就像电梯关门：有人陆续进来，门就一直推迟关闭，直到几秒内没人再进来，门才真的关上。适合「只关心最后一次」的场景：搜索框输入联想（等用户停手再发请求）、输入实时校验、窗口 resize 结束后重算布局。

节流（throttle）：按固定频率放行

节流的规则：无论触发多频繁，每 interval 毫秒内最多执行一次，像地铁闸机每两秒只放一个人，排队再长也按固定节奏走。适合「过程本身需要持续反馈」的场景：滚动监听（吸顶、回到顶部按钮显隐）、mousemove 拖拽、按钮防连点。实现上分「首次立即执行」和「结束后补一次」两种流派，核心不变：单位时间内只放行一个。

怎么选：一句话对照

  • 只要最终结果（最后一次输入）→ 防抖；比如搜索联想，前 99 次按键的请求都是浪费。
  • 要过程中的反馈（滚动位置）→ 节流；防抖会让反馈「憋」到你停下来才出现。
  • 两者都靠闭包保存定时器状态——这正是前置知识的作用。

计算缓存（记忆化）：把算过的答案抄下来

对纯函数（同样的输入永远得到同样的输出、不产生副作用），重复计算就是浪费。记忆化的做法：用 Map 以「参数」为键缓存「结果」，再问同一道题直接念答案，以空间换时间。两个注意点：参数是对象时要先序列化再当键；缓存要设上限或过期策略，否则越攒越大。Vue/React 里的 computed、useMemo 都是这一思想的产品化。

顺带一提：虚拟滚动

一万行的列表不必渲染一万个 DOM：只渲染可视区上下再加一段缓冲的那几十行，滚动时动态替换内容、用上下留白撑出总高度。DOM 数量恒定，滚动才不掉帧——它和节流配合，是长列表的标配组合。

生活类比 · 电梯、闸机与数学家的便签

防抖是电梯关门键：你按下关门，快合上时有人跑进来，门「叮」一声重新打开、重新倒计时；陆陆续续进来十个人，就重计十次。直到 3 秒内没人再进来，门才真正关上、电梯启动。对应到搜索框：用户每敲一个字都重置计时，停手 300 毫秒后才发唯一一次请求——前面 99 次冲动全部作废，正合「最后按的人说了算」。

节流是地铁早高峰的闸机：无论站台上挤了多少人，闸机每 2 秒只放行一个，节奏雷打不动；狂按刷卡也没用，下一秒自然轮到你。对应到滚动监听：不管 scroll 一秒触发多少次，回调每 200 毫秒最多执行一次，界面以稳定频率更新，主线程不被打爆。

计算缓存是数学家的便签：有人反复问他「37 乘以 43 等于几」，他第一次老老实实算出 1591，顺手抄在便签上；之后再有人问，他瞄一眼便签直接报答案——算力没花，结果一样。唯一的风险是便签贴满一面墙（缓存膨胀），得定期撕掉几张。

⑦ 面试视角

问法一：手写防抖和节流，并说明各自的适用场景。
  • 防抖要点：闭包保存定时器 id；每次触发先 clearTimeout 旧的再重设；执行时用闭包保留的 this 和 arguments 调原函数。
  • 节流要点：时间戳版（距上次执行超过 interval 才放行）或定时器冷却版（冷却期内直接 return）；两种都保证单位时间最多一次。
  • 场景辨析：搜索联想、输入校验用防抖（只要最后一次）；滚动/resize/mousemove 监听用节流（要过程反馈）；按钮防连点常配节流。
  • 加分项：能说出进阶需求——立即执行选项、取消方法、最后一次触发的尾随执行。
问法二：除了防抖和节流，高频计算场景还有哪些优化手段？
  • 计算缓存（记忆化）：纯函数以参数为键缓存结果，适合重复输入多的场景；注意缓存上限与失效策略。
  • 虚拟滚动：长列表只渲染可视区加缓冲的几十行，DOM 数量恒定。
  • 任务切片：把长任务拆成小块放进 requestAnimationFrame 或 setTimeout 分帧执行，避免长时间霸占主线程（对应 INP 指标）。
  • Web Worker：把纯计算挪到后台线程，主线程只收结果。
  • 本质一句话：减少计算量（缓存）、摊平计算密度（防抖节流切片）、转移计算位置（Worker）。
