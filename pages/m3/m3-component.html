② 深入浅出

一、组件的边界：一个组件只对一件事负责

组件是把「一段界面 + 它的行为」打包成的独立单元。判断拆没拆对，有个朴素标准： 你能用一句不含「和」「还有」的话描述这个组件干什么吗？「用户头像」可以；「用户头像和关注按钮和粉丝列表」不行—— 那是三个组件。职责单一的组件改起来不会牵连别人、测起来不用搭一堆脚手架、换个页面还能直接搬走。 拆分粒度也别走极端：拆到「一个组件只渲染一个 span」同样是对体力的浪费——以「复用或变化的可能」为界： 会单独变化、可能被单独复用的部分，才值得独立成块。

二、props 设计：组件对外的「合同条款」

props 是父组件与子组件之间的合同。写好这份合同有三条：① 类型与默认值—— 每个 prop 声明类型、给默认值，让错误在开发期就报出来（PropTypes / TS interface 都是在把口头约定变成白纸黑字）； ② 受控 / 非受控要想清楚——受控组件的值完全由父层状态决定、组件只通过 onChange「上报修改意图」， 数据有唯一源头；非受控组件的值存在自己肚子里（DOM 或内部 state），外部只在需要时来取， 适合「只关心提交结果」的简单场景；③ 只进不出地改——子组件永远不直接改 props， 单向数据流是可预测性的底线（这条在 React 一页的「props 只读契约」里展开过）。

三、组合优于配置：别把组件写成一万个开关的遥控器

需求总在变：这张卡片要带图、那张要带按钮、第三张要带角标。菜的做法是给 Card 加 showImage、showButton、showBadge……三十个 boolean 之后， 组件内部全是 if，谁也不敢动——这叫配置爆炸。 正确姿势是把「变化的部分」作为内容交出来：children（React）或插槽（Vue）让调用方自己往里放东西， Card 只负责「卡片的外壳与布局」，放什么由组合决定。render props / 作用域插槽更进一步， 把子组件内部的数据交出来让调用方自定义渲染。一句话：用「预留位置」代替「预测需求」。

四、通用组件的演进路径与 Headless 思想

通用组件很少一次设计成功，通常是被第三个场景复用时才逼出来的： 先在业务里老实写 → 出现第二个使用处时把业务逻辑剥离（数据请求、埋点留在业务层，组件只管展示）→ 参数化样式与行为 → 沉淀成通用组件。Headless（无头）组件是这条路的尽头形态： 组件只提供行为与状态（下拉的开合、焦点管理、键盘导航），渲染完全交给调用方—— 「逻辑」与「皮」彻底分离，复用逻辑的同时不被别人的样式绑架。

生活类比 · 乐高积木与遥控机器人

好的组件体系像乐高积木：每一块形状单一——2×4 的砖就是 2×4 的砖——但正因为单一， 才能拼出城堡、赛车、宇宙飞船（无限组合）。砖与砖靠统一的凸点接口咬合（props 契约）， 拼错尺寸插不进去（类型校验当场失败），拆掉一座塔，砖还能拿去拼港口（复用）。

坏的设计像造一台包揽一切的大型遥控机器人：想加个「喷水」功能，就得在机身里再焊一套水管， 再给遥控器加个按钮；功能越加越多，遥控器上三百个键（30 个 boolean props），最后没人敢碰它—— 因为动一个键，说不定整个机器人散架。改造它的成本，早已超过用积木重新拼一台。

组合优于配置，就是「想要新造型时，去拿几块积木重新拼」，而不是「回厂给机器人焊新功能」。

前置依赖：React 核心与 Hooks 与 Vue 响应式原理 （二选一即可）——props 只读契约、单向数据流、插槽语法是本页所有原则的载体。

向后延伸：组件设计往「体系」方向走就是 前端侧系统设计 里的组件库设计题（Modal / Select 怎么设计）；往「数据」方向走是 状态管理思想—— 「哪些状态该下沉到组件、哪些该提升共享」正是拆分粒度问题的另一面。

交叉链接：

  • 状态管理思想 —— 受控组件的「唯一数据源」推到全局，就是 store；组件设计与状态归属互为镜像。
  • 单元测试与 E2E 测试 —— 职责单一、依赖清晰、纯展示的组件才好测；组件设计质量直接决定测试成本。
  • 前端侧系统设计 —— 「设计一个通用组件/组件库」是系统设计题的高频子题，本页原则就是答题素材。

⑥ 巩固复习

一句话讲给外行听：组件设计像拼乐高——每块积木只做一件事、接口统一，要新造型就重新组合几块积木（组合优于配置）， 而不是造一台三百个按钮的遥控机器人再回厂焊新功能（配置爆炸）；积木之间靠合同（props）连接，值记在谁的账本上（受控/非受控）要先说清楚。

建议复习时间：今天睡前复述 1 次「单一职责看复用与变化、props 是合同要类型+默认值+受控分明、组合优于配置、Headless 是逻辑与皮的分离」，1 天后、3 天后、7 天后各回来重做一遍例题（对应遗忘曲线 1/3/7 天间隔），站点会在地图页标出「该复习了」。

⑦ 面试视角

问法一：让你设计一个通用的 Modal 弹窗组件，你会考虑哪些点？
  • 开关受控：visible 由外部传入、关闭意图通过 onClose 上报——组件不做主，数据有唯一源头；可同时提供非受控快捷用法（defaultVisible）。
  • 组合能力：标题、内容、底部按钮全部开放为 children/插槽或命名插槽，绝不用 footerType="a|b|c" 之类的枚举预测需求。
  • 挂载与层级：渲染到 body 下的独立容器（类似 React 的 Portal / Vue 的 Teleport），避免被父级 overflow/z-index 困住；多层弹窗做栈式层级管理。
  • 交互与可访问性：Esc 关闭、点遮罩可配置、打开时焦点圈定（focus trap）与关闭后焦点归还、role="dialog" 与 aria 属性。
  • 工程细节：动画前后生命周期（关闭动画结束再卸载）、滚动锁定、按需加载不拖累首屏。
问法二：组件拆分粒度怎么把握？听说过 Headless 组件吗？
  • 粒度判据：会「单独变化」或「单独复用」的部分才值得拆；能用一句话（不含「和」）说清职责的组件是合格的组件。
  • 两个信号提醒过度拆分：拆完只为传一堆 props 穿针引线（props 钻透）；或一个组件只包着一行标记。过细与过粗都是债。
  • Headless 组件：只提供行为与状态（开合、焦点、键盘导航、选中逻辑），不提供任何视觉，渲染完全交给调用方（如 render props / hooks 形态）。
  • 价值：逻辑复用与样式解耦——同一套下拉行为可以长出公司任何一套皮肤，适合沉淀成团队基础设施。
  • 加分项：把 Headless 与「组合优于配置」串起来讲——它是对「皮肤永远猜不中」这个问题的终极回答。
