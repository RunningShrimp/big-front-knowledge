② 深入浅出

一、先看没有模块的世界有多乱

最早的网页把所有 JS 堆在 <script> 标签里，所有变量都挂在全局：页面引了 10 个脚本， 就有 10 份代码在抢同一批全局变量名。你在 utils.js 里定义了 format， 同事在 chart.js 里也定义了 format——后加载的悄悄覆盖先加载的，报错的地方却离案发现场十万八千里。 而且「谁依赖谁」全靠人肉记住标签顺序，引错顺序直接运行时报错。模块化就是给代码建立「文件即仓库」的制度： 每个模块有自己的独立作用域，想给别人用什么就显式 导出，想用别人的东西就显式 导入——依赖关系写在纸面上，一目了然。

二、CommonJS：Node 世界的「运行时现拿」

CommonJS（CJS）是 Node.js 的模块制度，核心是 require 和 module.exports。 它有两个关键性格：① 运行时才加载——代码执行到 require('./math') 这一行， 才停下来同步读取并执行 math 模块，所以 CJS 的依赖可以是任何表达式，比如 require(name) 动态拼接； ② 导出的是值的拷贝——require 拿到的是 exports 对象「此刻内容」的一份引用快照， 之后原模块内部把值改了，已经 require 到手的那份不会被牵动。

三、ESM：语言标准的「编译期看清一切」

ESM（ES Module）是 JS 语言官方的模块制度，核心是 import / export。 它的性格几乎处处相反：① 编译期静态分析——import 是声明式语法、必须写在顶层， 模块名只能是字符串字面量，所以引擎不执行任何代码就能通读全文、画出完整依赖图； ② 导出的是「活引用」（live binding）——import 进来的不是拷贝，而是指向原模块导出的只读视图， 原模块内部的值变了，import 方看到的就是新值。顺带两个常考细节：import 声明会被提升到模块顶部； ESM 顶层的 this 是 undefined（CJS 顶层 this 是 module.exports）。

四、Tree Shaking：静态结构换来的「删代码特权」

打包时最想要的超能力是「把没人用的导出直接删掉」（Tree Shaking，摇掉枯叶）。 ESM 依赖图在编译期就完全确定、导出被谁用了清清楚楚，打包器能放心删掉 sub、mul 这些无人引用的导出。 而 CJS 的 exports 可能被 exports[变量名] 动态访问、模块可能在运行时才决定导出什么， 打包器「不敢保证删了没人找」，只能整包保留——这正是「ESM 能 Tree Shaking 而 CJS 很难」的根源。

生活类比 · 食堂打菜与共享菜谱

CommonJS 像食堂打菜：你端着餐盘走到窗口（执行到 require 这一行），师傅把你指的那道菜 「此刻的样子」盛一份给你（值拷贝）。端走之后，后厨把这道菜改了配方、加了辣，你盘子里那份纹丝不动—— 拷贝就是拷贝，跟原件再无关系。而且你必须走到窗口（运行时）才知道今天有哪些菜，菜谱没法提前拿到。

ESM 像共享菜谱：开店之前（编译期），所有人先把手里的菜谱交上来通读一遍， 管理者不用炒任何一道菜，就知道「A 菜谱要用到 B 菜谱的三道菜」——依赖图开工前就画好了。 大家看的是同一份原文（活引用）：原菜谱今天把「少糖」改成「无糖」，照着做的人立刻全都知道， 不存在「有人还拿着旧抄本」的问题。也正因为菜谱开工前就齐了，管理者一眼看出「mul 这道菜从头到尾没人点」， 开席时干脆不做它——这就是 Tree Shaking。

五、循环依赖：两套制度的不同表现

A 依赖 B、B 又依赖 A，就形成了循环依赖。CJS 下先被加载的一方执行到 require 时， 另一方可能还没执行完，拿到的是不完整的导出拷贝，用时容易 undefined； ESM 靠「声明提升 + 活引用」，import 方拿到的是引用本身，等真正使用时（而非导入时）原值多半已就位， 所以很多循环在 ESM 下能自然工作。结论一致：循环依赖能用，但都该靠重构避免。

⑥ 巩固复习

⑦ 面试视角

问法一：ESM 和 CommonJS 的核心区别有哪些？为什么 ESM 能做 Tree Shaking？
  • 加载时机：CJS 的 require 是运行时同步加载，执行到才去找；ESM 的 import 是声明，编译期就完成静态分析、画出依赖图。
  • 导出语义：CJS 导出值的拷贝（require 之后的改动与已拿到的无关）；ESM 导出「活引用」，只读视图，原值变了到处同步。
  • 语法约束：ESM 的模块名必须是字符串字面量、import 必须在顶层且会被提升；CJS 的 require 可以写进 if、可以动态拼接路径。
  • 顶层 this：CJS 是 module.exports；ESM 是 undefined。
  • Tree Shaking：因为依赖与导出的引用关系在编译期完全确定、无法被运行时动态改变，打包器能安全删除未被引用的导出；CJS 的 exports 可能被动态访问，打包器不敢删。
问法二：循环依赖在 CJS 和 ESM 下分别是什么表现？
  • CJS：模块加载有缓存，循环时第二次 require 命中「还没执行完的缓存」，拿到的是不完整的导出拷贝——访问尚未赋值的导出会得到 undefined，且事后原模块补上了也与你无关（拷贝语义）。
  • ESM：靠引用绑定 + import 提升，import 方拿到的是「指向导出的引用」，只要不在模块求值阶段立刻使用对方，等真正调用时值通常已就位，多数循环能自然工作。
  • 共同结论：循环依赖是设计坏味道，靠抽公共模块、依赖倒置重构掉，而不是指望运行时兜底。
  • 加分项：说出 ESM 的三步——构造（找依赖建图）、实例化（分配导出绑定）、求值（执行代码），循环主要体现在求值顺序上。
