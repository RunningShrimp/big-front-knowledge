② 深入浅出

图片为什么值得单独一章

对一个典型网页，图片常常占总流量的一半以上，而且它直接影响两大指标：图太大拖慢 LCP，图没写尺寸引发 CLS。优化图片是性价比最高的性能手段。

格式怎么选：一张表看懂

  • JPEG：照片类老将，有损压缩、兼容性拉满，色彩丰富的照片用它不会错。
  • PNG：无损、支持透明，适合图标、截图，但照片用它体积会非常大。
  • WebP：比同等画质 JPEG 小约 25%~35%，支持透明与动图，现代浏览器兼容已很好，是当前的默认之选。
  • AVIF：压缩率比 WebP 更高，但编码慢、较老环境不支持，适合作为「渐进增强」的首选档。
  • SVG：矢量格式，图标、Logo 的不二之选，任意缩放不糊。

工程上常用 <picture> 元素：支持 AVIF 的浏览器拿 AVIF，退而求 WebP，再退 JPEG——一条声明多种格式，各取所需。

响应式图片：srcset 与 sizes

手机宽度 375px 的屏幕没必要收一张 2000px 宽的大图。用 srcset 列出同一张图的多个尺寸，用 sizes 告诉浏览器「这张图在我的布局里大概占多宽」，浏览器会结合屏幕宽度与像素密度自动挑最合适的一份下载。CDN 还能在此基础上实时裁剪、转格式（URL 带上宽高与格式参数即可）。

懒加载：loading="lazy" 与 IntersectionObserver

懒加载的核心思想：图片进入（或接近）视口之前，不设置真实 src，自然就不会发请求。两种实现：

  • loading="lazy"：原生属性，一行搞定，浏览器自动处理，绝大多数场景够用。
  • IntersectionObserver：手动实现时的标准方案。它异步观察「目标元素与视口是否交叉」，交叉时把占位 data-src 换成真实 src 并停止观察。相比老式的监听 scroll + 手算位置，它不阻塞主线程、也不用自己节流。元素与视口的交叉判断思路，本页例题会让你亲手写一遍。

rootMargin 是关键参数：把判定区域向四周扩大 N 像素，实现「提前一点开始加载」——用户滚到时图刚好就绪，而不是看着灰块等图。

两个必须配套的细节

  • 写死宽高：img 加上 width/height（或用 CSS aspect-ratio），浏览器加载前就知道占多大空间，不会把下面内容顶开——这是防 CLS 的基本功。
  • 占位体验：加载中用低分辨率缩略图、纯色块或模糊背景垫底，避免灰块闪现。
  • 首屏大图不要懒加载：它本来就该立刻加载（甚至 preload），懒加载反而让 LCP 变慢——懒加载只用于首屏之外的图。
生活类比 · 自助餐厅的出餐方式

一家自助餐厅有两千道菜（一个长页面上百张图）。策略 A 的老板很豪横：你一进门，就把两千道菜全部做好端上桌——桌子瞬间堆满（流量被打爆），你还只吃得到面前那一盘（视口外的图全白下了），账单还按两千道算（用户为看不见的图付了流量费）。

策略 B 是自助餐的正确玩法：每个餐位先摆一小份样品碟（低清占位图），你朝着某个餐台走过去（滚动接近视口），厨师看你快到了，提前两步开火、你走到正好端上热气腾腾的大份正餐（rootMargin 提前量触发真实图片加载）。你从头到尾只吃了几盘，老板也只炒了几盘——按需出餐，两全其美。

唯一的例外：门口迎宾的那盘招牌菜（首屏 hero 大图）必须一进门就端上来，让客人先「眼见为实」——所以首屏图不做懒加载。

④ 知识联结

前置依赖：首屏与资源加载优化——懒加载、preload 的优先级思想都出自那一页。

向后延伸：图片没写宽高引发的内容跳动，会在Core Web Vitals 性能指标的 CLS 一节被精确量化；线上图片加载失败率、耗时分布，交给前端监控与错误上报。

交叉链接：

  • CSS 盒模型与 Flex·Grid 布局 —— 给图片写死宽高、用 aspect-ratio 占位，本质是盒模型知识
  • Core Web Vitals 性能指标 —— 「图片引起的布局抖动」最终都会被 CLS 记账
  • 首屏与资源加载优化 —— 首屏大图 preload、非首屏懒加载，正是加载优先级的两面

⑥ 巩固复习

一句话讲给外行听：图片优化就像自助餐按需出餐——先用小样占住位置，等用户真的滚到跟前，再把全尺寸大图端上来；既省流量，又不让页面跳来跳去。

⑦ 面试视角

问法一：说说图片懒加载的实现原理。
  • 原理：初始不给真实 src（放在 data-src），因此不发请求；当图片进入视口附近，再把真实地址赋回去触发下载。
  • 原生方案：img 加 loading="lazy"，浏览器自动判断加载时机，适合绝大多数场景。
  • 手动方案：IntersectionObserver 观察目标与视口的交叉，异步触发、不阻塞主线程；rootMargin 设置提前量让用户滚到时图已就绪，加载后 unobserve。
  • 边界：首屏大图不要懒加载（应立即加载甚至 preload），否则拖慢 LCP。
  • 加分项：提到旧方案监听 scroll + getBoundingClientRect 需要自己节流，IO 方案天然规避了这个问题。
问法二：如何避免图片加载引起的布局抖动？
  • 根因：浏览器不知道图片尺寸，加载完成后才撑开空间，把下方内容顶开，产生 CLS。
  • 手段一：img 写死 width/height 属性，浏览器据此按原始宽高比预留空间。
  • 手段二：响应式场景用 CSS aspect-ratio 或「padding-top 百分比占位盒」预留空间。
  • 手段三：加载中给低清占位图/纯色背景，视觉上更平滑。
  • 加分项：关联 CLS 指标说明为什么要做——无尺寸图片是线上布局偏移的头号来源。
