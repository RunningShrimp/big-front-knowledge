② 深入浅出

一、两种渲染哲学：映射原生 vs 自己全画

跨端方案绕不开一个问题：屏幕上的像素最终由谁画？RN 的答案是「平台的原生控件」—— JS 侧算好界面描述，交给 iOS / Android 的现成控件渲染，好处是质感与原生 App 一致， 代价是外观跟随平台默认风格、还要为「两个世界的沟通」付通信成本。 Flutter 给出第四条路：既不用 WebView，也不映射原生控件——它自带一整套渲染引擎， 把界面描述变成一条条绘制指令，直接画到屏幕上。控件长什么样完全由 Flutter 自己的组件库 （Material 与 Cupertino）说了算，所以同一份代码在两个平台上像素级一致。

二、Skia：绘制指令直达 GPU

Flutter 的渲染引擎基于 Skia（一个用 C++ 写的 2D 绘图库）。 每一帧的工作流大致是：Widget 描述界面 → 经布局与绘制阶段生成一串绘制指令 （画个圆角矩形、填充这个颜色、把这段文字放这里）→ 指令交给 GPU 光栅化上屏。 因为整条渲染管线都握在自己手里，Flutter 不受平台控件版本与默认样式的牵制， 动画可以做到稳定 60 帧（高刷设备上更高）。代价也要知道：引擎要打包进 App， 安装包有一个固定增量的底价；系统级能力（推送、无障碍等）需要通过平台通道额外对接。

三、Dart 与 AOT / JIT 双模式

Flutter 选了 Dart 作为开发语言，看中的正是它的双模式： 开发期用 JIT（即时编译）——代码改动后毫秒级生效，这就是「热重载」： 改完界面立刻在模拟器上看到效果，状态还能保留，调试体验极快； 发布期用 AOT（提前编译）——Dart 直接编译成目标平台的机器码， 运行时不做解释或再编译，性能接近原生。一种语言两头讨好：开发要快，发布要猛。

四、三棵树：Widget / Element / RenderObject

Flutter 里你写的是 Widget，但真正干活的还有两层，合称三棵树：

  • Widget（配置）：不可变的界面配置描述，相当于「这张按钮要蓝色、圆角 8」。 它非常轻，可以随状态变化频繁重建，重建不等于重画。
  • Element（管家）：Widget 与渲染对象之间的中间层，持有生命周期与上下文。 新 Widget 来了，它先比一比（类型与 key 是否相同），相同就复用已有的渲染对象、 只更新配置——这是 Flutter 性能的关键护栏。
  • RenderObject（工人）：真正负责布局计算、绘制与命中测试的重量级对象， 创建成本高，所以被 Element 层保护起来，能不重建就不重建。

这套「轻配置 + 重对象 + 中间复用」的设计，和 Web 世界「虚拟 DOM + Diff 复用真实 DOM」是同一个思想： 便宜的东西随便重建，昂贵的东西靠比对来省。

生活类比：连锁奶茶店的两种开法

假设同一份图纸的连锁奶茶店要在东京和巴黎各开一家。RN 的开法： 每座城市雇当地的施工队，建材就地采购。好处是成品贴合当地工艺习惯—— 东京店的门把手、巴黎店的窗棂都是本地师傅最拿手的样式，客人一进门就觉得「很本地」； 但两地成品会有细微差异，而且图纸是总部出的，施工队看不懂的地方要打电话来回确认 （跨世界通信），沟通一多进度就慢。

Flutter 的开法：总部直接拉一整集装箱施工队和全套建材过去 （自带渲染引擎打包进 App），到哪儿都按总部同一套工艺施工—— 东京店和巴黎店的吧台弧度、灯带色温差上一度都一样，品牌视觉绝对统一。 代价是：集装箱运费不便宜（安装包有固定增量），而且当地水电要自己接 （系统推送、无障碍这类平台能力得通过专门的「接驳口」额外对接）。 两种开法没有绝对优劣，看你要「融入当地」还是「风格统一」。

⑦ 面试视角

问法一：Flutter 与 RN 在渲染机制上的核心区别是什么？
  • RN：JS 写组件，框架算出界面描述后映射为平台原生控件渲染，控件质感与原生一致，但外观跟随平台默认风格。
  • Flutter：不使用平台控件，由自带渲染引擎（基于 Skia）把 Widget 描述转成绘制指令直接画到屏幕，双端像素级一致。
  • 通信模型：RN（旧架构）依赖 JS 与原生之间的异步消息桥，高频通信有序列化瓶颈；Flutter 的界面树与渲染都在引擎内部完成，没有这条跨语言桥。
  • 语言与运行：Dart 开发期 JIT 支持热重载，发布期 AOT 编译成机器码；RN 侧则是 JS 引擎执行 JS（新架构用 Hermes + JSI）。
  • 加分项：能指出 Flutter 的代价——引擎打进安装包有固定增量，平台能力需要通过平台通道对接。
问法二：Widget 是不可变的，界面岂不是要频繁重建整棵树？Flutter 怎么保证性能？
  • Widget 只是轻量的配置描述，重建 Widget 树很廉价，重建不等于重画。
  • Element 层持有生命周期，新 Widget 到来时按「类型 + key 是否相同」决定复用还是重建。
  • 能复用时，旧的 RenderObject 被保留，只把新配置更新进去，昂贵的布局绘制不会重来。
  • RenderObject 负责布局、绘制与命中测试，创建成本高，因此被 Element 层保护。
  • 加分项：类比「虚拟 DOM Diff 复用真实 DOM」，说明轻配置随便重建、重对象按需更新的通用设计。
