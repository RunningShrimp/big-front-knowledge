② 深入浅出

一、从一行代码起步：原生 http 模块的最小服务器

Node 内置了 http 模块，十几行就能起一个服务器。它只干一件事：守着端口收请求，每来一个请求就调用一次你给的回调，把「请求对象 req」和「响应对象 res」交给你：

var http = require('http');
var server = http.createServer(function (req, res) {
  res.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
  res.end('你好，我是服务器'); // 必须以 end 收尾，否则浏览器一直等
});
server.listen(3000);

它能跑，但没法长大：想加路由得手写 if (req.url === '/users')，想读请求体得手动拼字符串，想记日志得每个分支都补一句——功能全堆在一个回调里，很快变成面条山。

二、中间件：把「请求到响应」拆成一节节车厢

框架的解法是中间件：每个中间件就是一个函数，拿到 req/res 后做一小件事（记日志、解析 body、校验登录……），然后决定交棒（调用 next() 传给下一个）还是直接响应（自己 res.end / ctx.body）。服务器按注册顺序把请求依次流过每一节车厢——这就是「框架」最核心的那点事。

三、Express：回调式单向流水线

var express = require('express');
var app = express();
app.use(express.json());                    // 中间件：把 JSON 请求体解析进 req.body
app.use(function (req, res, next) {
  console.log(req.method, req.url);         // 中间件：记一笔日志
  next();                                   // 交棒给下一个中间件
});
app.get('/users/:id', function (req, res) { // 路由：路径参数 req.params.id
  res.json({ id: req.params.id });
});
app.listen(3000);

Express 的中间件按注册顺序单向流动：进 → 加工 → next → 下一站。静态资源一行 app.use(express.static('public')) 就能托管； 错误处理靠「四个参数」的特殊中间件 function (err, req, res, next)。注意 Express 4 的坑：异步代码里的 Promise 异常不会自动进错误中间件，要自己 next(err) 交出去。

四、Koa：async/await 与洋葱模型

var Koa = require('koa');
var app = new Koa();
app.use(async function (ctx, next) {
  var start = Date.now();        // 去程：请求刚进来，先干一件事
  await next();                  // 交棒给下游，等它全部处理完再回来
  ctx.set('X-Response-Time', (Date.now() - start) + 'ms'); // 回程：下游都完成了
});
app.use(async function (ctx) {
  ctx.body = { msg: 'ok' };      // 最内层：真正干活、写响应
});
app.listen(3000);

Koa 的中间件是 async 函数，await next() 之前的代码在去程执行，之后的代码在回程执行——一层包一层再原路展开，像洋葱。 这让「响应之后还要做的事」（耗时统计、加响应头、统一错误捕获 try { await next() } catch (e) {...}）有了天然的落点，一个最外层中间件就能兜住所有内层异常。

五、常用中间件清单：路由之外的三件套

真实项目几乎必备三样：body 解析（express.json() / koa-bodyparser，把请求体变成对象）、 cors（统一给响应加 Access-Control-Allow-Origin 等头，放行跨域请求）、静态资源（express.static，托管打包产物）。 它们都是普通中间件——理解了「函数 + next()」，就能看懂框架生态里的一切插件。

生活类比 · 打包一份礼物：层层裹上，原路拆开

快递员小 K 要寄一份礼物。他先套上防压盒，顺手贴好面单（中间件 A 的去程）；再塞防撞泡沫，顺手写了张易碎便签（中间件 B 的去程）； 最后套上快递袋（中间件 C 的去程），袋子最里面才是礼物本身（业务代码，真正写响应的地方）。

收件人拆包时严格按原路反序：先拆快递袋——拆的时候可以顺手拍照留底（中间件 C 的回程）；再取出泡沫——顺手核对便签（中间件 B 的回程）；最后拆防压盒——顺手在面单上盖章记录总耗时（中间件 A 的回程）。 Koa 的 await next() 之前是「裹包装」，之后是「拆包装」；而 Express 的流水线只有「裹包装」这一个方向，next() 一去不回头， 想在「拆开时」做点事（比如统计耗时）就得另想办法。这就是两个框架最本质的区别。

⑥ 巩固复习

一句话讲给外行听：后端框架像一条加工请求的流水线——每个中间件是其中一个工位，做点小活就把请求传给下一站；Express 的传送带只进不回，Koa 的洋葱模型则允许每个工位在请求「进来时」和「出去时」各干一次活。

⑦ 面试视角

问法一：Express 和 Koa 的中间件机制有什么区别？
  • 编程模型：Express 基于回调 (req, res, next)，控制权单向流动；Koa 基于 async/await 与 (ctx, next)，next() 返回 Promise。
  • 执行形状：Express 是单向管道，next() 一去不回头；Koa 是洋葱模型，await next() 之后代码会「回程」再执行一次。
  • 错误处理：Express 4 中异步代码的 Promise 异常不会自动进错误中间件，需手动 next(err)；Koa 在最外层 try { await next() } catch 即可统一兜底。
  • 对象设计：Express 的 req/res 贴近原生并做了扩展；Koa 把两者封装成 ctx，并用 getter/setter 代理常用属性。
  • 加分项：Express 5 已支持自动捕获 Promise 异常；也能提 Express 生态更老更全、Koa 更轻更现代。
问法二：洋葱模型解决了什么问题？举一个实际用法。
  • 核心价值：把「响应发出前后」的成对逻辑收敛进同一个函数，前半段去程处理请求、后半段回程处理响应。
  • 典型用法一：耗时统计中间件——去程记 start，回程 set 响应头，逻辑聚在一起不用改业务代码。
  • 典型用法二：统一错误处理——最外层 try { await next() } catch (err)，任何内层抛错都会被原路带回顶层。
  • 推演：三个中间件 A/B/C 的输出顺序恒为 A1 → B1 → C → B2 → A2，面试常考手写 compose。
  • 加分项：对比 Express 里同样需求要靠事件监听或多个中间件配合才能实现，说明洋葱模型的表达力优势。
