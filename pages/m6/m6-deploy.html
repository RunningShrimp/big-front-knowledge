② 深入浅出

一、从「我电脑上能跑」到「公网能访问」

本地开发时，程序跑在你自己的机器上，只有你能访问。上线还差几步：找一台全天在线的服务器（云主机）；把代码放上去并让它一直活着（进程守护，崩了自动拉起）；再让用户能顺利找到并进入——最后一环通常交给一个守大门的软件：Nginx。用户的请求先到 Nginx，Nginx 决定这请求该去哪儿。

二、Nginx 三大职责：静态、转发、分流

静态资源服务：打包产物（HTML、CSS、JS、图片）就是磁盘上的文件，Nginx 收到请求直接回文件，这活它干得又快又省。反向代理：遇到接口请求（如 /api 开头），Nginx 自己不干活，转手交给内网真正的后端服务（比如跑在 3001 端口的 Node），再把结果原样带回给用户——用户全程只认识 Nginx 这一个入口。负载均衡：后端起了多个实例时，Nginx 按策略（默认轮询）把请求分摊给它们，某台挂了还能自动摘除。核心片段长这样（proxy_pass 的真实写法是「协议名 + 内网地址端口」，此处示意）：

server {
  listen 80;                        # 前台只守一个大门
  location /api/ {                  # 规则一：以 /api/ 开头的请求
    proxy_pass 后端服务地址;          # 转发给内网后端（127.0.0.1:3001 一类）
  }
  location / {
    root /usr/share/app/dist;       # 其余请求：直接给打包好的前端静态文件
    try_files $uri /index.html;     # 文件不存在时兜底回首页（SPA 刷新 404 的解药）
  }
}

三、SPA 之痛：history 路由刷新 404

单页应用用 history 路由时，用户在 /detail/42 按下刷新，请求真的发到了服务器——可磁盘上根本没有 detail/42 这个文件，Nginx 只能回 404。解法就是上面那行 try_files $uri /index.html：先按路径找文件，找不到就统一回退到 index.html，让前端路由接管这个路径，正确渲染详情页。这条配置是每个 SPA 上线的标配。

四、Docker：把「应用 + 环境」装进集装箱

代码搬上服务器的第一坑是环境：「在我电脑上是好的」——你本机的 Node 20，服务器却是 Node 14；少装一个依赖、差一个系统库，程序就起不来。Docker 的解法是把应用和它依赖的整套环境（运行时、系统库、配置）一起打包成一个镜像；镜像在服务器上跑起来就是一个容器。关系像「类与实例」：镜像是只读模板，可以基于它起任意多个容器；容器之间互相隔离，互不污染。打包说明书叫 Dockerfile：Base 用什么系统、装什么依赖、拷什么文件、启动命令是什么，一步步写清楚。「一次构建，处处运行」——开发、测试、生产跑的是同一个镜像，环境漂移问题从根上消失。

五、一条最短的部署链路

把本页知识串起来：推代码 → 构建出前端静态产物与后端服务的 Docker 镜像 → 服务器上运行容器（后端 3001、3002…）→ Nginx 守 80/443 大门：静态文件自己回，/api 转发给容器，多实例轮询分流。前端的职责边界也清晰了：产出 build 产物、配好 history 兜底、了解缓存与压缩交给 Nginx 的姿势——至此，你的程序才真正「活在网上」。

生活类比 · 写字楼前台与整装集装箱

一栋写字楼只开一个正门，前台（Nginx）守在那里。访客（HTTP 请求）递上写着房间号的条子（URL 路径），前台看前缀指路：「/api 开头的，上 3 楼」；3 楼有 A、B 两个工位（后端多实例），前台按「一个轮一个」的顺序把访客分过去，谁休假了就跳过谁（负载均衡与摘除）；「/admin 开头的，去 5 楼」（另一组服务）；其余访客请到一楼资料架自取现成文件（静态资源，Nginx 直接回）。

有位访客的条子写着「展厅 42 号」（history 路由的 /detail/42），可资料架上并没有这个名字的文件——前台没有直接把他轰走（404），而是递给他一张公司总导览图（index.html）：「按图里的内部指引走，你自然能找到 42 号展厅」（try_files 兜底，前端路由接管）。这正是 SPA 刷新不白屏的秘密。

再看楼里的公司怎么入驻。老办法是租间毛坯房现场装修：刷墙、拉电线、装空调（服务器装环境），装到一半发现「我这版图纸在我原来的办公室是好的」——环境对不上，白干。新办法是整装集装箱（Docker）：工厂里把办公室连家具、电器、说明书打包成一个箱子（镜像），吊车把箱子放到哪栋楼（任何装了 Docker 的服务器），落地通电立刻开业（容器运行）；同一张图纸可以复制出多个箱子开分店（一个镜像跑多个容器），箱子与箱子之间互相隔离，一家重新装修（升级依赖）也弄不脏邻居。

交叉链接：

  • 前端路由原理 —— history 模式刷新 404 的前端侧成因，与 Nginx try_files 兜底是一对「前后端约定」
  • 浏览器缓存策略 —— Nginx 给静态资源补 Cache-Control 头，长缓存 + 指纹文件名的策略在部署层落地
  • HTTP 服务：Express 与 Koa —— 反向代理背后的目标正是这些 Node 服务；也解释了为什么生产环境常让 Node 只管接口、静态交给 Nginx

⑦ 面试视角

问法一：正向代理和反向代理的区别是什么？
  • 看代理「站在哪一侧」：正向代理站在客户端一侧，替客户端出门办事，服务器看到的来源是代理而非真实用户（如公司统一出口、内网穿透）。
  • 反向代理站在服务端一侧，统一收客再分发，客户端不知道也不需要知道背后哪台机器在干活（如 Nginx 转发、云网关）。
  • 隐藏的对象不同：正向代理对服务器隐藏「真实客户端」，反向代理对客户端隐藏「真实服务端」。
  • 反向代理的附带价值：负载均衡、HTTPS 终结（大门统一配证书）、限流与安全隔离、缓存。
  • 加分项：一句话总结——方向相反的两次「代劳」，区别在替谁隐藏谁。
问法二：Docker 解决了什么问题？镜像和容器是什么关系？
  • 核心痛点：环境不一致——「在我电脑上是好的」。应用依赖运行时版本、系统库、配置，手工装环境必然漂移。
  • Docker 把应用与依赖环境打包成镜像，开发、测试、生产跑同一个镜像，实现「一次构建，处处运行」。
  • 镜像与容器是「类与实例」：镜像是只读模板（分层存储、可复用可版本化），容器是镜像的运行实例，写层独立、彼此隔离。
  • 与虚拟机的区别：容器共享宿主机内核、只隔离用户态，秒级启动、占用极小；虚拟机则连内核一起虚拟，重但隔离更彻底。
  • 加分项：Dockerfile 是镜像的「装修图纸」，构建即按步生成镜像层；配合 Nginx 统一入口就是最小可用部署链路。
