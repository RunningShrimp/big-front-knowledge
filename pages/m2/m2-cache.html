② 深入浅出

一、为什么需要缓存

打开一个网页，浏览器要下载几十个文件：HTML、CSS、JS、图片……如果每次访问都把所有文件从远端服务器重新拉一遍，用户要等、服务器要扛、运营商流量也白烧。 于是浏览器与服务器约定了一套「缓存策略」：把某些文件存一份在本地，下次需要时先看本地这份还能不能用，能用就一分流量都不花。 缓存判定的主角全在响应头里，核心就两层：强缓存与协商缓存。

二、强缓存：保质期内，自己说了算

服务器首次返回资源时，可以附带「保质期」声明。浏览器把资源连同保质期一起存下来，保质期内再次需要它时直接用本地副本，连请求都不发——这就是强缓存（控制台里显示为 memory cache / disk cache）。 声明保质期有两种头：

Expires：写一个绝对时间（如某个具体日期），「到这天为止都有效」。缺点是它依赖用户电脑的时钟——本机时间被改错，判断就全乱了。 Cache-Control：写相对时间与策略指令，如 max-age=600（自响应时刻起 600 秒内有效），不依赖本地时钟是否准确，因此优先级高于 Expires（两者同时出现时，Cache-Control 说了算）。 常用指令还有：no-cache（可以存，但每次使用前必须先问服务器验证）、no-store（彻底不存）、private（只允许浏览器存，代理等中间节点不能存）、public（沿途节点都可以存）。

三、协商缓存：保质期过了，问一问再决定

保质期一过，本地副本不能直接用了，但直接扔掉重新下载也可能浪费——万一服务器上根本没变呢？于是浏览器发起一次「协商」请求，带上本地副本的「身份证」让服务器比对。身份证有两套：

Last-Modified / If-Modified-Since：服务器上次告诉浏览器「这文件最后修改于某时刻」，浏览器下次带着这个时间问「从那之后改过吗？」。 ETag / If-None-Match：服务器给内容算一个唯一指纹（如内容哈希），浏览器下次带着指纹问「指纹还是这个吗？」。 两套同时存在时，ETag 优先——因为修改时间只能精确到秒（1 秒内改多次它看不出）、文件内容没变但时间变了它也会误判，而指纹直接对内容负责，更准。

四、304：没变就别重传

服务器比对后发现内容没变，就返回 304 Not Modified——这是一个只有头部、没有正文的应答，意思是「我确认没变，你继续用本地那份吧」。 一张几 MB 的图片，304 只花几百字节的头部开销，省下的是整个正文；如果变了，服务器正常返回 200 OK 加上完整新内容（以及新的指纹和保质期），浏览器用新内容替换旧缓存。

五、完整判定流程与实战策略

把两层串起来就是面试必背的判定链：发起请求 → 查本地有无缓存副本 → 无：直接向服务器要（200）→ 有：先看强缓存是否命中（Cache-Control/Expires 仍在有效期）→ 命中：直接用本地，不发请求 → 未命中：发起协商缓存请求（带 If-None-Match / If-Modified-Since）→ 服务器比对 → 没变回 304（继续用本地），变了回 200 + 新内容（更新缓存）。

实战中的经典搭配是「HTML 不缓存 + 静态资源长缓存加指纹」：HTML 是入口，必须每次协商验证（如 Cache-Control: no-cache），保证用户总能拿到最新的引用关系； 而打包产物 JS/CSS 的文件名里带上内容指纹（如 app.a3f9c2.js），内容一变指纹就变、URL 就变，于是可以放心设置超长强缓存（如 max-age=31536000）——既快又不担心更新丢失。

生活类比 · 小美家的冰箱与楼下生鲜超市

小美家有台冰箱（浏览器缓存），楼下有家生鲜超市（服务器）。周日她去超市囤了一盒鲜奶，小票上印着「保存期 3 天」（Cache-Control: max-age）。 周一想喝：她先开冰箱——奶还在保质期内，直接喝，超市的门都没进（命中强缓存，浏览器根本不发请求）。 周四想喝：保质期过了。她没有直接扔，而是打电话问超市：「我冰箱里这盒是 A 批次的，换货了吗？」（携带 If-None-Match: A 发起协商缓存）。 店员看一眼货架：「没换。」小美说声「行」就挂了电话——牛奶不用重新送一趟（304 Not Modified，响应没有正文），她继续喝冰箱里那盒。 如果店员说「换到 B 批次了」，超市才把新牛奶送上门（200 OK 带完整新内容和新批次号），小美把旧奶下架、新奶放进冰箱（更新缓存）。 早期超市流行在小票直接印「最佳日期：某月某日」（Expires 绝对时间），可小美家挂钟不准（用户电脑时间可能被改错），经常闹出「明明没过期却当作过期」的乌龙——所以后来都改用「从囤货起算 N 天」的相对记法（Cache-Control: max-age），并且以它为准。

④ 知识联结

前置依赖：HTTP/1.1、HTTP/2 与 HTTP/3——缓存判定读的全是响应头，先懂报文结构再看策略。

向后延伸：缓存是首屏性能的第一杠杆，配合关键渲染路径一起优化，见首屏与资源加载优化； Cookie 作为「另一种本地存储」的容量、发送行为与缓存头思想一脉相承，见浏览器存储：Cookie、Web Storage 与 IndexedDB。

交叉链接：

  • Core Web Vitals 性能指标 —— 强缓存命中率直接影响 LCP：主内容能不能秒出，很大程度看资源是否免下载
  • 部署基础：Nginx 与 Docker —— 缓存头最终由服务端（如 Nginx）配置下发，部署时才能真正落地「HTML 不缓存 + 指纹资源长缓存」
  • HTTPS 与 TLS 握手 —— 强缓存命中时连请求都不发，TLS 建连开销也随之省掉；缓存与安全传输是配合关系

⑦ 面试视角

问法一：说说强缓存与协商缓存的完整判定流程？Expires 和 Cache-Control 谁优先？
  • 先查本地有无缓存副本：没有 → 直接请求服务器，返回 200 与新内容。
  • 有副本 → 先判强缓存：Cache-Control 的 max-age 未过期（或 Expires 未到期）→ 命中，直接用本地副本，请求不发出（对应 memory/disk cache）。
  • 强缓存失效 → 发起协商请求，携带 If-None-Match（ETag）与 If-Modified-Since（Last-Modified）→ 服务器比对。
  • 未变：返回 304 Not Modified（无正文），浏览器继续用本地副本并刷新保质期；已变：返回 200 + 新内容 + 新的 ETag/保质期，更新缓存。
  • 优先级：Cache-Control > Expires（相对时间不依赖本地时钟）；ETag > Last-Modified（指纹对内容负责，修改时间只有秒级精度且有「内容没变时间变了」的误判）。
  • 加分项：提到 no-cache（可存但需协商验证）与 no-store（彻底不存）的区别，说明对指令语义有准确理解。
问法二：实际项目里你会怎么设计缓存策略？为什么 HTML 和 JS/CSS 要区别对待？
  • HTML 作为入口不设长强缓存：用 no-cache（每次协商验证），保证用户拿到的是最新的资源引用关系，避免「更新后用户还是旧页面」。
  • JS/CSS/图片等静态资源：构建时把内容指纹写进文件名（如 app.a3f9c2.js），内容一变文件名即变、URL 即变。
  • 因为 URL 变了就必然绕开旧缓存，这类资源可以放心设超长强缓存（如 max-age 一年），命中率极高、加载飞快。
  • 收益：入口保证「新」，静态资源保证「快」；两者配合才能既不丢更新又不浪费流量。
  • 加分项：提到服务端（Nginx）下发缓存头、HTML 与静态资源分开路由配置；或提到 CDN 缓存与浏览器缓存的分层。
