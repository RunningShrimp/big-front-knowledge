② 深入浅出

一、HTTP 是金鱼记忆：无状态的困境

HTTP 协议天生无状态：每个请求都是独立的，服务器处理完就忘。你刚刚登录成功，下一个请求过来，服务器照样一脸茫然——「你谁啊？」。但真实业务离不开「记住用户」：登录后要看到自己的订单、会员积分、购物车。所以需要一套机制，让服务器在「每次都是新请求」的协议之上，认出「这一串请求都来自同一个人」。这套机制由两件东西配合完成：浏览器侧的 Cookie 和服务侧的 Session。

二、Cookie：浏览器自动携带的小纸条

Cookie 是服务器「寄存」在浏览器里的小段文本，随后浏览器每次请求都自动带上它——这正是「记住」的物理载体。服务器通过响应头 Set-Cookie 下发，浏览器按属性管理它：

  • Expires / Max-Age：过期时间。不设则是「会话 Cookie」，关浏览器就没。
  • Domain / Path：作用域。决定带去哪些路径、哪些子域。
  • Secure：只在 HTTPS 连接上发送，防明文裸奔。
  • HttpOnly：禁止 JS 通过 document.cookie 读取，XSS 脚本偷不走。
  • SameSite：限制跨站请求携带，是缓解 CSRF 攻击的第一道闸。

注意 Cookie 本身只是「顺路的口袋」：容量小（约 4KB）、每个请求都带着（放多了浪费流量），所以别把大数据塞进去。

三、Session：敏感信息锁在服务端，Cookie 只放钥匙

如果直接把「用户名、会员等级、余额」都存进 Cookie，等于把家当印在名片上随身带——能被看见、能被篡改、装不下也浪费。正统做法是 Session：登录成功时，服务端在自己这边开一个「柜子」，把用户数据存进去，柜子上有个随机编号（SessionID）；然后只把这个编号通过 Cookie 发给浏览器。之后的每个请求，浏览器带着编号，服务端查表：sessionStore[sid] 一查，就认出了你。数据在服务端，Cookie 里只有一把「钥匙」——这是 Cookie 与 Session 的分工核心。

四、会话的一生：建立、续期、登出

登录 = 建柜子发钥匙；之后的每次请求可以顺手动一动柜子的「最后活跃时间」实现滑动续期（越活跃越不掉线）；超过时效没动静，柜子被清掉，钥匙作废，下次要重新登录；登出则由服务端主动销毁柜子并让浏览器清掉 Cookie——所以「登出」从来不只是前端删一个变量，必须让服务端那本登记簿上的记录消失才算数。

五、分布式难题：登记簿只有一本怎么办

单机时代柜子就在进程内存里；一旦服务扩成多台机器，问题来了：你的柜子开在 1 号机，下一个请求被负载均衡分到了 2 号机——它翻遍自己的登记簿也找不到你。三种主流解法：粘性会话（让同一用户固定打到同一台机，但机器挂了会话全丢）、集中存储（把 Session 搬进 Redis，所有机器查同一本登记簿，最常用）、无状态化（干脆不存了，把信息签名后塞给客户端自带——就是下一页的 JWT）。

生活类比 · 健身房的手环系统

第一次去健身房，前台让你填表、拍照、登记会员信息——这些资料全部存进健身房的会员系统（服务端 Session 存储），你只拿到一枚手环，上面只有一个编号，没有你的任何隐私（Cookie 只存 SessionID）。以后每次进店，闸机「嘀」一声刷手环，前台凭编号查系统：「3 号会员，小明，年卡有效」——你就被认出来了。

这套系统的好处立刻显现：手环丢了不用慌，资料在店里而不在环上，别人捡到也只看到一串号码；但你若把环借给别人，他刷你的号就能冒充你进店（SessionID 被盗用）——所以健身房规定手环不得转借（HttpOnly 防脚本偷环）、长期不来要重新核验身份（会话过期）。最后是连锁店场景：小明今天去 A 店、明天去 B 店，B 店也认得他——因为所有分店共用同一套会员系统（Redis 集中存储的分布式 Session）。如果每家分店各记各的账本（各机内存自存 Session），换个店就没人认识你了，这正是分布式部署要解决的第一个鉴权难题。

④ 知识联结

前置依赖：浏览器存储——Cookie 的属性、容量与自动携带行为是本页一切机制的物理基础。

向后延伸：Session 有状态、扩容要共享存储，于是有了「把信息签名后让客户端自带」的无状态方案，见JWT 与 OAuth 2.0。

交叉链接：

  • Web 安全：XSS、CSRF 与 CSP —— HttpOnly 防 XSS 偷 Cookie、SameSite 缓解 CSRF，攻防两端都要回到 Cookie 属性来理解
  • 跨域与 CORS —— 跨域请求想带上 Cookie，前端 withCredentials 与服务端 Allow-Credentials 必须双向配合
  • RESTful API 设计 —— 「未登录 401、无权限 403」的语义，正是会话校验中间件在接口层的落点

⑥ 巩固复习

⑦ 面试视角

问法一：Cookie 和 Session 有什么区别？它们如何配合？
  • 存储位置：Cookie 数据在浏览器、随请求自动携带；Session 数据在服务端（内存或 Redis 等存储）。
  • 安全边界：Cookie 用户可见可改（别放敏感信息与权限明文）；Session 只有服务端能读写，客户端只拿到一把 SessionID「钥匙」。
  • 容量与寿命：Cookie 约 4KB、受域名与路径作用域约束；Session 容量取决于服务端，过期策略由服务端控制。
  • 配合流程：登录成功 → 服务端建 Session 存用户态 → Set-Cookie 下发 SessionID（建议 HttpOnly + Secure）→ 后续请求浏览器自动带上 → 服务端按 ID 查 Session 认人。
  • 加分项：SessionID 应是高熵随机串防猜测；登出必须销毁服务端 Session 并清 Cookie，仅前端删变量不算登出。
问法二：服务扩到多台机器后，Session 会遇到什么问题？怎么解决？
  • 问题本质：Session 存在单机内存里，负载均衡把同一用户的请求分到另一台机器时查不到会话，登录态「时有时无」。
  • 方案一 粘性会话：让同一用户固定路由到同一台机器；实现简单，但机器宕机该机会话全丢、负载不均。
  • 方案二 集中存储：Session 统一放 Redis 等外部存储，所有机器读同一份，这是生产最常用方案；要考虑 Redis 本身的高可用。
  • 方案三 无状态化：不存会话，把用户信息签名后交给客户端自带（JWT 思路），扩容最省心，但换来「注销难」等新问题。
  • 加分项：能顺着说「无状态化正是下一站 JWT 的动机」，体现知识链路。
