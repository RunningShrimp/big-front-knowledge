② 深入浅出

一、先回忆：普通网页是「单世界」的

在浏览器里，HTML、CSS、JS 活在同一个世界：JS 拿得到 document，能随时增删改查页面上的任何节点， 改完浏览器立刻重排重绘。这个「随手可改」很方便，但也意味着——页面长什么样，可以被 JS 随心所欲地控制。

二、小程序拆成了两个世界

小程序把这件事拆成了两半：渲染层负责把界面画出来（每个页面一个 WebView）； 逻辑层负责跑你写的 JS（所有页面共用一个独立的 JS 引擎线程）。 关键在于：逻辑层里没有 window、没有 document，拿不到任何 DOM 节点。 你想让界面变，只有一个正规通道——调用 setData，把「什么数据变了」告诉渲染层，由它去更新视图。

三、为什么要这样隔离：安全与管控的取舍

既然拿不到 DOM，JS 就没法跳出框架乱改页面，也无法嗅探、篡改平台不希望它碰的东西。 平台由此获得了统一管控能力：所有界面变更都走规定通道，体验可控、审核可查、安全可控。 代价是：每次界面更新都要跨线程通信，比浏览器里直接改 DOM 多了一道「寄快递」的流程。 这是一道典型的工程取舍——用一点通信开销，换整个生态的管控与稳定。

四、两个世界怎么说话：setData 与 Native 中转

渲染层和逻辑层互相看不见对方，中间站着的裁判是原生层（Native）。 流程是这样转的：用户在渲染层点了按钮 → 事件被打包，经 Native 层送到逻辑层 → 逻辑层执行你的回调、调用 setData → 变更数据经 Native 层序列化后送回渲染层 → 渲染层应用数据、更新视图。 注意两条结论：通信是异步的（发出 setData 后渲染层不会立刻变），以及能传过去的只有可序列化的数据（函数、DOM 节点这类东西根本过不去）。

五、频繁 setData 为什么是性能大坑

因为每一次 setData 都是一次跨线程通信：打包、序列化、过桥、反序列化，一步都省不了。 在一个滚动列表里每帧调用一次 setData，等于每帧都寄一次「全程快递」，快递费（通信与序列化开销）会把帧预算吃光，于是掉帧、卡顿。 对应的优化手段也就顺理成章：合并多次 setData 为一次、只传变化的数据（按路径更新）、对高频操作节流、 不要在页面已进入后台时还继续 setData、别把与渲染无关的大对象塞进 data。

六、WXML / WXSS：长得像 HTML / CSS，但不是一回事

渲染层写的不是 <div>，而是 <view>、<text>、<image> 这些框架统一封装的组件； 样式文件是 WXSS，提供了 rpx 这种按屏幕宽度自适应的单位，选择器支持范围也比 CSS 更窄。 模板里的 wx:if、wx:for 更像 Vue 的指令风格，而不是标准 HTML。 可以把它们理解为：专门为「组件化 + 数据驱动」重新设计的一套界面描述语言，只是借用了 HTML/CSS 的皮。

生活类比：一家只有传菜口的火锅店

想象一家规矩很特别的火锅店。前厅（渲染层）只负责一件事：把端出来的菜摆好、给客人看， 并收集客人点的单；后厨（逻辑层）闷头炒菜，但后厨没有窗户，看不到客人，也看不到前厅的桌面。 前厅和后厨之间只有一条窄窄的传菜口（Native 中转）。 客人点单，单子从传菜口递进后厨；后厨做好一道菜，也得从传菜口递出来，前厅才能摆上桌—— 菜在传菜口排队的这段时间，客人桌上就是空的，这就是「异步」。

店规也很严：后厨递出来的只能是包装好的食材包（可序列化的数据），活鱼活虾带锅带灶（函数、DOM 节点）一律不许过口。 经理（平台）还在传菜口派了安检员，每样出去的东西都要过检——这正是平台能统一管控页面、保障体验的原因。 最后是成本问题：客人连点十次「加菜」，服务员要是十次单独跑传菜口，口子就被堵死了； 聪明的做法是把十份改动打包成一箱，一次递过去。单传得太勤，菜都凉了。

前置依赖：建议先学「虚拟 DOM 与 Diff」（渲染层拿到数据后如何最小化更新视图） 与「事件循环」（逻辑层 JS 的事件驱动执行模型），本页的通信模型建立在这两者之上。

向后延伸：理解双线程后，下一步是看它与普通 Web 的具体差异（小程序与 Web 的差异）， 以及另一类「原生壳 + WebView」方案里桥通信的样子（Hybrid 开发与 JSBridge）。

交叉链接：

  • 事件循环 —— 逻辑层里 tap 回调、定时器、Promise 全靠事件循环调度。
  • 虚拟 DOM 与 Diff —— 「先算差异、再最小更新」与 setData 优化是同一个思想。
  • Hybrid 开发与 JSBridge —— 同样要跨 JS 与原生通信，对比两种桥的设计。
  • 渲染流水线与重排重绘 —— 浏览器里改 DOM 的成本，帮助理解通信成本之外的第二重开销。

⑦ 面试视角

问法一：小程序为什么采用双线程架构？
  • 管控与安全：逻辑层拿不到 DOM/BOM，界面变更只能走 setData 正规通道，平台可统一管控体验、支撑审核体系。
  • 渲染与逻辑解耦：渲染层每个页面一个 WebView，逻辑层单线程跑全部 JS，页面间互不干扰、方便回收。
  • 避免互相阻塞：Web 里长任务 JS 与渲染抢同一线程会卡界面；双线程下逻辑计算不直接阻塞渲染线程。
  • 代价要答出来：跨线程通信是异步且有序列化成本，因此催生了 setData 系列性能优化话题。
问法二：setData 有哪些优化手段？为什么？
  • 合并调用：多次 setData 合并为一次，因为每次调用都是一次完整的跨线程序列化通信。
  • 只传变化数据：按路径更新（如更新列表某一项）而不是整棵 data 全量下发，减少序列化体积。
  • 高频操作节流：滚动、输入等高频事件里避免每帧 setData，通信开销会直接吃掉帧预算导致掉帧。
  • 数据瘦身：与渲染无关的纯计算数据不放 data；页面进入后台后停止 setData。
  • 加分项：能指出「思想与虚拟 DOM Diff 同源——先算最小变更，再最小传输」。
