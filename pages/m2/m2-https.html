② 深入浅出

一、HTTP 明文的烦恼，HTTPS 垫在哪一层

HTTP 报文像一张明信片：写的是「帮我把余额转到某账户」，从你家到收件人，沿途每一个经手人（同一 WiFi 里的陌生人、路由器、运营商网关）都能看内容、改内容——偷窥密码、往页面里插广告、把你的跳转劫持到假网站，都是这么发生的。 HTTPS 并不是一个全新的协议，它就是「HTTP + TLS」：在 HTTP 与 TCP 之间垫了一层 TLS（安全传输层），发出前先把报文装进加密信封，路上只见密文，到对方手里再拆封。这就顺手拿到了三样东西：机密性（看不懂）、完整性（改了会被发现）、身份认证（确认对方真的是那个网站）。

二、两把锁：对称加密与非对称加密的组合拳

对称加密：加密和解密用同一把钥匙。优点是快，适合加密海量数据；缺点是致命的——钥匙怎么安全地送到对方手里？在明文信道上直接寄钥匙，等于把密码写在明信片上寄出去。

非对称加密：一把钥匙成对出现——公钥和私钥。用公钥锁上的箱子，只有配对的私钥能打开；公钥可以随便发，私钥永远不出门。这解决了「密钥配送」难题，但它很慢，不适合加密大量数据。

于是 TLS 取长补短：握手阶段用非对称加密把「会话密钥」安全地送到对方手里（并验证签名），之后的数据传输全部改用这把商量好的对称密钥——又安全又快，这就是混合加密。

三、先验明正身：数字证书与 CA 信任链

非对称加密还剩一个漏洞：浏览器收到一把「公钥」，凭什么相信它真的属于目标网站，而不是半路有人调包的？这就轮到数字证书出场：由浏览器和操作系统都信任的权威机构（CA，证书颁发机构，好比公证处）核验网站身份后，把「域名、持有者、公钥、有效期」打包成证书，并用 CA 自己的私钥对内容签名——签名相当于火漆印，谁都能用 CA 公开的公钥验证，但没有 CA 私钥就仿造不出来。

浏览器验证证书时会依次核对：① 用内置的 CA 公钥验签（签名对不上，直接拒绝连接）；② 沿证书链逐级核对（站点证书由中间 CA 签发、中间 CA 又由根 CA 背书，根证书预装在系统里，这是信任的锚点）；③ 域名匹配（证书里的域名必须和你访问的一致）；④ 有效期与吊销状态。任何一环失败，浏览器都会拦下连接并提示风险。

四、TLS 握手流程拆解（对照下面的动画走一遍）

以经典的 TLS 1.2 为例，握手大致是这五步：① ClientHello：浏览器发出「我支持的加密套件列表 + 一个客户端随机数」； ② ServerHello：服务器从中选定一套，回一个服务端随机数； ③ Certificate：服务器出示数字证书（含公钥）； ④ 密钥交换：浏览器验证证书后，生成一段「预主密钥」，用服务器公钥加密发过去——路上是密文，只有握着私钥的服务器能解开； ⑤ 会话密钥：双方用「客户端随机数 + 服务端随机数 + 预主密钥」各自算出同一把会话密钥，互发 Finished 校验后，之后的通信全部用它做对称加密。两个随机数让每次连接的密钥都不同，防止旧密钥被套用（防重放）。

TLS 1.3 把握手从约两次往返（2-RTT）压到一次往返（1-RTT）：密钥交换直接并入两边的 Hello 报文，配合会话恢复甚至能做到 0-RTT；同时砍掉了 RSA 密钥交换等一批不再安全的旧算法，只保留具备前向安全（私钥日后泄露也解不开过去的流量）的方案。

五、中间人为什么防住了

假设攻击者半路劫持流量、把自己的公钥冒充成服务器的公钥发给你：他出示的假证书没有可信 CA 的签名，浏览器用内置公钥一验就对不上，当场拒绝连接；就算他只截获加密的预主密钥，没有服务器私钥也解不开。签名与证书校验，堵住了「调包」这条路。 但要清楚边界：HTTPS 只保「路上安全」——钓鱼网站同样能申请到合法证书（小锁不等于官方可信），XSS、CSRF 这类应用层攻击它也管不着，那是后续 Web 安全页的主题。

生活类比 · 小周给异地表哥寄房产证

小周要把一份房产证原件寄给异地的表哥，路上快递员、中转站谁都可能经手，怎么办？他设计了这么一套流程： 第一步，验明正身。小周并不直接信「对方自称是表哥」，而是找双方都信任的长辈（CA 公证处）作保：长辈当面核过表哥的身份证后，在他的挂锁照片旁签上名、盖上火漆印，做成一张「担保卡」（数字证书）。火漆印人人能辨认真假（用 CA 公钥验签），但只有长辈有那枚章（CA 私钥），仿不出来。 第二步，公开的锁先寄来。表哥把一只「扣得上却打不开的挂锁」（公钥）连同担保卡寄给小周——这锁谁拿到都能扣上，但开锁的钥匙（私钥）全世界只有表哥有一把，从不外借。 第三步，小周核对火漆印：签名对得上长辈的笔迹、担保卡上写的确是表哥的名字、卡片没过保质期——都对，才敢用这把锁。 第四步，寄钥匙。小周把自家保险箱的新钥匙放进小盒，用表哥的挂锁咔哒扣上寄回（用公钥加密预主密钥）。半路就算有人截下包裹，既打不开挂锁，也仿不出火漆印；只有握着唯一钥匙的表哥能取出里面那把新钥匙。 第五步，之后寄东西全换新钥匙：两人用这把商量好的钥匙上锁（对称加密），又快又稳，而且每寄一轮就换一把新钥匙（随机数参与），旧钥匙丢了也波及不了别轮。 如果中途有人把自己配的锁冒充表哥的锁寄来（中间人攻击），担保卡上的火漆印根本对不上——小周一眼识破，直接拒绝收件（浏览器拦截连接）。

④ 知识联结

前置依赖：HTTP/1.1、HTTP/2 与 HTTP/3——HTTPS 就是 HTTP 套上 TLS 信封，先懂明文报文长什么样，才知道加密加密的是什么。

向后延伸：HTTPS 只保传输安全，XSS、CSRF 这类应用层攻击要靠下一课，见Web 安全：XSS、CSRF 与 CSP； 跨域请求同样跑在安全与同源规则的夹缝里，见跨域与 CORS。

交叉链接：

  • Cookie、Session 与鉴权基础 —— Cookie 的 Secure、HttpOnly 属性配合 HTTPS 才能守住登录态；加密信道是会话安全的底座
  • 首屏与资源加载优化 —— TLS 建连多出的往返与运算开销直接影响首屏速度，会话恢复、HTTP/2/3 复用连接都是为省掉这段成本
  • 浏览器缓存策略 —— 强缓存命中时连请求都不发，TLS 握手开销也随之免掉；缓存与安全传输是一对配合关系

⑥ 巩固复习

一句话讲给外行听：HTTPS 就是寄贵重物品前先互相验明身份（公证处盖章的证书），再用对方公开的锁（公钥）商量出一把只有你俩知道的新钥匙（会话密钥），之后所有信件都用这把钥匙上锁——路上的人既看不懂也改不了。

建议复习时间：今天睡前默写一遍「ClientHello → ServerHello → 证书与验签 → 公钥加密预主密钥 → 算出会话密钥 → 对称加密通信」握手链；1 天后、3 天后、7 天后各回来重做一遍例题（对应遗忘曲线 1/3/7 天间隔），站点会在地图页标出「该复习了」。

⑦ 面试视角

问法一：HTTPS 建连为什么比 HTTP 慢？TLS 1.3 快在哪？
  • HTTP 建连只需 TCP 三次握手（约 1-RTT）；HTTPS 在此之上还要做 TLS 握手。
  • TLS 1.2 握手约需额外 2-RTT：协商算法、服务器发证书、浏览器验证证书并交换密钥材料，之后才能发第一个 HTTP 请求。
  • 除了往返延迟，还有计算开销：证书链验证、签名验签、密钥运算都要耗 CPU。
  • TLS 1.3 的提速：握手压缩到 1-RTT（密钥交换并入两边的 Hello 报文），会话恢复可 0-RTT；砍掉 RSA 密钥交换等旧算法，只保留前向安全的方案，协商更快也更安全。
  • 加分项：HTTP/3 基于 QUIC，把传输层握手与 TLS 1.3 握手合并成一步，建连总共 1-RTT 甚至 0-RTT；配合会话复用与 CDN 就近接入进一步压缩建连成本。
问法二：数字证书是如何防止「服务器身份被伪造」的？为什么中间人拿到密文也没用？
  • 证书内容：域名、持有者、服务器公钥、有效期等，由 CA 用自己的私钥对内容摘要做签名——签名人人可验，但没有 CA 私钥就造不出来。
  • 浏览器验证链：用预装的根 CA 公钥验签 → 沿证书链逐级核对 → 再核对域名匹配、有效期与吊销状态，任一环节失败即拒绝连接。
  • 密钥安全：浏览器用服务器公钥加密的预主密钥，只有持有配对私钥的真服务器能解开；中间人截获密文却没有私钥，无法还原密钥材料。
  • 会话密钥由「双方随机数 + 预主密钥」共同推导，每次连接不同，旧密钥泄露不影响其他会话（配合 ECDHE 还有前向安全）。
  • 加分项：主动说清边界——HTTPS 提供机密性、完整性、身份认证，但不防钓鱼（假站也能有合法证书）、不防 XSS/CSRF 等应用层攻击。
