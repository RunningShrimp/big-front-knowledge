② 深入浅出

为什么需要前端监控

你在自己电脑上把页面测得滴水不漏，可线上用户的手机可能是三年前的旧机型、网络可能是地铁里的弱信号——这些环境你一个都测不到。更关键的是：用户遇到 bug 的默认动作是沉默离开，而不是找客服反馈。没有监控，你往往是最后一个知道产品出问题的人。监控解决的就是「先于投诉发现问题」。

监控体系全景：三大类数据

  • 错误监控：JS 运行时错误、未被接住的 Promise 拒绝、资源加载失败、接口异常——本页重点。
  • 性能监控：加载速度、交互延迟、卡顿，采集的就是 Core Web Vitals 那套指标，外加自研的长任务统计。
  • 行为埋点：用户点了什么按钮、走了哪条路径、在哪个页面停留——出了问题能还原「用户当时在干什么」。

JS 错误怎么采：两套钩子各管一摊

window.onerror（或 window.addEventListener('error')）负责同步运行时错误：比如读了 undefined 的属性，回调里能拿到错误信息、出错文件、行号列号。window.addEventListener('unhandledrejection') 负责另一摊：Promise 被拒绝却没有任何 catch 接住的情况——异步代码越来越多，这类错误占比很高，onerror 是收不到它的。

还有个容易漏的角落：资源加载失败（图片、脚本、样式表请求失败）触发的 error 事件不会冒泡，window.onerror 完全收不到。标准做法是在捕获阶段监听 error 事件，再判断事件目标是不是一个资源元素，从而和 JS 错误区分开。

接口异常怎么采：别指望全局钩子

接口报 500、超时，各自以不同方式抛出，全局钩子抓不全也不带业务上下文。所以业内做法是在封装好的请求层统一接住：不管底层用什么方式发请求，都过同一个包装函数，失败时记录请求地址、状态码、耗时、关键参数摘要，再交给上报队列。

上报怎么发：通道与策略

  • 通道：早期用「动态创建图片、把数据拼进地址」打点；普通请求在页面卸载时会被浏览器取消；navigator.sendBeacon 专为「页面关闭前最后一搏」设计——即使页面正在卸载，浏览器也会尽力把数据送出去。
  • 批量合并：错误往往成片出现，一条一个请求会形成上报风暴。把短时间内的记录攒进队列，凑一批再发。
  • 失败重试：上报本身也可能失败，失败的数据要留在队列里择机重试，不能直接丢。
  • 采样与聚合：同一个错误一分钟刷一万条，只需留几条样本加一个次数；低危错误还可以按比例采样。
  • 自我兜底：上报代码自己绝不能再抛错，否则监控反而成为新的故障源。
生活类比 · 便利店的监控摄像头与飞机黑匣子

你楼下有家 24 小时便利店（线上产品）。店长不可能 24 小时盯着每个货架（开发者不可能盯着每个用户的屏幕），但他在天花板装了一排摄像头（监控 SDK）。摄像头从不拦着顾客走路，顾客也感觉不到它的存在（监控对用户无感、性能损耗极小）；某天夜里商品被整箱搬走（线上报错），店长第二天不用等顾客投诉，直接调录像回放——看清了时间、柜台、甚至对方从哪个门进来（错误发生的页面、文件行号、堆栈、用户环境）。没有摄像头，他只能等顾客主动说「昨天你家被偷了」，而大多数顾客的选择是再也不来。

而错误队列就像飞机上的黑匣子：飞机（页面）正常运行时，它安安静静只记录不出声；一旦出现异常，它把当时的关键参数原样存下来（错误类型、堆栈、环境快照）。飞机平安落地，记录就攒着，落地后统一交给地面分析（批量上报）；万一飞机失联（页面被关闭），黑匣子也要想办法把最后的数据送出去——这正是 sendBeacon 存在的意义。要是黑匣子自己天天冒烟短路（上报代码拖垮性能、自己报错），航空公司早就把它拆了——所以监控的第一戒律是：别打扰飞行。

④ 知识联结

前置依赖：Core Web Vitals 性能指标——性能监控采集的对象就是这三大指标，先懂「测什么」再看「怎么采」。

向后延伸：监控负责「发现问题」，接下来学错误处理与容错设计负责「接住问题」——重试、降级、兜底，让单个故障不至于拖垮整个页面。

交叉链接：

  • Promise 与 async/await —— 看不懂 Promise 的拒绝语义，就理解不了 unhandledrejection 为什么会出现
  • 事件循环与任务队列 —— 错误在哪一轮循环里抛出、全局钩子何时收到，都由事件循环决定
  • 运行时优化：防抖、节流与计算缓存 —— 上报的采样降频与批量合并，用的正是节流与攒批的思想

⑦ 面试视角

问法一：让你从零设计一个前端错误监控系统，你会怎么做？
  • 采集层：window.onerror 抓同步错误、unhandledrejection 抓未接住的 Promise 拒绝、捕获阶段监听 error 事件抓资源失败、请求层统一 catch 抓接口异常，可补充白屏检测与接口耗时。
  • 上报层：错误先入内存队列，批量合并上报；页面卸载前用 sendBeacon 兜底；失败留队重试；按错误指纹去重聚合、低危采样，上报代码自身要包一层兜底，避免监控拖垮页面。
  • 数据层：后台按版本、机型、系统、地域聚合下钻；线上压缩代码用 source-map 还原成源码位置。
  • 告警层：错误率 / 影响用户数超过阈值时通知负责人，区分「新版本引入」与「存量问题」。
  • 加分项：提到监控要「无感」——上报量可控、不阻塞主线程、不在关键路径上做额外工作。
问法二：window.onerror 能捕获所有 JS 错误吗？会漏掉哪些？
  • 漏掉未接住的 Promise 拒绝：那归 unhandledrejection 管，两者是互补关系。
  • 漏掉资源加载失败：img / script / link 的 error 事件不冒泡，不会走到 window.onerror，需要捕获阶段监听 error 并判断事件目标。
  • 跨域脚本报 "Script error."：出于安全，页面拿不到别人域下脚本的具体报错，需给 script 标签加 crossorigin 属性且对方返回 CORS 响应头。
  • 已被 try/catch 接住的错误不会再触发全局钩子；另外语法错误在解析阶段就失败，运行时钩子也收不到（构建期就能暴露）。
