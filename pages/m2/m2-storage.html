② 深入浅出

一、为什么浏览器需要「存东西」

网页一刷新，JS 变量就全部清零；HTTP 请求之间也互相「失忆」。可产品需要记住东西：登录状态、购物车、主题偏好、离线草稿……于是浏览器提供了几个容量、生命周期、行为各不相同的「存储柜」。挑错柜子轻则浪费流量，重则丢数据、出安全问题。

二、Cookie：随身口袋名片，走到哪递到哪

Cookie 是最老的存储：容量很小（约 4KB），最大特点是每次向同源发起 HTTP 请求时自动随请求发送——这是它的本职：让服务器在无状态的 HTTP 上认出「这是谁」。主要属性： 生命周期用 Expires（绝对时间）或 Max-Age（相对秒数）设置，不设置就是会话级 Cookie，浏览器关闭即消失； 作用域用 Domain 与 Path 限定发往哪些路径；安全属性有三个：HttpOnly（页面脚本读不到，防 XSS 偷取）、Secure（仅加密连接发送）、SameSite（限制跨站附带，防 CSRF）。 因为「每个请求都带着」，往 Cookie 里塞大文件是典型的反模式——白占请求带宽。

三、localStorage 与 sessionStorage：家里的储物柜

Web Storage 提供两个兄弟接口，容量都在 5MB 级，只存字符串（存对象要先序列化），API 是同步的 getItem / setItem / removeItem / clear： localStorage：持久保存，关浏览器、重启电脑都还在，除非代码或用户手动清除；同一源的所有标签页共享，且能收到 storage 事件感知彼此的修改。 sessionStorage：会话级，标签页关闭即清空，而且每个标签页独立——同一网站开两个标签页，各自的 sessionStorage 互不相通，适合「本次操作流程」的临时数据（如表单多步草稿）。 它们不会自动随请求发送，纯粹是页面自己用。也正因页面脚本能随便读，敏感凭证放这里要掂量 XSS 风险。

四、IndexedDB：私人档案室

要存大量结构化数据（离线笔记、聊天记录、离线缓存的数据集），4KB 和 5MB 都不够用，就该请出 IndexedDB：浏览器内置的事务型数据库——容量可达数百 MB 甚至更多， 数据按「对象仓库（object store）」分门别类，每个仓库有主键，可以建索引加速查找；所有读写都必须在事务里进行，保证一批操作要么全部成功要么全部回滚； API 是异步的（事件或 Promise 包装），不会卡住页面；存取用结构化克隆，对象、数组、甚至二进制都能直接放，不必先转字符串。代价是 API 繁琐，实际项目常借助封装库。

五、场景选型速查

登录态：首选 HttpOnly + Secure + SameSite 的 Cookie，由服务端配合 Session 或令牌机制——脚本偷不走，还能防 CSRF。 主题偏好、界面设置等纯前端小数据：localStorage，持久且不占请求带宽。 一次性流程的临时数据：sessionStorage，关页即走，不留垃圾。 大量结构化数据的离线能力（离线笔记、待同步队列）：IndexedDB。 原则一句话：服务器要读的放 Cookie，页面自己用的小数据放 Web Storage，大数据用 IndexedDB；任何存储都不该明文放敏感信息。

生活类比 · 小李通勤路上的四种「口袋」

小李每天通勤，身上有四种地方可以装东西。Cookie 是他西装胸前口袋里的名片：容量小，只装得下几行字（约 4KB）；但有个怪规矩——每进一栋写字楼（每发一次请求），保安都要求他把这张名片递出去过目，所以名片上只能写身份信息（登录态），塞张大照片进去他天天累得慌（占带宽）。名片还能设定「只用一周」（Max-Age），到期自动作废。 localStorage 是他家里的储物柜：能装 5MB 的东西，放在家里（浏览器里）不出门、不给人看（不随请求发送），每天回家都能取到（持久化），想处理得自己动手（手动清除）。 sessionStorage 是酒店房间的临时置物袋：也是 5MB 级，但退房（关闭标签页）时酒店直接清走；而且每间房的袋子互相独立（标签页隔离），隔壁房间翻不到你这袋。 IndexedDB 是他租的私人档案室：空间大得多，档案按抽屉分门别类（对象仓库）、每个抽屉有编号目录（索引）能快速翻找，存取都要走登记簿（事务），一沓文件要么全部登记成功要么全部作废。 小李的教训：把全家福塞进名片口袋（大文件放 Cookie）会天天累垮；把房卡写进置物袋后想第二天再用（跨会话数据放 sessionStorage）就会发现袋子早被清空；而把银行卡密码抄在储物柜标签上（敏感信息明文放 localStorage）更是大忌。

④ 知识联结

前置依赖：浏览器缓存策略——「本地留副本、按有效期决定去留」的判定思想，与 Cookie 的 Expires/Max-Age 一脉相承。

向后延伸：登录态存进 Cookie 之后，服务端如何凭它认人？见Cookie、Session 与鉴权基础；无状态的令牌方案见JWT 与 OAuth 2.0。

交叉链接：

  • Web 安全：XSS、CSRF 与 CSP —— HttpOnly / SameSite / Secure 正是 Cookie 的安全属性，存储选型直接决定安全面大小
  • 跨域与 CORS —— 「跨域携带 Cookie」要前后端同时许可，凭证与通配符互斥的规则就出自这里
  • HTTP/1.1、HTTP/2 与 HTTP/3 —— Cookie 每请求自动附带，头部体积对 HTTP/1.1 尤其敏感，是大文件不放 Cookie 的底层原因

⑥ 巩固复习

一句话讲给外行听：浏览器给了你四种口袋——名片口袋（Cookie）小但每次进门都要递给人看；家里储物柜（localStorage）能装还不跟着跑；酒店置物袋（sessionStorage）退房就清空；私人档案室（IndexedDB）能分门别类存大量档案——装什么，先想清楚「要不要给服务器看、要放多久、有多大」。

建议复习时间：今天睡前默写「容量 / 是否随请求发送 / 生命周期」三维对比表；1 天后、3 天后、7 天后各回来重做一遍例题（对应遗忘曲线 1/3/7 天间隔），站点会在地图页标出「该复习了」。

⑦ 面试视角

问法一：Cookie 与 localStorage 的核心区别有哪些？
  • 容量：Cookie 约 4KB；localStorage 约 5MB 级，差两个数量级。
  • 发送行为：Cookie 在每次同源 HTTP 请求中自动附带（服务端也能下发/修改它），会占用请求带宽；localStorage 完全在浏览器本地，不随请求发送。
  • 生命周期：Cookie 用 Expires / Max-Age 设定，不设置则为会话级（浏览器关闭即失效）；localStorage 持久保存，直到被代码或用户清除。
  • API 与数据形态：document.cookie 接口原始难用；localStorage 是 getItem/setItem 等同步 API，且只能存字符串（对象需序列化）。
  • 作用域：Cookie 可用 Domain/Path 细分；Storage 按源隔离，sessionStorage 还额外按标签页隔离。
  • 场景结论：服务器需要读的状态（登录态配合 HttpOnly）放 Cookie；纯前端偏好与缓存放 localStorage。
问法二：登录令牌该放 HttpOnly Cookie 还是 localStorage？怎么权衡？
  • HttpOnly Cookie：页面脚本完全读不到，XSS 即使注入成功也偷不走令牌；配合 Secure 只走加密连接、SameSite 缓解 CSRF；代价是要处理 CSRF 防御（Token/SameSite）与跨域场景下的 credentials 配置。
  • localStorage：读写方便、不涉及跨域凭证问题；但任何一次 XSS 得手令牌即泄露，且无浏览器层兜底，必须靠严格的输出转义 + CSP 把 XSS 挡死。
  • 通用加固：令牌短有效期 + 刷新机制、绑定设备指纹、敏感操作二次确认、服务端可吊销。
  • 结论倾向：安全优先选 HttpOnly Cookie；选 localStorage 必须以「把 XSS 防御做到位」为前提，并能在面试里说清两种方案的攻防面。
  • 加分项：提到两者都不要存可长期明文使用的敏感信息，以及多标签页共享登录态时 Cookie 天然同步、Storage 可靠 storage 事件同步。
