② 深入浅出

一、HTTP 是什么：浏览器与服务器之间的一问一答

你在地址栏输入网址回车，浏览器就要去找存放网页的电脑（服务器）要东西。双方隔着网络互不见面，必须约定一套说话的固定格式——这就是 HTTP（超文本传输协议）：浏览器发「请求」，服务器回「响应」，一来一回像寄信，信纸格式双方都要认得。后面学的 HTTPS（加密版）、缓存（响应头的保质期）、跨域（放行规则），全是建立在这套信件格式之上的「附则」。

二、拆一封「信」：请求行 / 状态行、头部与正文

请求报文分三段：请求行（第一行，写明「干什么、要什么」，如 GET /list?page=2 HTTP/1.1）＋ 头部（一行一条的元信息，如 Host: e.com、Accept: text/html、Cookie: ...）＋ 正文（可选，POST 提交的表单或 JSON 就放在这）。 响应报文对称地分三段：状态行（如 HTTP/1.1 200 OK）＋ 响应头部（Content-Type 告诉浏览器正文是什么类型、Cache-Control 交代缓存策略、Set-Cookie 下发名片）＋ 响应正文（HTML、图片字节、JSON 数据等「货」）。 一句话记忆：头部是「关于货的说明」，正文才是「货」——后面缓存页会看到，304 的省流量原理就是「只回说明、不回货」。

三、常用方法：动词要用对，还要讲「幂等」

请求行的第一个词是「动词」（方法），常用的四个： GET——读数据（看商品详情）；POST——提交/新建（下订单）；PUT——整体替换（把档案整份覆盖更新）；DELETE——删除（注销账号）。 面试爱考的词是幂等性：同一个请求执行一次和执行一百次，对服务器资源状态的影响是否相同。GET 幂等（读多少遍都一样）、PUT 幂等（覆盖多少遍结果一致）、DELETE 幂等（删一次和删十次，剩的都是「没有」）、POST 不幂等（提交十次可能生成十笔订单——这就是「下单按钮防重复点击」的根源）。幂等还带来工程收益：幂等的请求丢了可以放心自动重试。

四、状态码家族：看首位数字就知道结果

状态行里那个三位数是「办理结果」：1xx 收到了，继续说；2xx 成功（200 成功且带正文、204 成功但没内容）；3xx 重定向（301 永久搬家、302 临时借道、304 缓存协商通过「没变，用你本地那份」）； 4xx 客户端的问题（400 参数不对、401 没登录、403 登录了但没权限、404 找不到资源、429 请求太频繁）；5xx 服务器的问题（500 内部错误、502 网关收到坏响应、504 网关等上游超时）。调试口诀：4xx 先查自己发的请求，5xx 先查服务端日志。

五、HTTP/1.1 的痛：一条车道上的队头阻塞

网页要加载几十个资源，但 HTTP/1.1 有一条硬规矩：同一条连接上，请求-响应必须一来一回排队——前一个响应没送完，后面的请求只能干等。想象一辆超大的 CSS 文件慢慢吞吞往前挪，它后面排着的 3 张小图片全被堵死，这就是队头阻塞（队首堵，队尾全堵）。 1.1 也有补救：keep-alive 让一条 TCP 连接可以反复用（省掉每次重新握手的成本），浏览器还会对同一域名并发开约 6 条连接——但每条连接内部依然串行排队，而且连接数有上限，队头阻塞并没有消失，只是排了更多的队。

六、HTTP/2：把报文切成帧，多车道并行

HTTP/2 的核心一招是多路复用：把报文拆成一个个小二进制帧，每个请求-响应占一条「流」，同一条 TCP 连接上多条流可以交错传输——慢响应的帧先传一部分，不耽误其他流的帧穿插着跑，到达后按流号重新拼装。效果：一个慢请求只堵自己，不再殃及别人；连接数也省了（一条连接就够）。 另外两件配套小事：头部压缩（头部字段重复率高，做字典压缩省流量）与服务器推送（服务器猜你要什么，提前推）。但注意：HTTP/2 治的是 HTTP 层的队头阻塞——底下的 TCP 还有自己的一层：TCP 要求字节流严格按序交付，丢一个包，后面所有流的数据都得等重传补齐，所有流一起停。

七、HTTP/3：连底座一起换——QUIC

HTTP/2 的剩余瓶颈在 TCP 本身，改不动它，那就换掉：HTTP/3 把传输底座从 TCP 换成 QUIC（建在 UDP 之上的新协议）。三件大事： ① 流级独立确认：每条流单独编号确认，某条流丢包只重传那条，其他流照跑——把传输层队头阻塞也解决了； ② 握手更快：QUIC 把传输与加密握手合并，建连往返更少（配合 TLS 1.3 通常一次往返就能发数据）； ③ 连接迁移：连接用一串身份号标识而不是「IP+端口」，手机从 Wi-Fi 切到流量，连接不必断开重连。 三代版本一句话总结：1.1 一条车道排队；2 多车道并行但桥墩还是 TCP；3 连地基换成 QUIC，个别车道塌方不再殃及全桥。

生活类比 · 早高峰过江的通勤车队

一队车要过江送四件货：一件大 CSS 家具（又大又慢）和三件小图片包裹。HTTP/1.1 时代，江上只有一条单车道大桥：同一时刻只放一辆车，前车不到后车不发——大家具慢慢挪，三件小包裹在桥口干瞪眼，这就是队头阻塞。 后来桥务处搞了「年卡闸机」（keep-alive）：车过桥不用每次重新排队买票（TCP 不用反复握手），省了办手续的时间，但桥面还是一次一辆，队头阻塞照旧；顶多旁边再修五条一模一样的单车道（浏览器并发约 6 条连接），可每条车道内部照样排队。 HTTP/2 把大桥拓宽成多车道（多路复用），还规定货车可以把货拆成小箱子（帧）交错运：慢车道上的大家具分批运，不挡快车道的包裹，各送各的。可惜桥墩还是老地基（TCP）：某处塌方（丢包），全桥所有车道一起停运等抢修。 HTTP/3 干脆连地基一起换，新地基叫 QUIC：每条车道独立编号、独立抢修（流级独立确认），个别塌方只停那条道；而且新地基记人不靠车牌（IP+端口）而靠通行证（连接 ID），你从 WiFi 切到流量不用下车重新安检（连接迁移）。

⑥ 巩固复习

⑦ 面试视角

问法一：HTTP/2 的多路复用和 HTTP/1.1 的 keep-alive 有什么区别？
  • keep-alive：只是复用同一条 TCP 连接，省去反复握手建连的成本；但连接内请求-响应仍是一来一回串行，前一个响应没完，后面的请求必须等——应用层队头阻塞还在。
  • 多路复用：把报文拆成二进制帧，一条连接上多个「流」并行交错传输，到达后按流号重组——慢响应只堵自己的流，不再堵别人。
  • 结论一句话：keep-alive 省的是「建连接的次数」，多路复用省的是「排队的时间」，二者解决的不是同一个问题。
  • 加分项：指出 HTTP/2 仍有 TCP 层队头阻塞（丢包时所有流一起等重传），这才是 HTTP/3 换 QUIC 的动机；顺带提头部压缩（HPACK）与二进制分帧。
问法二：HTTP/3 相比 HTTP/2 改了什么？为什么能更快？
  • 底座更换：传输层从 TCP 换成基于 UDP 的 QUIC 协议——因为 TCP 是操作系统内核层的老协议，改动空间几乎为零。
  • 彻底解决队头阻塞：QUIC 在传输层给每条流独立编号、独立确认，某条流丢包只重传那条流，其他流不受牵连；而 TCP 一丢包所有流都得等按序补齐。
  • 建连更快：QUIC 把传输握手与 TLS 握手合并（通常 1-RTT，重连可 0-RTT 恢复），首包更早发出。
  • 连接迁移：连接由连接 ID 标识而非「IP+端口」，网络切换（Wi-Fi ↔ 蜂窝）不断线、不重握手。
  • 加分项：说明 UDP 只是「载体」，可靠传输、拥塞控制、加密都由 QUIC 在用户态重新实现；HTTP/3 语义层（方法、状态码、头部语义）与 HTTP/2 一脉相承。
