② 深入浅出

一、同源策略：浏览器的「小区门禁」

两个地址要算同源，必须协议、域名、端口三者完全一致：协议不同（https 对 http）、域名不同（a.com 对 b.com）、端口不同（443 对 8443），任何一个对不上都算「跨域」。 这条规矩叫同源策略，是浏览器最核心的安全防线：没有它，你登录过的任何网站，都能被另一个恶意网页用你的身份随意读写。 注意两点边界：其一，跨域限制是浏览器行为，服务器之间的调用（如后端互调、curl）不存在跨域；其二，img、script 等标签本身可以跨域加载资源（所以能用 CDN），被限制的主要是「脚本读取跨域响应内容」这类操作。

二、CORS：服务器主动发放的「通行许可」

跨域不是要一刀切禁止，而是要「经过许可」。CORS（跨源资源共享）就是这套许可机制：服务器在响应头里写明「我允许哪个来源访问我」，浏览器核对许可后再决定要不要把响应交给页面脚本。 三个关键响应头：Access-Control-Allow-Origin（允许的来源，如具体的一个源；带凭证时不能写通配符 *）、 Access-Control-Allow-Methods（允许的请求方法）、Access-Control-Allow-Headers（允许的自定义请求头）。

三、简单请求：直接放行，事后查票

并非所有跨域请求都要多走一步。同时满足下面条件的算简单请求，浏览器直接发出，收到响应后再核对许可：

① 方法是 GET、POST、HEAD 之一；② 请求头只包含安全名单里的字段（如 Accept、Accept-Language、Content-Language 等少数几个）； ③ Content-Type 仅限于 text/plain、application/x-www-form-urlencoded、multipart/form-data 三种传统表单类型。 这些都是早年间 HTML 表单就能发出的「祖传请求」，服务器本来就得有能力处理它们，所以浏览器放心直接发。

四、预检请求：先递签证明，再放正主

不满足简单请求条件的（比如带 X-Token 自定义头、用 PUT/DELETE 方法、Content-Type 是 application/json），浏览器会先拦下真正的请求，改发一个 OPTIONS 方法的预检请求： 「我接下来想用某某方法、某某头来访问你，可以吗？」服务器用 Allow-Origin / Allow-Methods / Allow-Headers 回复许可；预检通过后，浏览器才发出真正的请求。 预检是每个新请求序列开始前的一次额外往返，可以通过 Access-Control-Max-Age 让浏览器把预检结果缓存一段时间，减少重复 OPTIONS。 面试常问「为什么要有 OPTIONS」：因为非简单请求可能携带服务器没预期过的能力（新方法、新头部），先确认可以避免服务器收到它无法安全处理的「写操作」请求。

五、跨域携带 Cookie：身份不能随便外借

默认情况下，跨域请求不带 Cookie。要带上，前后端要同时配合：前端在 fetch 中把 credentials 设为 'include'（XHR 则设 withCredentials = true）； 服务端除了允许该来源，还必须返回 Access-Control-Allow-Credentials: true，且此时 Access-Control-Allow-Origin 不能是通配符 *，必须写明确的具体来源——「允许全世界」和「允许刷卡进入」不能同时成立。

六、JSONP：老办法与它的退场

在 CORS 普及之前，常用的跨域取数手段是 JSONP：script 标签加载不受同源策略限制，于是让服务器把数据包在一个函数调用里返回，页面提前定义好这个函数就能收到数据。 但它只能 GET、需要服务端特殊配合、且执行的是「远端返回的代码」，安全性差。如今首选 CORS，JSONP 只在兼容极老浏览器时才考虑。

生活类比 · 阳光小区住户去月光公寓串门

小陈住在「阳光小区」（页面所在的源），想去「月光公寓」（另一个源的服务器）拿点东西。月光公寓门口有保安（浏览器）把守——这是小区门禁（同源策略）。 小陈直接往里闯是不行的：就算他溜进去了（请求其实发出了），保安也会把他带回来的东西当场扣下（浏览器拦截跨域响应）。 除非月光公寓物业在门口贴出告示：「允许阳光小区居民进入」（Access-Control-Allow-Origin 指明来源），保安核对告示后才放行。 如果小陈要带一个大箱子（自定义头 X-Token）进去，规矩更严：保安会先不让正主进门，而是自己跑去物业前台问一句「这个人能带箱子进吗？」（OPTIONS 预检）， 物业答复「可以，箱子也报备过了」（Allow-Methods / Allow-Headers），保安这才回去放正主进来——多跑一趟，但保障了公寓安全。 至于门禁卡（Cookie）：物业明说「只许阳光小区这位住户刷卡」（具体来源 + Allow-Credentials），而不能挂一块「谁都能刷卡」的牌子（通配符）——身份凭证绝不发给匿名大众。

④ 知识联结

前置依赖：HTTP/1.1、HTTP/2 与 HTTP/3——看懂请求方法、请求头与 OPTIONS，才明白预检在检什么。

向后延伸：同源策略挡住的「坏人」只是安全体系的入口，接下来系统学习 XSS / CSRF 防御，见Web 安全：XSS、CSRF 与 CSP； CORS 携带 Cookie 的许可机制，与登录态在服务端如何保管直接相关，见Cookie、Session 与鉴权基础。

交叉链接：

  • RESTful API 设计 —— 前后端分离下 API 常部署在不同源，Allow-Methods 能不能放开 PUT/DELETE 由接口设计决定
  • 浏览器存储：Cookie、Web Storage 与 IndexedDB —— Cookie 正是「跨域携带凭证」的主角，其作用域属性与同源判定同源同根
  • HTTPS 与 TLS 握手 —— 协议不同的两个地址就算跨域，部署时统一走 https 是减少跨域麻烦的第一步

⑦ 面试视角

问法一：为什么会出现 OPTIONS 请求？什么条件算「简单请求」？
  • 非简单请求在正式发送前，浏览器会先发一个 OPTIONS 方法的预检请求，询问目标服务器「允许这个来源用这些方法、这些头访问吗」。
  • 简单请求三条件（同时满足）：方法为 GET / POST / HEAD；请求头仅限安全名单字段（Accept、Accept-Language、Content-Language 等）；Content-Type 仅限 text/plain、application/x-www-form-urlencoded、multipart/form-data。
  • 预检的意义：非简单请求可能携带服务器未预期的能力（自定义头、PUT/DELETE 等写操作），先确认可避免服务器收到无法安全处理的请求。
  • 预检响应用 Access-Control-Allow-Origin / Allow-Methods / Allow-Headers 表明许可；Access-Control-Max-Age 可让浏览器缓存预检结果，减少重复 OPTIONS。
  • 加分项：指出预检是浏览器行为，服务器之间互调、用工具直接请求接口都不会触发。
问法二：跨域请求要带上 Cookie，前后端分别要做什么？JSONP 与 CORS 怎么取舍？
  • 前端：fetch 把 credentials 设为 'include'（XHR 则 withCredentials = true）；不带凭证的跨域默认不发送 Cookie。
  • 服务端：返回 Access-Control-Allow-Credentials: true，且 Access-Control-Allow-Origin 必须是具体来源，不能是通配符 *——「匿名放行」与「凭证放行」互斥。
  • JSONP：利用 script 标签不受同源限制，服务端把数据包进函数调用返回；只能 GET、需服务端配合、执行远端代码有安全隐患。
  • 取舍：首选 CORS（方法、头部、凭证支持完整，纯头部协商、不执行远端代码）；JSONP 仅在兼容极老浏览器且只读 GET 的场景下考虑。
  • 加分项：提到开发环境的替代思路——由构建工具的开发服务器做代理转发，让请求「同源化」，从源头绕开跨域。
