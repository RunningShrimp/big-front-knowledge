② 深入浅出

一、XSS：数据被当成了代码

XSS（跨站脚本攻击）的本质一句话就能说清：不可信的数据被浏览器当成了代码来执行。页面里的留言、评论本该是纯文字，但如果用户提交的内容未经处理就被拼进了页面结构，浏览器分不清「这是内容」还是「这是指令」，就会照着执行。 按恶意内容进入页面的路径，常见三种形态：存储型——恶意内容被存进数据库（如留言板），每个打开页面的用户都会中招，危害最大； 反射型——恶意内容藏在链接参数里，服务器把它原样「反射」回页面，需要诱导用户点击特制链接； DOM 型——纯前端问题，页面自己的脚本把不可信数据直接写进了会当 HTML 解析的容器（如直接拼接插入），服务器毫无察觉。

二、XSS 防御体系：让数据永远是数据

防御 XSS 是一套组合拳，核心三板斧：

输出转义：把数据渲染进页面之前，把会改变结构的字符替换成「纯展示」的写法（如 & 变 &amp;、< 变 &lt;），数据就永远只被当作文字。注意要按输出上下文选转义规则：进 HTML 正文是一套、进属性值是一套、进 JS 字符串又是一套，一把钥匙开一把锁。 HttpOnly Cookie：给存放登录态的 Cookie 加上 HttpOnly 属性后，页面脚本完全读不到它——即使 XSS 防线失守，最值钱的凭证也偷不走。 输入校验与最小化注入：对用户输入做长度与格式约束；富文本场景不做「一刀切转义」，改用白名单过滤器只保留安全的标签与属性；使用现代框架时享受默认转义，慎用一切「按原始 HTML 插入」的口子。

三、CSRF：不偷代码，只借身份

CSRF（跨站请求伪造）的巧妙之处在于：请求里没有任何攻击代码。用户在 A 网站登录后，浏览器会在此后对 A 的每个请求里自动附上 Cookie（这是 Cookie 的正常行为）； 此时如果用户被诱导访问了恶意网页 B，B 里的页面偷偷向 A 发出一个请求——浏览器一看目标是你登录过的 A，就把 Cookie 带上了，A 的服务器分不清这是用户本人操作还是别人替他点的头，于是「替用户」完成了操作。 一句话：XSS 是「我的站点执行了别人的代码」，CSRF 是「别人的站点借用了我的身份」。

四、CSRF 防御：让伪造请求带不上合法凭证

CSRF Token：服务端给每个会话发放随机一次性令牌，埋在表单隐藏字段或自定义请求头里，提交时校验。恶意站点处于另一源，受同源策略限制读不到你站点页面里的令牌，伪造的请求自然缺票。 SameSite Cookie：把 Cookie 标记为 SameSite=Lax / Strict，浏览器就不在跨站请求里附上它——从「自动带身份」这一环直接掐断。 Origin / Referer 校验：服务端检查请求来源头，非本站来源的关键操作直接拒绝。三者常叠加使用，关键操作（改密码、转账）再加二次确认。

五、CSP：从源头限定「谁能在这页面上跑」

CSP（内容安全策略）是浏览器执行的一张资源白名单：服务器通过 Content-Security-Policy 响应头声明「本页面的脚本只允许来自这些来源」，例如 default-src 'self' 只许加载同源资源；还可以禁止内联脚本、要求脚本带 nonce 一次性凭据。 即使某处转义被漏掉、恶意内容混进了页面，浏览器发现它不在白名单内也拒绝执行——CSP 是 XSS 的最后一道闸门，但它不能替代输出转义（白名单配得再严，也防不了同源内的注入点），而且防不了 CSRF（CSRF 根本不需要在你的页面里执行代码）。可先用 Report-Only 模式只上报不拦截，观察误伤后再正式启用。

生活类比 · 小区公告栏、防伪条码与盖章制度

小区门口有块公告栏（评论区），本该只贴纯文字告示。有一天有人贴了张「告示」，远看是通知，细看里面夹着一行「执行指令」——路过居民的智能眼镜（浏览器）一扫描，居然真的照着做了：这就是 XSS，内容里混进了指令。 物业随后立了三条规矩：第一，所有张贴内容必须先经过「誊抄员」，把一切疑似指令的字迹原样描成普通文字再上墙（输出转义），眼镜从此只把它当文字念； 第二，居民放钥匙的柜子（Cookie）换成只有物业能开的保险箱，居民自己都摸不到（HttpOnly），小偷翻遍公告栏也偷不走钥匙； 第三，公告栏挂出牌子「本栏只张贴物业盖章的告示」（CSP），没盖章的内容直接不上墙——就算誊抄员打了个盹，还有盖章这道闸。 再说另一件事：老王没偷你家钥匙，只是趁你把钥匙牌忘在门卫时，拿着你的钥匙牌去物业替你交了份申请（CSRF）——他借的是「钥匙牌自动代表你」的规则。物业的对策：申请单必须附上当场发放、一次一码的防伪条码（CSRF Token），外来小区的人根本拿不到；同时规定非本小区递来的单子一律不认（SameSite / Origin 校验）。

④ 知识联结

前置依赖：跨域与 CORS——同源策略是这一切的前提：攻击者读不到你源内的 CSRF Token，防御才成立。

向后延伸：登录态的发放与保管（Session / Token）是 XSS 与 CSRF 攻防的焦点，见Cookie、Session 与鉴权基础与JWT 与 OAuth 2.0。

交叉链接：

  • 浏览器存储：Cookie、Web Storage 与 IndexedDB —— HttpOnly / SameSite / Secure 都是 Cookie 的属性，存储选型直接影响安全面
  • 前端监控与错误上报 —— 上线后的安全事件常先以「异常报错」露头，监控是把防御延伸到运行时的眼睛
  • HTTPS 与 TLS 握手 —— 传输加密防的是链路上的窃听与篡改，与 XSS/CSRF 的「页面内防线」互补而非互替

⑥ 巩固复习

一句话讲给外行听：XSS 是有人往你家公告栏贴「看着像通知、实际是命令」的纸条，骗智能眼镜照做——所以上墙前要先把内容「誊成纯文字」（转义）、钥匙换保险箱（HttpOnly）、只贴盖章告示（CSP）；CSRF 则是别人捡到你忘在门卫的钥匙牌去替你办事——所以办事要当场发的一次性条码（Token），外小区的单子不认（SameSite）。

⑦ 面试视角

问法一：XSS 与 CSRF 的本质区别是什么？各自的防御思路为何完全不同？
  • XSS：恶意代码在受害者站点的页面上下文中被浏览器执行，攻击者可窃取凭证、操纵页面——本质是「注入了代码」，攻击发生在你的站内。
  • CSRF：请求里没有任何代码，攻击者借用浏览器「自动附带 Cookie」的规则，以用户身份向你的站点发伪造请求——本质是「借用了身份」，攻击发生在站外诱导。
  • XSS 防御：输出转义（按上下文选规则）、HttpOnly Cookie（凭证偷不走）、输入校验/富文本白名单、CSP 收紧可执行来源。
  • CSRF 防御：CSRF Token（站外拿不到）、SameSite Cookie（跨站不附带）、Origin/Referer 校验、关键操作二次确认。
  • 一句话总结：XSS 防的是「别让数据变代码」，CSRF 防的是「别让浏览器自动代为证明身份」；两者叠加时最危险——XSS 得手后 CSRF Token 也会被读走。
问法二：CSP 是什么？它能防住什么、防不住什么？
  • CSP 由服务端通过 Content-Security-Policy 响应头下发（也可用 meta 标签），声明本页面允许加载/执行的资源来源，由浏览器强制执行。
  • 常用指令：default-src 'self' 只许同源；script-src 限定脚本来源；配合 nonce 或 hash 允许特定内联脚本，避免一刀切放开 unsafe-inline。
  • 能防：即使转义被漏掉、恶意内容混入页面，来源不在白名单内浏览器也拒绝执行——大幅压缩 XSS 的发挥空间，是最后一道闸门。
  • 防不住：配了 unsafe-inline 或来源过宽时形同虚设；防不了 CSRF（CSRF 不需要在页面内执行代码）；也不能替代输出转义与输入校验。
  • 加分项：提到先用 Content-Security-Policy-Report-Only 只上报不拦截，观察误伤后再正式启用；以及 report-uri 收集违规上报。
