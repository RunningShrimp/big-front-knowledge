② 深入浅出

一、问题起源：状态放在哪都难受

一个「当前登录用户」会被导航栏、设置页、下单弹窗同时使用。如果每个组件各存一份副本，改了一处其他处就是旧数据； 如果靠 props 逐层传，爷爷传爸爸、爸爸传孙子，中间五层组件被迫当「传声筒」（术语叫 props 钻透），拆改一处牵动全身。 状态共享的两大痛点：副本不一致和传递链太长。状态管理库就是为了治这两个病。

二、药方：单一数据源 + 单向数据流

核心思想就两句话：全应用只留一份全局 state（单一数据源，single source of truth）； 谁都不许直接改它，只能「申报」。申报的格式叫 action——一个描述「发生了什么」的普通对象，如 { type: 'SELL', n: 2 }。处理申报的叫 reducer——一个纯函数，拿着「旧 state + action」算出「新 state」，绝不顺手改旧数据。 store 负责保管 state、执行 dispatch、广播变化。整条链路是闭环：视图发 action → reducer 算出新 state → store 存下并通知 → 视图刷新， 数据只朝一个方向流，出了问题顺着日志就能定位。

三、Redux 三原则，与 Vuex/Pinia、Zustand 的对比

Redux 把上面的思想立成三条规矩：① 单一数据源——全应用一棵 state 树； ② state 只读——唯一修改方式是 dispatch action；③ 纯函数修改——reducer 输入相同输出必相同。 各家方案思想同源，差别在约束强弱与 API 繁简：Vuex / Pinia 是 Vue 生态的实现，Pinia 去掉了 Vuex 的 mutation 层、 天然支持按模块拆 store、对 TS 更友好；Zustand 走极简路线，一个函数创建 store，组件里像用 Hook 一样取值。 记住：库只是形式，「集中存放、显式变更、单向流动」才是灵魂。

生活类比 · 公司统一知识库

三个部门各自拷贝一份项目文档（组件各存状态副本），一周后版本打架：A 部门改到 v5，B 部门还停在 v3，开会吵成一团。 公司于是建立统一知识库：所有人只从同一份源头（单一数据源）读取，谁也不许在本地另存「官方版」。

要改内容，必须提交一份写明「改什么、为什么改」的申请单（dispatch action）；管理员按固定规则审批定稿 （reducer 纯函数：同样申请单 + 同样旧版本，必然得到同样新版本），从不偷偷直接改文件； 每张申请单都留档可回溯（action 日志，甚至能按顺序重放出任意历史版本）；文件一更新，订阅的部门自动收到通知（subscribe）。

四、状态分类：不是什么状态都值得进全局库

先分两类：服务端状态（列表、详情——本质是远端数据的缓存，要考虑去重、失效、重新拉取）和 客户端状态（主题色、弹窗开关、表单草稿）。服务端状态如今常交给请求缓存库打理，全局库只管真正的客户端共享状态。 什么时候才需要引入状态库？出现这些信号再说：多个页面/多个层级要频繁共享同一份状态、状态间有派生关系、 变更需要留痕调试。一个按钮自己的开关文字、一个表单没提交的草稿，用组件本地 state 就好——上全局库是杀鸡用牛刀，还添堵。

④ 知识联结

前置依赖：React 核心与 Hooks——组件内部「state 驱动视图」是地基； 全局状态管理只是把「这份 state」从组件里搬到了 store，单向流动的方向从未改变。

向后延伸：路由地址本质上也是一种全局状态（当前视图 = f(当前路由)），去 前端路由原理看它如何被管理；多个 store 如何按业务拆分、组件如何消费， 见 组件设计原则。

交叉链接：

  • Vue 响应式原理 —— Pinia 依赖 Vue 的响应式做「store 变了视图自动更新」这最后一步。
  • 作用域与闭包 —— createStore 里「state 藏在闭包里、只暴露只读接口」就是闭包的经典应用。
  • 浏览器存储 —— 全局状态存内存、会话结束即清；要跨刷新持久化，得落 localStorage 一层。

⑦ 面试视角

问法一：什么场景才真正需要引入全局状态管理？
  • 看信号：多层级/多页面频繁共享同一份状态（登录信息、购物车、主题）、兄弟组件间要双向同步、变更需要留痕与回溯调试。
  • 反面清单：仅组件内部使用的 UI 开关、未提交的表单草稿——本地 state 足够；纯服务端列表数据——请求缓存层更合适。
  • 代价要会说：引入库意味着更多样板代码、更高的上手成本；把所有状态塞进全局会失去模块边界，「全局变量」化的代码更难维护。
  • 加分项：先按「服务端状态 / 客户端状态」分类，再用组件本地 → 模块共享 → 全局库的顺序升级，而不是一上来就 Redux。
问法二：为什么 reducer 必须是纯函数？违反了会怎样？
  • 纯函数：相同输入（旧 state + action）永远返回相同输出，且不修改入参、不产生副作用。
  • 可预测性：状态变化完全由「action 流水」决定，可以保存每个 action、回放出任意历史时刻（时间旅行调试）。
  • 可测试性：reducer 是普通函数，不依赖环境，直接传参断言即可单测。
  • 违反的后果：在 reducer 里直接 push 旧数组、发请求、写随机数，会让「同样输入不同输出」，回放失真、渲染时序难排查。
  • 加分项：所以 Redux 约定返回全新引用（如展开运算符生成新对象/数组），配合浅比较才能正确触发订阅更新。
