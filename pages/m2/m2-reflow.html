② 深入浅出

一、流水线跑完不等于一劳永逸

上一页的流水线（解析 → 渲染树 → 布局 → 绘制 → 合成）把页面画上了屏幕，但页面不是静态照片：JS 随时在改样式、改结构。每次改动，浏览器都要判断「流水线要从哪一站重新跑」——跑的站越多，越卡。这页就把「改动 → 代价」这张对应表讲清楚。

二、重排（Reflow / Layout）：几何变了，从头量起

改动影响布局几何的属性——宽高（width/height）、位置（top/left）、内外边距（margin/padding）、字号（fontSize）、甚至增删节点、读写布局信息——都会触发重排：渲染树作废重来，从布局站起重新算几何，然后绘制、合成也全部重跑。更麻烦的是重排会「连坐」：一个元素的几何变了，它后面兄弟节点、甚至整个文档流都要重新计算，所以它是三者中最贵的。

三、重绘（Repaint）：只换颜色，不用重量

改动只影响外观、不影响几何的属性——文字颜色（color）、背景色（backgroundColor）、边框颜色、阴影（boxShadow）、visibility——触发重绘：几何没变，布局站不用重跑，但从绘制站起重跑（重新生成像素），合成站也要走一遍。比重排便宜，但依然消耗主线程。

四、仅合成（Composite）：GPU 直接换图层，最快

transform 和 opacity 是特殊两位：它们不参与文档流布局——transform 像把已画好的图层整体挪动/缩放/旋转，opacity 像调图层透明度，都不改变「元素占多大地方」。于是浏览器只需在合成站把新图层重新叠一下，由 GPU 完成，跳过布局和绘制，主线程几乎不被占用——这就是「动画优先用 transform 而不是 top/left」的根本原因：top/left 每帧重排，transform 每帧只合成。

五、强制同步布局：读写交错为什么慢

浏览器本想把多次样式改动攒成一批，到下一帧才统一布局（批处理）。但如果代码刚写完样式就立刻读布局信息（offsetWidth、getComputedStyle 等），浏览器为了给你正确的值，被迫立刻同步执行一次布局——攒批计划被打破。循环里「写一次、读一次」重复 N 次，就触发 N 次强制布局，这就是性能事故里高频出现的布局抖动（Layout Thrashing）。解法是读写分离：把所有「读」集中到前面，把所有「写」集中到后面。

六、优化清单与 will-change 的两面性

减少重排重绘的常用手段： ① 批量改样式：多次修改合并成一次（切换一个 class，或用 cssText 一次写全）； ② 读写分离：先批量读布局，再批量写样式，避免循环内交错； ③ 动画用 transform/opacity：让每帧只走合成站； ④ 对「脱离文档流」的元素做频繁改动：position: fixed/absolute 的元素重排连坐范围小； ⑤ 必要时用 will-change: transform 提前提示浏览器「这个元素要做动画」，让它提前创建独立合成层。 但 will-change 是双刃剑：每个合成层都要占额外内存，给全站元素都加会让层数爆炸，合成器负担和内存压力反而拖慢页面——正确用法是只在确有动画的少数元素上、动画前加、动画后移除。

生活类比 · 老王家的三种「改主意」

老王家装修完住了半年，想调整一下。第一次他说「客厅太小，把隔墙砸了改户型」——工头哭了：量尺员要重新量（布局），油漆工要重刷被砸的墙面（绘制），家具要重新摆、全屋重新拍照（合成），连着客厅的走廊、餐厅都得跟着重排——这是重排，最伤筋动骨。 第二次他说「墙的米白色看腻了，全屋刷成浅灰」——尺寸一点没变，量尺员不用来，但油漆工得把墙面重新刷一遍（绘制），最后还是得重新拍个交付照（合成）——这是重绘，中等工作量。 第三次他说「就把客厅那张挂画换成另一张」——装修队根本不用进场，他自己踩着凳子把新海报往旧位置一贴，三秒搞定——这是仅合成：画面变了，但没动任何「结构」。 至于强制同步布局，就像量尺员刚收拾好工具，老王又喊「等等，我现在就要知道沙发到墙多远」——量尺员被迫一次又一次返场重测；而聪明的做法是：把所有问题一次问完，再一起动手改。

④ 知识联结

前置依赖：浏览器渲染流水线——重排/重绘/合成的定义，就是「流水线从哪一站重跑」；没学五站顺序，本页的代价排序就背不牢。

向后延伸：重排的直接可观测后果是页面「跳动」——Core Web Vitals 性能指标里的 CLS（累积布局偏移）专门量化它；性能优化主线则继续通向首屏与资源加载优化。

交叉链接：

  • CSS 进阶：BFC、层叠上下文与动画 —— transform 动画的性能优势、层叠上下文与合成层的对应关系。
  • 虚拟 DOM 与 Diff 算法 —— 框架先在内存里算出最小改动清单，再一次应用到真实 DOM：本质就是「批量写」的框架级实践。
  • Core Web Vitals 性能指标 —— 重排连坐让内容位移，就是 CLS 指标抓的「餐桌被突然挪走」。

⑥ 巩固复习

一句话讲给外行听：改网页的代价分三档——改尺寸位置像砸墙改户型，量尺寸、刷墙、摆家具全部重来（重排，最贵）；改颜色像重新刷漆，不用重量尺寸但要重新涂（重绘）；换图片透明度像贴一张新海报，直接贴上就完事（仅合成，最快）。

⑦ 面试视角

问法一：如何减少重排与重绘？说说常用手段。
  • 先亮代价排序：改几何属性（width/top/margin…）触发重排（布局起全跑）> 改颜色类（color/background…）触发重绘（绘制起重跑）> transform/opacity 仅合成（GPU 换图层，跳过布局绘制）。
  • 批量改样式：多次修改合并为一次（切换 class / cssText），减少触发次数。
  • 读写分离：避免在循环里「写样式 → 读 offsetWidth」交错，把读集中在前、写集中在后，避免强制同步布局（布局抖动）。
  • 动画用 transform/opacity 替代 top/left/width；频繁改动的元素用 position: absolute/fixed 脱离文档流，缩小重排连坐范围。
  • 需要时对将做动画的元素加 will-change: transform，提示浏览器提前建独立合成层。
  • 加分项：提到「改 display:none 再改回来」只触发两次重排而非中间每步一次；或提到 DocumentFragment 批量插节点。
问法二：will-change 的原理是什么？为什么不能滥用？
  • 原理：will-change: transform 等属性是给浏览器的「预告」——告诉合成器这个元素即将变化，浏览器会提前把它提升为独立合成层，动画开始时无需临时建层，避免第一帧掉帧。
  • 收益：元素有了独立图层后，transform/opacity 的每帧变化只在合成器（GPU）完成，跳过布局与绘制，主线程不被占用。
  • 滥用风险：每个合成层都要消耗额外内存（图层位图）；层数过多会让合成器管理负担加重、内存占用飙升，低端设备反而更卡。
  • 正确用法：只给确有频繁动画的少数元素加；动画结束后移除（如用 transitionend 后清掉），不要「全站无脑加」。
  • 加分项：指出某些属性本身也会隐式提升合成层（如 3D transform），效果等同隐式 will-change。
