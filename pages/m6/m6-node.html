② 深入浅出

一、Node 是什么：给 JS 装上「做后端的本事」

浏览器里的 JS 没有读写文件、开端口监听的能力。Node 在 JS 引擎外面又包了几层，自下而上是： 操作系统（真正干 IO 的地方）→ libuv（C 语言库，提供事件循环、异步 IO 和线程池）→ C++ 绑定层（把 C 的能力翻译给 JS）→ 内置模块（fs、http、path 等用 JS 包好的外壳）→ 最上面才是你写的 JS 代码，由 V8 引擎执行。记住这个分层：V8 负责「算」，libuv 负责「等和搬」。

二、异步非阻塞 IO：一个总管怎么同时接住一万个电话

「阻塞式」就像点奶茶站在柜台前干等；「非阻塞」是下单拿号就走，做好了叫号。Node 发起 IO 后立即返回继续干活： 网络 IO 交给操作系统的多路复用机制（Linux 上是 epoll），文件 IO、DNS 解析交给 libuv 线程池（默认 4 个线程）。 IO 完成后，对应的回调函数被放进事件循环的相应阶段排队，等主线程来执行。所以 Node 的「单线程」只指 JS 执行的主线程只有一条，底下干活的手其实不少。

三、事件循环六大阶段：libuv 的流水线

Node 的事件循环不是一条简单的队列，而是六个工位轮着转，每轮顺序固定：

① timers（执行到期的 setTimeout / setInterval 回调）→ ② pending callbacks（执行上一轮遗留的系统级回调）→ ③ idle / prepare（libuv 内部使用）→ ④ poll（取回 I/O 结果并执行其回调；没活时可在此挂起等待新事件）→ ⑤ check（执行 setImmediate 的回调）→ ⑥ close callbacks（执行关闭回调，如 socket 的 close 事件）。 转完一圈再来一圈，程序不退出就永不停歇。

四、与浏览器事件循环的差异

浏览器是「取一个宏任务 → 清空全部微任务」的简单模型。Node 11 及以上版本已与浏览器对齐为每个宏任务执行完立刻清空微任务； 更老的版本则是在「阶段切换时」才统一清空，输出顺序题因此有新老之分。另外两个 Node 特有的规则： process.nextTick 的回调优先级高于 Promise 微任务（当前操作一结束就插队执行，堆太多会让 I/O 饿死）； 主模块顶层同时写 setTimeout(fn,0) 和 setImmediate(fn) 谁先执行不确定（受机器性能影响）， 但在 I/O 回调内部这么写，setImmediate 恒定先执行——因为 poll 阶段结束后必经 check 阶段。

五、给零基础的三条实践提醒

① 别在主线程写大段同步计算（如百万次循环加密），它会卡住整个事件循环，所有请求一起排队；② process.nextTick 别堆量，插队太狠会饿死真正的 I/O； ③ setTimeout(fn, 0) 只表示「到 timers 阶段就执行」，不代表立刻执行。

生活类比 · 装修公司的前台总管「小诺」

小诺在一家装修公司当前台总管。她给自己立了条规矩：从不亲自拿扳手干活——她只做两件事，登记需求和转交调度。 客户电话一个接一个（并发请求），她每接一个就撕一张登记单贴到墙上，重活累活（读写文件、查资料）外包给施工队（libuv 线程池）， 网络类的活（查物流）喊一声合作方（操作系统 epoll）帮忙盯着。施工队干完一单，小诺就按登记单给客户回个电话（执行回调）。

她处理回电有固定的巡检路线，每天沿六张桌子转圈：先处理「预约到点的回电」（timers），再补办昨天的遗留手续（pending）， 顺路经过员工休息室（idle，不停留），然后到取件窗口发施工队交回来的成果（poll），再到加急窗口插一批「必须这轮处理」的特急件（check）， 最后处理退单结账（close）。走完一圈再来一圈。正因为她从不在任何一通电话上干等，一个人也撑起了整家公司的调度—— 这就是「单线程 + 异步非阻塞」。

④ 知识联结

前置依赖：事件循环与任务队列——Node 的六阶段是浏览器「宏任务 + 微任务」模型的加强版，先懂简单版再上加强版。

向后延伸：有了会跑事件的运行时，下一步就是用它监听端口、处理 HTTP 请求，见HTTP 服务：Express 与 Koa。

交叉链接：

  • Promise 与 async/await —— await 之后的代码被排进微任务；Node 11+ 里它会在每个宏任务后立刻执行
  • 运行时优化：防抖、节流与计算缓存 —— 防抖节流的定时器正是 timers 阶段的常客，卡顿排查要懂事件循环才能定位
  • 小程序双线程架构 —— 逻辑层同样是「单线程 + 队列调度」，跨线程传话与 Node 的回调排队思想相通

⑦ 面试视角

问法一：Node 与浏览器的事件循环有什么区别？setImmediate 和 setTimeout 谁先执行？
  • 浏览器：一套「宏任务队列 + 微任务」模型，取一个宏任务清一次微任务，页面渲染穿插在宏任务之间。
  • Node：由 libuv 驱动，分为 timers → pending → idle/prepare → poll → check → close 六个阶段循环。
  • 微任务时机：Node 11+ 与浏览器对齐（每个宏任务后立刻清空微任务）；更老版本在阶段切换时统一清空。
  • Node 特有：process.nextTick 优先级高于 Promise 微任务；setImmediate 的回调在 check 阶段执行。
  • setTimeout vs setImmediate：主模块顶层顺序不确定（受机器性能影响）；在 I/O 回调内部 setImmediate 恒定先执行（poll 之后必经 check）。
  • 加分项：说明 timers 阶段用最小堆管理到期时间、poll 阶段没有任务时会阻塞等待新 I/O 事件。
问法二：Node 单线程为什么能扛高并发？什么场景会把它打挂？怎么解？
  • 「单线程」仅指 JS 执行主线程：网络 IO 靠操作系统多路复用（epoll/kqueue）+ libuv 事件通知；文件 IO、DNS 走 libuv 线程池（默认 4 线程）。
  • 扛并发的本质：不为每个请求养一个线程，而是「发起 IO 立即返回 + 完成后回调排队」，主线程永远在干活而不是干等。
  • 弱点：同步 CPU 密集计算（大循环、加解密、图片处理）会阻塞事件循环，所有请求一起卡住。
  • 解法：拆小计算分批执行、worker_threads 开工作线程、子进程，或把重计算下沉到独立计算服务。
  • 加分项：提到用 perf_hooks 之类手段监控事件循环延迟，说明有线上排障意识。
