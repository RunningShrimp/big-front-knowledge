② 深入浅出

一、数据库：断电也不丢的仓库

变量存在内存里，程序一关、电脑一断，数据就没了。凡是需要留下来、下次还在、多人共用的数据（用户注册信息、订单、文章），都要放进一个专门管存储的软件——数据库。它像一座有规矩的仓库：数据怎么摆放、谁先进先出、怎么防止两个人同时改一份货单，它都替你想好了，你只要按它的「语言」下指令。

二、两大门派：表格思维与文档思维

关系型数据库（MySQL、PostgreSQL）把数据摆成一张张二维表格：每行一条记录，每列一个字段，表与表之间靠 id 相互引用。适合数据结构规整、要多表联查、对一致性要求高的场景——比如订单、账户余额。 非关系型数据库（MongoDB 等文档型、Redis 等键值型）则更自由：一条数据就是一份文档（像一个大 JSON）或一个键值对。适合结构多变、读写量巨大的场景——比如商品详情、点赞数缓存。新手先学好关系型：表格思维是地基，其他都是变体。

三、SQL 四板斧与 JOIN

操作关系型数据库的语言叫 SQL，日常就是四句：

INSERT INTO users (name, age) VALUES ('小明', 18);   -- 增
DELETE FROM users WHERE id = 7;                     -- 删
UPDATE users SET age = 19 WHERE id = 7;             -- 改
SELECT name FROM users WHERE age > 18;              -- 查（用得最多）

-- 数据分表存时，用 JOIN 把它们按关联字段拼起来查：
SELECT o.id, u.name FROM orders o JOIN users u ON o.user_id = u.id;

注意「查」是这个家族的绝对主力：页面上的列表、详情、统计，落到后端都是一条条 SELECT。所以下面的问题来了——表里有一百万行，WHERE name = '小明' 怎么才能不从头翻到尾？这就是索引登场的地方。

四、索引：给查询修一条「直达电梯」

没有索引时，数据库只能全表扫描：从第一行逐行问「你是小明吗」，最坏问完一百万行。索引的思路是另建一份有序的小抄：只存「字段值 → 行的位置」，并组织成一棵 B+ 树。B+ 树的特点是「矮而胖」：每个节点可以有几百上千个分叉（数据按页存放，一个分叉约一次磁盘读），一百万行数据的树通常只有三四层——也就是说，定位任何一行只要三四次 IO，而不是一百万次比较。树的叶子节点还首尾相连成链表，所以「查 18~30 岁的用户」这种范围查询可以顺着链表一路扫过去，这是它胜过哈希表的关键。

五、索引的代价与失效：目录不是白印的

索引不是免费的午餐：它占磁盘；每次写入（增删改）都要顺手维护这棵有序树，写越多的表，索引越要克制。而且建了索引也可能用不上——B+ 树靠「值有序」来二分定位，一旦破坏了有序性假设就失效了：对索引列套函数（WHERE UPPER(name) = ...）、以通配符开头的模糊查询（LIKE '%明'）、类型不匹配的隐式转换，都会让数据库放弃索引退回全表扫描。多列联合索引还有「最左前缀」规则：查的时候必须从最左列开始连续命中，跳过最左列就用不上。

生活类比 · 查《新华字典》：目录页 vs 从第一页翻起

小新要查「驰」字。他先翻到书前的部首检字表：马部 → 三画 → 「在第 782 页」，直接翻过去，三步搞定——这张检字表就是索引，它自己按部首、笔画排好了序，所以能快速定位。

要是没有检字表呢？小新只能从第 1 页开始一页页翻，翻到 782 页才找到——这就是全表扫描。字典越厚，逐页翻越可怕；而检字表再厚，多翻几层目录也只要几步——这就是索引把查询从「跟数据量成正比」变成「跟数据量的对数成正比」。

但代价也写在字典上：检字表自己占了开头几十页的篇幅（索引占磁盘）；而且每出新版字典收录或删掉一个字，检字表都得重新排版（写入变慢）。还有，检字表只对「知道读音/部首」的查法管用——如果你只记得「这字左边一个马、右边也念马」却说不清部首规则，检字表就帮不上忙了，这对应数据库里「破坏有序假设」的模糊查询（LIKE '%明'）同样查不动。类比值了然，结论要记准：索引加速的是「按有序规则定位」，不是任何查询都能加速。

交叉链接：

  • 浏览器存储 —— IndexedDB 就是浏览器里的「迷你数据库」，事务与索引的思想同源
  • HTTP 服务：Express 与 Koa —— 接口层收到请求后执行 SQL，再把数据库吐出的行拼成 JSON 响应
  • 虚拟 DOM 与 Diff —— 列表渲染用 key 定位节点，和索引用有序值定位数据行，是同一个「用标识换速度」的思路

⑦ 面试视角

问法一：MySQL 为什么用 B+ 树做索引，而不是哈希表或红黑树？
  • 先说硬件前提：数据在磁盘上，按「页」读取，每次读页都是一次昂贵的磁盘 IO，索引设计的核心目标是减少 IO 次数。
  • B+ 树矮而胖：单节点可容纳大量分叉（上千），千万级数据树高也只有 3~4 层，定位一行只需 3~4 次 IO；红黑树/二叉树每个节点只有 2 个分叉，树高是几十层，IO 次数不可接受。
  • 对比哈希表：哈希等值查询快，但不支持范围查询与排序；B+ 树叶子节点有序且串成双向链表，范围扫描顺链表走即可。
  • B+ 树非叶子节点只存索引不存数据，单个节点能装更多键，扇出更大树更矮；叶子层才挂完整数据行（聚簇索引）。
  • 加分项：能说出「一个节点约等于一个 16KB 数据页」与「树高等于 IO 次数」这两个量化锚点。
问法二：哪些字段适合建索引？索引有哪些代价与失效场景？
  • 适合建：WHERE / ORDER BY / JOIN ON 里高频出现的列、区分度高的列（如手机号）；不适合：区分度极低（如性别只有两三个值）、频繁更新或几乎不出现在查询条件的列。
  • 代价一：占磁盘空间；代价二：每次增删改都要同步维护 B+ 树，写入变慢——写多读少的表要克制建索引。
  • 失效场景：对索引列套函数或运算、LIKE '%xx' 前置通配、类型不匹配导致隐式转换、联合索引不满足最左前缀。
  • 排查手段：EXPLAIN 看执行计划是否走了索引（type、key、rows 等列）。
  • 加分项：指出「索引加速的是有序定位」，任何破坏有序性假设的写法都会让优化器放弃索引。
