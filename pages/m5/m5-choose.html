② 深入浅出

一、先把候选方案排成一条光谱

把主流方案按「渲染路径与性能上限」从左到右排开，能看得非常清楚： H5（WebView 渲染）→ 小程序（WebView 为主、双线程管控）→ RN（映射原生控件）→ Flutter（自带引擎自绘）→ 原生（系统直绘）。 越靠左，开发越快、发版越灵活、多端复用越省，但性能与体验上限越低； 越靠右，性能与系统能力越强，但开发节奏慢、双端要维护两套代码。 选型不是找「最好的方案」，而是在这条光谱上找业务约束对应的那个位置。

二、四维评估法：给每个方案打分

拍脑袋容易翻车，工程上通行的是四个维度逐项打分：

  • 性能体验：渲染路径长短、动画流畅度、启动速度——重交互场景的一票否决项。
  • 开发效率：改版发布节奏、热更新能力、一套代码复用度——活动类页面的生命线。
  • 团队技术栈：团队是 React 栈还是原生栈？会不会 Dart？这是经常被低估的硬约束—— 方案再好，团队驾驭不了就是负资产。
  • 生态成熟度：组件库、坑的文档、招人难度——冷门方案省下的工时会在排坑时加倍还回去。

给每个维度一个权重（按场景定），加权总分最高的方案就是当前约束下的推荐—— 注意是「当前约束下」：换一个场景重排权重，推荐很可能就换了。

三、三个典型场景走一遍

电商大促会场页：一周改三版、几天内上线、还要同时投 App 内与小程序。 开发效率与多端复用权重拉满，性能只要「够用」——H5 / 小程序一类 Web 容器方案胜出， 原生壳配上离线包兜住首屏。工具类 App：交互较复杂、长期迭代、团队是前端 React 栈—— 性能与效率都要，RN 顺理成章；若更看重双端像素一致，Flutter 是有力备选。 重交互核心链路（交易下单、密集动画）：性能上限一票否决—— Flutter 或原生优先，且核心交易模块往往保留原生兜底。

四、混合策略：成熟团队的组合拳

真实项目很少「一股脑全跨端」或「全部原生」，而是按模块分而治之： 交易、支付等核心链路用原生或高性能方案保体验上限； 运营活动、内容展示等常改页面用 H5 换发版自由；多端铺量的小程序用一套跨端框架维护。 「核心原生 + 边缘跨端」的组合，让每个模块都落在光谱上最合适的位置—— 这也是面试里最能体现工程判断力的答案。

生活类比：通勤选交通工具

搬家前先搞清楚通勤怎么走。地铁（原生）速度最快、班次稳定， 但线路是修出来的——不到你家门口，你就得为「最后三公里」另外想办法，修线路的成本极高（原生开发慢、双端各一套）。 共享单车（H5）随处可用、扫码就走（改版即上线、端端能跑）， 但刮风下雨、远距离就吃不消（复杂交互与性能上限低）。 网约车（RN / Flutter）在两者之间：随时叫车、速度不错、价钱适中（跨端复用 + 性能够用）。

真正的通勤高手不会迷信某一种车：先看今天去哪儿、几点出门、几个人同行 （场景与约束），再决定坐什么；甚至地铁加单车组合着来（混合策略）。 让一个天天坐地铁的人改骑单车上班，和让一个买菜的人天天打车，都是「方案没错、场景配错」—— 选型失误的根源从来不是车不好，而是没先看路。

⑥ 巩固复习

一句话讲给外行听：选跨端方案就像选交通工具——先看要去哪儿、多急、几个人， 再决定坐地铁（原生）、打车（RN / Flutter）还是骑共享单车（H5）；而且成熟团队常常几种车换着坐， 核心路段坐地铁，最后一公里骑单车。

建议复习时间：今天睡前复述 1 次，1 天后、3 天后、7 天后各回来重做一遍例题（对应遗忘曲线 1/3/7 天间隔），站点会在地图页标出「该复习了」。

⑦ 面试视角

问法一：让你为一个新产品选跨端方案，你会怎么论证？
  • 先讲方法再给结论：明确场景与约束（性能要求、迭代节奏、团队栈、目标端），再上四维评估（性能体验、开发效率、团队技术栈、生态成熟度）。
  • 列出候选光谱：H5 / 小程序 / RN / Flutter / 原生各自的位置，说明为何纳入或排除某几个。
  • 按场景给权重打分，输出推荐与混合策略：核心模块原生保上限、活动与内容模块跨端换效率。
  • 补充风险与再评估触发条件：如团队扩招、性能不达标、生态变化时重审选型。
  • 加分项：能引用典型结论——大促页 H5 优先、工具类 RN/Flutter 看团队栈、重交互链路原生或 Flutter 兜底。
问法二：跨端方案的性能差距，根源是什么？
  • 渲染路径：WebView 渲染走完整浏览器管线；RN 映射原生控件（旧架构有跨语言桥）；Flutter 自绘指令直达 GPU；原生路径最短。
  • 跨边界通信开销：JSBridge 传参序列化、小程序 setData 跨线程、旧 RN Bridge 的 JSON 消息，高频通信时都会成为瓶颈。
  • 启动与体积：WebView 初始化、JS 引擎启动、Flutter 引擎打进包的固定增量，各有代价。
  • 结论表述：性能差异不是「跨端」三个字的锅，而是「谁画像素、消息怎么过界」这两个架构决定的。
  • 加分项：把该结论与四维评估法勾连——性能维度的打分依据正是这些架构事实，而非口碑。
